# simlin-edit

Edits to a project: the patches a host or an agent lands, the plans of a person's gestures on a diagram, and a variable's equations as a host draws them.
It uses [simlin-base](/src/simlin-base/CLAUDE.md), [simlin-diagram](/src/simlin-diagram/CLAUDE.md) and [simlin-formats](/src/simlin-formats/CLAUDE.md), and not the compiler: an edit is made to a project whether or not it compiles.
The root `CLAUDE.md` holds the development rules; this file is a map of where functionality lives (paths are relative to this crate's `src/`) and of the standing invariants code in this crate keeps.

## Patches and equations

- `patch_fields.rs` -- the edits by field a host and the agent tools share (`SetEquation`, `SetElementEquation`, `SetUnits`, `SetNotes`, `SetLookup`, `SetDimensions`): each changes one field of one variable and leaves the rest, keeping an arrayed variable in its smallest form -- the equation every element follows (apply-to-all, or a default that applies) and the elements with equations of their own, in their dimensions' order; no own element left is apply-to-all again, and no dimension left is a scalar.
- `patch_dimensions.rs` -- the project operations that edit a dimension (`UpsertDimension`, `RenameDimension`, `RenameElement`, `DeleteDimension`) and carry the edit through every variable over it: its dimension list, its own elements' keys (an element removed takes its own equations with it) and every equation that names the dimension or the element, respelled through the variable rename's walk (`patch::respelled_text`); a rename that would leave a bracketed name meaning two things is refused, as a variable rename is.
  A stock's equation is its initial value.
  An element given a lookup takes the equation every element follows as its input, written out so every format keeps it.
  `tools::edit`'s operations are translations into these, so an agent's edit and a host's mean the same.
- `patch.rs` -- the `ProjectPatch`/`ModelPatch` operations of `project_patch.rs` (upsert, delete, rename, views, stock flows, loop names, the field edits, and `EditView`, a view edit whose model operations `editing::derived_operations` derives from the edited view when the patch applies; `is_view_only_patch` derives them to decide whether a patch needs recompiling).
  - A rename is syntactic: each expression text (`Variable::expression_texts`) is parsed as written (`Expr0::new`) to find its references, and each renamed reference is spliced into the text at its span, so everything else the modeler wrote comes back byte for byte.
    A text longer than a span addresses (`u16::MAX` bytes: `builtins::Loc` is a pair of `u16`s, and a position past them wraps) is respelled by `print_eqn` instead, decided on the text's length before any span is read.
    Neither compiler tier can serve a rename: the parse memo's tree is the expanded one (a `SMTH1(x, 3)` is already an instance read, a `PREVIOUS(x + 1)` a capture), and the lowered tree is absent for an equation the compiler refuses, which must still be renamed.
    The new name is spelled by `ast::print_ident` from its canonical form, so one holding a literal period is written quoted.
    The rename's walk is also how a text's references are read without compiling it (`patch::text_references`, each with its `Site`) and which variables' texts name a variable (`patch::variables_naming`, a rename of the name to itself): what reads a variable whose equation the compiler refuses.
  - `patch::Rename` says what a name refers to.
    A reference names the variable bare in its own model and through a chain of module instances from a model that instantiates it, resolved as `db::DepScope::resolve` does (a spelling whose head is no instance, or an instance of a model the project lacks, is one local name); a module reference's `dst` names a port through the instance it starts at, whatever that instance instantiates.
    So a rename reaches the equations, module `src`/`dst` and stock flow lists of every model that can name the variable, and every other place a model holds the name (`Model::map_variable_names`) but a diagram's labels: every view's label keeps the old name until a view edit or a diagram sync that carries the patch relabels it.
  - A rename never decides what an identifier inside a subscript's brackets names, because the compiler has no single statement of it: the dependency walk skips a dimension or an element of any dimension (`variable::ClassifyVisitor::is_dimension_or_element`), a static subscript reads an element of its axis (`compiler::subscript`, `resolve_axis_index_name`), a range reads its ends as elements only when both are, and a dimension's name is the active axis's element where an axis supplies it and the like-named variable where none does (`compiler::Context::lower_from_expr3`).
    Unifying that rule is the compiler's work; until it is one rule, a rename that would have to choose is refused, changing nothing (`patch::Reader`): when the old or the new name is a dimension's (XMILE 1.0 section 3.7.1 requires dimension names to differ from variable names), when the variable is written alone in a subscript (or at an end of a range there) and its old or new name is an element of a dimension, and when a reference's new spelling is a `dimension·element`.
    Never replace the refusal with a reading of the brackets: a second resolver of one spelling drifts exactly where the rule is non-trivial, and this one has three.
  - A rename refuses a new name that contains `"`, which has no spelling.
    It does not give a variable the name of one of the run's clock slots (`results::IMPLICIT_GLOBALS`, asked through `results::is_implicit_global`: the time, the time step, the initial and the final time): a variable of that name takes the slot's results key, where hosts read the clock, so the rule is deliberately stricter than the compiler, which resolves the quoted name.
    A model that already declares one keeps it, its display spelling included, and renaming it away respells its quoted references and leaves the bare words, which are the builtin.
    Another builtin's name (`pi`) is not refused: the printer quotes it.
  - The standing test of a rename is the run: it is refused and changes nothing, or the model computes after it what it computed before (`patch_rename_tests.rs`, on fixtures that name every refusal in the default suite, and on a corpus sample in the gates, which holds no name the subscript rule refuses).
    A delete unwires every module reference either end of which starts at the deleted variable, in any spelling: at its first segment when that is a module instance, else at the whole spelling, which is one local name.
    `SetSimSpecs` sets the project's specs and takes the root model's own away (`Project::default_model`), so the project's are what the root model runs under; another model's own specs stay.
- `equation_view.rs` -- `variable_equation`, a variable's equations as a host draws them: every variable one shape, the equation every element follows (`every`; a scalar's equation, a stock's initial value) and one cell per element in its dimensions' declared order (`own`, `follows` or `missing`), each text with its tree from the parse alone (`Expr0::new`: a builtin stays the call written), references resolved only as far as drawing needs (whether the model has the variable and its spelling, and each bracketed index as an element of its axis, then a dimension, the compiler's precedence), and a `group` node wherever the printers' one grouping rule (`ast::needs_parens`) puts parentheses.
  Spans are UTF-8 byte offsets into their own text.

## Diagram editing

`editing/` is the editing core native hosts plan through ([design plan](/docs/design-plans/2026-09-12-editing-core-in-rust.md); the invariants G1-G8, M1-M3 and E1-E6 are [the TypeScript core's](/docs/design-plans/2026-09-10-diagram-editing-core.md)).
It is tuned for touch and deliberately differs from the TypeScript planner where that planner follows from pointer-and-keyboard input; no test holds the two together.

- Flow geometry: `geometry.rs` (the G1-G8 constants, which `diagram::flow_geometry` reads too), `terminal.rs` (face attachment and terminals), `route.rs` (`route`/`route_end` over obstacles queried by region), `offset.rs`, `heal.rs`, `path.rs`, `validity.rs`.
- Planning: `base.rs` (`BaseView`, the index a tap or a drag plans against, built once), `hit.rs` (`HitIndex`, a view indexed for hit testing: every drawn element's shapes, end handles and label box computed once, and a grid of the boxes each element reaches over; an entry holds a part only where the scene draws its shape, asked of the scene's own builders and the predicates `scene::finish` filters with (`SceneShape::is_finite`, `SceneLabel::is_finite`), never of a finiteness check of its own; `hit_test` builds one for a single call; decided in tiers: a firmly held body, an end handle, a firmly held label, the nearest drawing), `gesture.rs` (`plan_tap`, `begin_drag`, `GestureSession::frame`, `plan_move`, the move-selection frame at an offset, which a drag's frame calls and a keyboard nudge plans without a session, `Plan::edit`; every edit is planned through `Changes::into_plan`, which plans nothing where the changes equal the base and commits nothing where a changed element holds a non-finite number, which the scene would draw nothing for, so a frame, its release and a nudge agree on what lands; a drop target is valid exactly where the drop is allowed (`Changes::into_drop`), so an allowed drop that changes nothing keeps its valid target and commits nothing), `links.rs` (links following moved endpoints), `preview.rs` (a frame's scene elements, through `diagram::scene`'s one element serializer), `edit_view.rs` (`plan_delete`, `plan_rename`, `derived_operations`).
- A frame allocates in proportion to what its gesture changes, never to the size of the view.
- A hit costs in proportion to what is near the point, never to the size of the view.
  The tiers walk the elements from the topmost down, and an element offering a point nothing changes nothing in that walk, so walking only the elements with a box within reach decides what walking every element decides; that equality is the grid's one claim, and `hit_prune_tests.rs` checks it (both walks, and the rule that decided, over generated scenes and World3).
- Tests: `invariants.rs` is the one oracle, every arm enumerated (`FlowArm::ALL`); `scene_gen.rs` generates scenes with its own geometry, never the checker's or the core's; every decision table derives its rows from its enum (`HitPart::ALL`, `GestureKind::ALL`, the no-drag arms of `begin_drag`, the kinds of view element a nudge moves), and a commit is checked by applying it through the production patch path.

## Tests

A test that compiles or runs the edited project uses simlin-engine, which is a dev-dependency.
What the edits by field store is saved and read back in simlin-tests (`src/simlin-tests/tests/integration/field_edits.rs`).

## Cargo features

`schema` (JSON schemas of what a patch reports), `invariants` (the checker of a diagram edit's invariants, for simlin-layout's eval harness), `test-support` (for `[dev-dependencies]` edges alone).
