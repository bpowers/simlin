# @simlin/notebook-widget

The anywidget front-end module (AFM) that hosts `@simlin/diagram`'s `Editor` inside a notebook cell for pysimlin's `ModelWidget` (JupyterLab 4, Notebook 7, VS Code, Colab). It builds to ONE self-contained ES module, `dist/widget.js`, which pysimlin ships inside its wheel as the widget's `_esm`; the engine wasm (`src/engine/core/libsimlin-browser.wasm`) ships beside it in the wheel and reaches the browser over the widget comm at runtime. Design: [docs/design-plans/2026-08-17-pysimlin-widget.md](/docs/design-plans/2026-08-17-pysimlin-widget.md).

For global development standards, see the root [CLAUDE.md](/CLAUDE.md). For the TypeScript conventions, see [docs/dev/typescript.md](/docs/dev/typescript.md).

## Hosting model (why everything here looks the way it does)

anywidget loads `_esm` by writing the module text into a `blob:` URL and `import()`ing it (anywidget `load.ts`), once per widget instance (`runtime.ts` builds a `Runtime` per model, each with a fresh blob URL). Three consequences drive this package:

- **No relative assets.** `import.meta.url` is a blob URL, so nothing next to the module can be fetched: no worker chunk, no `.wasm`, no `.css`, no font files. The bundle injects its CSS from JS (`output.injectStyles`), inlines fonts as data URIs, and receives the wasm as bytes over the comm. Anything that would emit a second output file is a bug in this package's build; rspack's ESM runtime also defines its base URI by resolving `./` against `import.meta.url`, which THROWS for blob URLs at module init -- `tools.cssLoader.esModule: false` keeps `url()` handling out of that runtime (see rsbuild.config.ts).
- **The page is someone else's.** The CSS lands in the notebook's `<head>` (no shadow root), so every global stylesheet the Editor needs -- `theme.css` (design tokens on `:root`, a universal reduced-motion rule) and katex (`body { counter-reset }`) -- is rewritten at build time to live under the widget root class `.simlin-notebook-widget` (`build/scope-css.ts`, a PostCSS plugin wired through `tools.postcss`; CSS Modules are skipped, their classes are hashed already). `build/scope-css.test.ts` runs the plugin over the real theme.css and katex.min.css and pins that no top-level selector survives without the root class, and the Playwright journey checks the page root sees none of the tokens. N displayed widgets still inject N (identical, scoped) copies of the styles -- harmless, and unavoidable while each instance is its own module.
- **Module state is per widget instance.** Every displayed widget gets its own copy of this module, its own React, and its own `@simlin/engine` wasm singleton. The only page-wide sharing possible is through `globalThis`, so `engine-bootstrap.ts` caches the COMPILED `WebAssembly.Module` (the expensive part) under `globalThis["__simlinWidgetWasmModule:<sha256>"]` -- keyed by the sha256 of the `libsimlin-browser.wasm` the bundle was built against, baked in by `rsbuild.config.ts` (`source.define` `SIMLIN_WIDGET_WASM_SHA256`; the build fails if the wasm is missing) -- and each instance instantiates its own engine from it via `ready(module)`. Two cells displaying models compile the wasm once and ask the kernel for it once; two bundles from different builds on one page (two kernels with different pysimlin versions, an old output beside a redisplay after an upgrade) each compile their own instead of the second running the first one's wasm against a JS side built for another ABI. The key states what the bundle was BUILT with, not what the kernel sent: a wheel whose widget.js and wasm come from different builds is a packaging error the staging/wheel checks own (`ASSETS.json` records both hashes).
- **`initialize` must return fast.** anywidget rejects a model whose module load plus `initialize` exceed ~2 s (`runtime.ts`, `AbortSignal.timeout(2000)`), after which every comm message for that model is dropped. `initialize` only kicks off the engine bootstrap; `render` awaits it. anywidget also queues comm messages until the module has loaded (`_handle_comm_msg` awaits `runtime.ready`), so an early kernel reply is safe.

## Engine strategy

- Wasm flavor: `@simlin/engine/internal/wasm` is aliased to `@simlin/engine/internal/wasm.supplied` -- no bundled artifact, no asset fetch; `init()` without a source throws. The bootstrap hands `ready()` the shared compiled module.
- Backend: `@simlin/engine/internal/backend-factory` is aliased to `@simlin/engine/backend-factory.direct` -- libsimlin runs on the main thread. Chosen over the Web Worker backend because a worker needs a second file (or an inline-blob worker built in a second compilation stage plus a new engine factory that spawns from source), and the widget's simulations are the Editor's sparklines and small models -- heavy runs happen in the kernel. Cost: opening/compiling a very large model blocks the notebook UI for the duration (seconds for a C-LEARN-sized model). The measured worker chunk is small (`SIMLIN_WIDGET_BACKEND=worker pnpm build`: ~38 KB raw / ~10 KB gz, self-contained), so an inline-blob worker is a contained follow-up if main-thread jank becomes a problem -- it is not a hack, just a second build stage; the as-built worker variant is NOT loadable from a blob URL (its chunk URL is resolved against `import.meta.url`).
- Wasm handshake (`engine-bootstrap.ts`): the first instance on the page `model.send({type:'wasm'})`; the kernel answers with a custom message `{type:'wasm'}` whose first binary buffer is the artifact (`model.on('msg:custom', (msg, buffers) => ...)`, buffers arrive as `DataView`s from ipywidgets), or `{type:'wasm', error}` when it cannot. A reply without a buffer is an error, not a hang; no reply within 60 s is an error; a failed shared promise is dropped so a later widget retries.

## Model contract

Trait names live in `widget-core.ts` `TRAITS`. Kernel-owned traits: `project_json` (the authoritative whole-project engine-native JSON snapshot; THE WIDGET NEVER SETS IT), `revision` (integer, kernel-only), `height`, `theme` (`auto|light|dark`), `read_only`, `max_snapshot_bytes` (the largest snapshot the widget may send, measured as it rides in the message -- the snapshot text JSON-string-escaped, in UTF-8 bytes; default `MAX_SNAPSHOT_BYTES` = 8 MiB, the same constant in pysimlin's `_widget_core.py`). Widget-written trait: `selection`. Custom messages, widget -> kernel: `{type:'wasm'}`, `{type:'snapshot', base:int, json:string}`, `{type:'oversize', bytes:int}` (sent INSTEAD of a snapshot whose wire size exceeds `max_snapshot_bytes`; `bytes` is that wire size; owed no reply). Kernel -> widget: `{type:'wasm'}` + binary buffer / `{type:'wasm', error}`, `{type:'saved', revision:int}`, `{type:'rejected', revision:int}`, `{type:'notice', text, level?:'info'|'warn'}`.

Why snapshots ride in a custom message and not a trait: ipywidgets allows ONE in-flight trait sync per model and assign-MERGES the `patch` messages it buffers behind it, so consecutive trait writes reach the kernel collapsed (a burst {S1,base n},{S2,base n+1},{S3,base n+2} arrives as {S1,base n},{S3,base n+2}: S2 lost, S3 rejected). Custom messages are queued in order and never merged, and an explicit reply per snapshot removes any need to infer acceptance from trait echoes.

### Kernel obligations (MUST)

1. **Seed**: set `project_json` and `revision` before the widget is displayed.
2. **Exactly one reply per `snapshot`.** Wrap the whole handler so that ANY exception (parse failure, write error, a bug) ends in `{type:'rejected', revision}` (+ a `notice` carrying the error) -- the widget's save promise resolves only on the reply, and `ProjectController` runs one save at a time, so a snapshot that never gets its reply hangs every later save of that view until it is remounted. `revision` in a reply is a JSON integer.
3. **Accept** a `snapshot` whose `base` equals the current revision: apply and write the file, then inside ONE `hold_sync()` assign `project_json = <the exact bytes received>` and `revision += 1` (plain assignments -- the frontend never set this trait, so there is no property lock and no `send_state` is needed), then send `{type:'saved', revision}`. The state message SHOULD leave before `saved` (exit the `hold_sync()` block first): in JupyterLab (ipywidgets 8.1 / jupyterlab 4.3) a state update is applied on the awaited promise chain before a following custom message dispatches, so with that order the widget sees push then `saved`; the widget tolerates the reverse (it adopts the accepted state from `saved` itself), so this is a SHOULD, not a MUST, but keeping the order avoids relying on that tolerance in hosts (VS Code, Colab bridges) whose dispatch order is unverified.
4. **Reject** a `snapshot` whose `base` is stale, or that could not be applied at all (it does not parse; the kernel raised before applying): never write the file from it; do NOT touch the traits (they already hold the authoritative state, and only the kernel writes them); send `{type:'rejected', revision}`, optionally with a `notice`.
5. **Applied but unwritten** (the snapshot was applied in memory but the file write failed -- disk full, permissions): this is an ACCEPT, not a reject. The kernel's revision has advanced by one and the project is dirty, so it pushes the exact bytes received at `revision + 1` and sends `{type:'saved', revision}` exactly as in obligation 3, plus a `{type:'notice', level:'warn'}` naming the error and the fix (`model.save()`). Replying `rejected` here would leave the widget's acknowledged base one behind the kernel's and every later save would be rejected as stale.
6. **Own changes** (Python `edit()`, a disk reload): assign both traits in one `hold_sync()`; add a `{type:'notice', text:'Updated on disk'}` for disk.
7. **Notices are custom messages, not a trait**: a notice is an event (a second identical "Updated on disk" must show again), which a trait cannot express.
8. **Wasm**: answer `{type:'wasm'}` with a custom message `{type:'wasm'}` whose first binary buffer is `libsimlin-browser.wasm`, or `{type:'wasm', error: string}`.
9. Only the kernel ever writes `project_json` and `revision`.
10. **Size**: seed `max_snapshot_bytes` (default 8 MiB) below the notebook server's browser->kernel websocket limit (tornado `websocket_max_message_size`, 10 MiB by default, for any host that reaches the kernel through a Jupyter server) with room for the envelope and message header, which are a few hundred bytes -- the cap is measured on the snapshot AS IT RIDES IN THE MESSAGE (JSON-string-escaped UTF-8; pysimlin `snapshot_wire_size`, JS `snapshotWireSize`), so no other content-dependent inflation remains. Answer an `{type:'oversize', bytes}` report with a warn `notice` and NOTHING else -- no `saved`/`rejected`: the widget resolved that save itself and has nothing in flight. pysimlin also emits a `RuntimeWarning`, which goes to the kernel's stderr (a comm handler runs outside any cell, so JupyterLab shows it in the Log Console, not a cell output -- the toast is what the user sees). Warn the Python user (once per widget, attributed to the user's cell) when seeding or pushing a `project_json` above the cap, since every editor edit of that model will be refused.

### Widget guarantees

- **At most ONE snapshot in flight per view.** `onSave` sends `{type:'snapshot', base, json}` and returns a promise that resolves ONLY when the matching reply arrives: `saved` -> the new revision (the controller adopts it as acknowledged) and the widget adopts (revision, sent bytes) as the Editor's seed right then; `rejected` -> `undefined` (the controller keeps its version). A reply-typed message with a missing/non-integer revision is treated as a reject, not ignored (it still consumes the one reply the snapshot is owed; ignoring it would hang the save queue). `ProjectController` already serialises saves (one in flight, one queued flush that re-serialises the LATEST state and re-reads the acknowledged version), so with a busy kernel (a long-running cell) the Editor keeps working locally and one flush of the latest state goes out when the answer arrives. There is deliberately no timeout while in flight -- a long cell legitimately delays the reply and a timeout would misfire -- but unmount/abort resolves it `undefined` so nothing dangles, a reply arriving with nothing in flight is ignored, and an `onSave` after unmount (a queued flush racing the dispose) is refused with `undefined` rather than sent. A second `onSave` while one is in flight (the controller never does this) is likewise refused.
- Kernel trait pushes (`change:project_json` / `change:revision`; the two traits travel in one `hold_sync` but surface as up to two events, so the handler classifies the FINAL pair idempotently, `classifyPush`): if a snapshot is in flight and the pair equals (in-flight json, base + 1) it is the accept's state -- adopt it as the seed, keep the live Editor and its undo history; if it equals the seed pair (including the pair a `saved` reply already adopted), nothing; otherwise remount `<Editor key=revision#generation>` on it (kernel edit, disk change -- including one that raced an in-flight snapshot). Push-then-`saved` and `saved`-then-push therefore both end with one live Editor and no remount. A remount while a snapshot is in flight resolves that save `undefined` at once (its Editor is gone; nothing may wait on a reply for a mount that no longer exists) and FREES the slot, so the new Editor's first save goes out with the new base instead of being refused as "one already in flight" (which left that edit unsaved until a later edit); the reply the kernel still owes for the freed snapshot is counted as stale (`staleRepliesOwed`) and, since replies arrive in order, the next `saved`/`rejected` is consumed and ignored -- it neither remounts (the push already did) nor adopts its pair as the seed (a late `saved` for the old snapshot would step the seed back behind the state just remounted on).
- Reject handling is defense in depth under either order: when the kernel's state moved, its trait push already remounted the Editor and the following `rejected` re-checks the (revision, json) pair and finds it already seeded (no second remount); when it did not move (a reject at an unchanged revision: the kernel raised before applying anything), the pair equals the seed and nothing remounts -- the Editor keeps its local edits at the same version and the next save goes out against the same base. Remounts are idempotent on the pair (`remountFrom`); `generation` makes the key change even when the revision number does not.
- **Never sends a snapshot above `max_snapshot_bytes`** (`checkSnapshotSize` on the wire size -- `JSON.stringify` then UTF-8 bytes via `TextEncoder`, mirroring pysimlin's `snapshot_wire_size` -- read live from the trait so a raised cap is honoured without a remount): the server would drop it (tornado closes the socket with 1009 on an oversize frame; JupyterLab reconnects the kernel silently) and the save would never resolve. Instead `onSave` sends `{type:'oversize', bytes}`, shows its own warn toast ("Edit not saved: the model is too large for the notebook connection (N > M limit); edit it from Python instead." with sizes from `formatSize`, KiB below 1 MiB else MiB to one decimal, round-half-to-even -- byte-identical to pysimlin's `format_size` on the fixture list pinned in both suites, so the kernel's notice and the toast collapse into one), and resolves `undefined`: the controller keeps its version and the Editor its local edit, and the next edit is refused the same way until the model shrinks or is edited from Python. Exactly at the cap is sent.
- The widget never writes `project_json`; only `selection` (set + `save_changes()` at most every 150 ms).
- Notices auto-hide after 5 s; a repeat restarts the timer. The toast sits bottom-centre at 80px, above the Editor's own snackbar viewport (`Snackbar.module.css`, bottom 8px) and above the tool dial FAB (top edge at 72px, so a wrapped two-line notice in a narrow cell still clears it), away from the search bar -- the top edge is Editor chrome ("Find in Model", the details drawer) and a toast there covers it. `theme: 'auto'` follows JupyterLab's `body[data-jp-theme-light]` (a `MutationObserver`) else `prefers-color-scheme` (a `matchMedia` listener), live, both unsubscribed on unmount.

Correctness boundary: the file is only ever written from a snapshot whose `base` equalled the kernel's revision at handling time, so a snapshot edited from stale state can never overwrite a change the widget has not seen; what a reject costs is the local edits since the last accept, which the remount discards (the notice tells the user).

### Known limitation: two views of one model

anywidget runs `render` once per VIEW; two views of the same model (`display(w)` twice, or a JupyterLab "create new view for output") each mount their own Editor and their own in-flight slot against ONE model. Their saves interleave on the same comm: view A's accept is a foreign push for view B (it remounts, losing B's undo history and unsaved local edits), and a reply's `msg:custom` reaches both views (the one with nothing in flight ignores it). Correctness holds -- every write is a kernel-accepted snapshot -- but two live editors of one model on one page is not a supported editing arrangement; display two `ModelWidget` instances (two cells) instead, which each carry their own model.

## How the assets reach the wheel

`pnpm build` here is `rsbuild build && pnpm run stage`; `stage` runs `src/pysimlin/scripts/stage_widget_assets.py --no-build`, the ONE owner of copying `dist/widget.js` and `src/engine/core/libsimlin-browser.wasm` into `src/pysimlin/simlin/_widget/` (git-ignored package data) and writing `ASSETS.json` beside them (source commit, wasm-opt mode from build.sh's `.mode` stamp, per-file size and sha256; deterministic, so an unchanged tree restages nothing). Do not add a second copy step -- pysimlin's `make assets`, `src/pysimlin/scripts/build_wheels.py`, and the release workflow all call that script (which by default runs `pnpm --filter "@simlin/notebook-widget..." run build` first). pysimlin's `setup.py` refuses to build a wheel/sdist when the assets are missing, empty or do not match the manifest, and `release.yml` builds them once (ubuntu, `--require-opt`), ships that one set in every platform wheel, and checks each wheel with `src/pysimlin/scripts/check_wheel_assets.py`. The pre-commit hook builds with `DISABLE_WASM_OPT=1`, so a locally staged wasm is usually `raw`; that is fine for development and refused for release.

## Size

Measured 2026-08-18 (rsbuild 2.1.5 production build, `gzip -9`; wasm-opt version 125 with build.sh's `-O3` flags), in KiB (bytes / 1024). Regenerate with `ls -l` / `gzip -9 -c ... | wc -c` on `dist/widget.js`, `src/engine/core/libsimlin-browser.wasm.raw` and a `wasm-opt` run of it; the KaTeX font share is the total length of the woff2 `data:` URIs in the bundle.

| Artifact                                                                                                                     | raw       | gzip      |
| ---------------------------------------------------------------------------------------------------------------------------- | --------- | --------- |
| `dist/widget.js`                                                                                                             | 1,539 KiB | 605 KiB   |
| of which inlined KaTeX woff2 faces (20 files, base64 data URIs)                                                              | ~339 KiB  | ~262 KiB  |
| `libsimlin-browser.wasm`, wasm-opt'd (mode stamp `opt`)                                                                      | 5,262 KiB | 1,758 KiB |
| `libsimlin-browser.wasm`, unoptimized (`DISABLE_WASM_OPT=1`, what the pre-commit hook leaves in the engine's core directory) | 6,532 KiB | 1,568 KiB |

The wasm-opt'd blob is 20% smaller raw but 12% LARGER gzipped: cargo already builds wasm32 at `opt-level = "z"` (`.cargo/config.toml`), whose output is repetitive and compresses well, while `wasm-opt -O3` trades that regularity for speed (inlining, unrolling) -- fewer bytes, higher entropy. Which number matters depends on the channel: the widget comm carries the raw bytes (websocket frames are not compressed by default), so the wasm-opt'd blob is the one to ship; the wheel is a zip, where the difference is a wash. Roboto is deliberately NOT bundled: the Editor's stylesheets fall back through `Roboto, Helvetica, Arial, sans-serif`, hosts that have Roboto (JupyterLab does not by default) use it, and shipping the four woff2 subsets simlin-serve self-hosts would add ~60 KB for a font the notebook chrome does not use.
