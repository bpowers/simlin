# simlin-engine

The simulation engine: it parses, lowers, type-checks, unit-checks, compiles, and simulates system dynamics models. The root `CLAUDE.md` holds the development rules; this file maps where functionality lives (paths are relative to this crate's `src/`) and states the standing invariants that code in this crate must keep. It is a map, not a history: `git log` and `git blame` are the changelog.

## Compilation pipeline

Equation text becomes a running simulation in these stages. Each stage names the module that owns it.

1. **Parse** (`lexer/`, `parser/`, `ast/expr0.rs`). `Expr0::new` produces the parsed AST. `lexer::KEYWORDS` is the reserved-word table; `ast::needs_quoting` reads it when printing an identifier back to equation text, so a name that is a keyword round-trips quoted.
2. **Module-function expansion** (`builtins_visitor.rs`, `capture.rs`, `module_functions.rs`). `instantiate_implicit_modules` rewrites stdlib calls (`SMTH1`, `DELAY3`, ...) and project macros into module instances and routes `PREVIOUS`/`INIT` to the `LoadPrev`/`LoadInitial` opcodes.
   - Everything it synthesizes is parsed data on one ordered `capture::ImplicitVar` list: a `Capture` (a `PREVIOUS`/`INIT` argument that is not a static slot) or a `HoistedArg` (a call argument that is not a bare identifier) carries the argument's `Expr0` subtree, and an `ImplicitModule` carries its target model and input-port wiring. `ImplicitVar::parsed_variable` is the one conversion back to a parse-stage variable, so no helper is printed and parsed back (GH #913's class). A helper's equation errors carry spans into the PARENT's equation and are reported on the parent. `substitute_dimension_refs` rewrites a hoisted argument before the hoist, because a helper is a scalar with no axis of its own: an active dimension name becomes its element, a foreign one resolves through `resolve_mapped_read`, the rule the compiler applies to the same spelling.
   - `capture::synthetic_ident` is the one derivation of a helper's `$⁚{parent}⁚{n}⁚...` name (`n` shared by an instance and its arguments), an external key the runlist, the layout and the results map sort by; `capture::insert_implicit_var` is the one rule for two helpers claiming one name. `snapshot_arg::SnapshotArg::access` is the single statement of what a `PREVIOUS`/`INIT` argument addresses (`SnapshotAccess`: slot, view, or capture), classified by this parse and by codegen (`static_slot`, `Compiler::snapshot_static_view`) alike, so the dependency graph and the bytecode cannot disagree (GH #568's class). Whether an identifier subscript of such an argument pins ONE declared element is the one model-level question the parse answers itself (a capture cannot be un-minted at lowering), through `builtins_visitor::SnapshotIndexFacts`: the source parse asks the referenced variable's declared axis -- an element of that axis wins over a same-named variable, XMILE 1.0 footnote 9 and the compiler's own `dimensions::resolve_axis_index_name` -- and whether the project declares a qualified `dimension·element`; the generated LTM parse, whose target may be a synthetic variable with no declared axis, asks whether any dimension declares the element and no variable of the model shadows it. A capture's kind is its phase demand (`capture::CaptureKind`): `PREVIOUS` storage is refreshed in flows only, `INIT` storage is populated in initials only unless a per-step definition reads its current value, and the dt and active-initial parses minting one storage for both consumers share it with the union of the two.
   - `MacroRegistry::resolve_call` is the one routing decision for a call (`Expand`, `Passthrough`, `RenamedBuiltinSelfCall`, `Unresolved`), read by the visitor and by macro-recursion analysis. A macro shadows a like-named builtin: the engine's rule, unverified against Vensim's documentation, and the opposite of XMILE 1.0 3.2.2.5, which reserves builtin names (they cannot be used as macros or functions) and says a conflict SHOULD be flagged (see `resolve_call`). A genuine passthrough lowers as its builtin under the macro's arity, and the enclosing macro's own renamed builtin lowers as the builtin (GH #554).
3. **AST lowering** (`ast/`). `Expr0` -> `Expr1` (typed `BuiltinFn`) -> `Expr2` (array bounds resolved against the dimension context). `variable.rs` drives this per variable: `parse_var(&ParseContext, impl Into<VariableSource>, ..)` is the one parse entry point, and `classify_dependencies` the one dependency walk. A `VariableSource<'_>` is a BORROWED view of the fields a parse reads (ident, equation, gf, units, kind, flows, module refs and target model name, and the three compat-derived fields `non_negative`, `can_be_module_input` and `active_initial`), built either straight over the salsa inputs (`db::variable_source`) or from a `datamodel::Variable`; a `ParseContext` carries the project-global contexts (dimensions, units, the macro registry, the enclosing macro body) plus the `SnapshotIndexFacts` a `PREVIOUS`/`INIT` subscript index is decided with. A source parse reads the owning model only through per-name projections (`variable_owner_model`, `model_variable_by_name`, `variable_dimensions`, `project_has_qualified_element`), never its variable set, so `db::parse_source_variable` is keyed on `(variable, project)`; what a `PREVIOUS`/`INIT` argument's NAME denotes -- a bare module instance (refused: it has no storage of its own), a bound input port (its own slot), a module output port or a plain variable (a fixed slot) -- is resolved at lowering by `compiler::context::Context::snapshot_storage` from the dependency's shape, and the parse captures only the one module-backed name it can know without the model, an instance synthesized earlier in the same walk. `model.rs` holds the whole-model stages (`ModelStage0`/`ModelStage1`) that unit checking consumes. `builtins.rs` holds the typed `BuiltinFn` and `BuiltinFn::signature()`, the one statement of every per-builtin fact -- name and aliases, source arity, which argument positions are array operands and whether the enclosing apply-to-all element pins their axes (`ArgKind`), the result's shape (`ResultKind`), and the invariance class (`Invariance`); `args()`/`args_mut()` and the `map` family are the uniform argument view. A match over `BuiltinFn` anywhere else encodes per-variant semantics (which opcode, which unit rule, which argument shapes the result) and says so in a comment.
4. **Per-variable fragment compilation** (`compiler/fragment.rs`, `db/var_fragment.rs`, `db/fragment_compile.rs`, `db/ltm/compile.rs`, `compiler/`). `compiler::fragment::lower_fragment(&FragmentInput, is_initial)` is the one per-variable lowering entry point. A `FragmentInput` is the variable in its `Expr2` form plus a `DepShape` -- dimensions, and whether the name is a plain variable or a module instance -- for every name it can reference, carrying no offset of the model being compiled; explicit variables (`explicit_fragment_input`), implicit helpers (`implicit_fragment_input`), LTM synthetic variables (`ltm_fragment_input`) and LTM implicit helpers (`ltm_implicit_fragment_input`) are its four constructors. The two in-model constructors resolve dependency shapes through the per-variable firewall queries (`model_variable_by_name`, `model_implicit_var_by_name`, `variable_dimensions`, `model_shape` for a module's sub-model); the two LTM constructors read the whole `model.variables(db)`, `model_implicit_var_info` and `model_ltm_implicit_var_info` maps, which costs them nothing extra because the LTM surface they lower is itself derived from a whole-model query (`model_ltm_variables`). `lower_fragment` lowers `Expr2` -> `Expr3` (`ast/expr3.rs`, a structural rewrite that resolves wildcards and gives every bare array reference its subscripts) -> `compiler::Expr`: `compiler/mod.rs` expands apply-to-all and arrayed equations per element; `compiler/context.rs` resolves references and subscripts against the dependency shapes; `compiler/subscript.rs` normalizes static subscripts into views; `compiler/fold.rs` folds constants; and `compiler/array_operand.rs`, the fragment's ONE materialization pass, moves every array value codegen cannot express in place -- the array-producing builtins, the per-element arrayed-GF applies, and the computed array operands -- into temps, so codegen only ever sees views. It is the only caller of `ast::TempAllocator::alloc`; the allocator is owned by the `compiler::Context` the fragment lowers under and shared by every context derived from it. `compiler/codegen.rs`, under the same input's `FragmentInput::emit_ctx`, emits `SymbolicOpcode`s whose variable operands are `VarRef { name, element_offset }`.
5. **Assembly** (`db/layout.rs`, `db/assemble.rs`, `compiler/symbolic.rs`). `compute_layout` assigns slots per model, and `flattened_offsets` reads that layout back out as the results-offset map (`CompiledSimulation::offsets`: `module·var` through each module instance, `var[e1,e2]` per element of an arrayed explicit variable, no key for a lookup-only table or for an INIT-only capture, whose slot nothing writes per step), so slot order is stated once. `assemble_module` collects every fragment source -- explicit, implicit, LTM synthetic, LTM implicit -- into one map, emits each of the module's three programs in runlist order (a resolved recurrence SCC's members replaced by the SCC's combined fragment at the first member, the run-invariant flows hoisted ahead of the dynamic ones, the LTM tail after the runlist), and drives ONE `FragmentMerger` through them: every initial as a standalone program, then the flows and the stocks as one concatenation each. A combined fragment interleaves the members' per-element segments in the element graph's order, and `segment_member_by_element` is the one statement of where a member's code splits -- the graph and the combiner both read it: a member's PROLOGUE (the leading temp blocks two or more elements read, or that a later prologue block reads) is emitted once, immediately before the first of its readers in that order, and the graph wires the prologue's reads into exactly those readers, so a recurrence whose shared temp reads a non-reader element runs that element first rather than being refused. The merger renumbers per-fragment literal/GF/module/view/temp/dim-list ids into the module's single table set, de-duplicates graphical functions by content, and gives each program its own literal pool; then `resolve_module` turns `VarRef`s into offsets. `assemble_simulation` enumerates module instances and builds the `CompiledSimulation`.
6. **Execution** (`vm.rs`, `bytecode.rs`, `wasmgen/`). The stack VM runs initials, then per step flows and stocks, under Euler, RK2, or RK4. `wasmgen` lowers the same `CompiledSimulation` to one self-contained wasm module that mirrors the VM opcode for opcode.

`db::compile_project_incremental` is the single production entry point for ordinary models. `queue_compile::compile_sim` is the dispatch every VM-backed caller goes through: a model with a conveyor or queue marker takes the special-stock path (below), anything else goes to `compile_project_incremental`. `build_sim` is `compile_sim` plus `Vm::new`.

## Salsa layer (`db.rs`, `db/`)

`SimlinDb` owns the salsa storage, the sync state of the last synced datamodel, the expanded (conveyor/queue) twin's sync state, and the one-shot stdlib model inputs. The inputs (`db/input.rs`) are `SourceProject`/`SourceModel`/`SourceVariable`, storing datamodel fields directly so invalidation is per field; `db::variable_source` is the parser's borrowed view of them, so a parse costs no re-assembled `datamodel::Variable`. `db/sync.rs` maps a `datamodel::Project` onto those inputs through one `SourceVariableFields::from_datamodel` extraction that both the fresh-sync constructor and the incremental updater read, reusing handles across syncs and setting only fields whose value actually changed. Everything else is tracked queries:

- `db/query.rs` -- per-variable parse, direct dependencies, dimension reads, module maps, the module-reference graph, and the firewall queries (`model_variable_by_name`, `model_implicit_var_by_name`, `variable_owner_model` over the `owner_model` name the sync sets on every `SourceVariable`, `project_has_qualified_element`) that let a fragment or a parse depend on one variable, one owner or one element instead of the whole map.
- `db/dep_graph.rs` -- the dependency graph and cycle gate: runlists, the dt/init cycle relation (`walk_successors`), and recurrence-SCC resolution (an SCC whose element-level graph is acyclic is compiled as one interleaved fragment instead of being rejected). A capture's runlists are its kind: an INIT-only capture leaves flows unless a per-step definition's current-value closure reads it, a PREVIOUS capture is never seeded into initials, and every helper's `INIT` referents are initialization roots. A model instantiated as a module (an explicit module's target, a stdlib template, a macro) evaluates every value-bearing variable in its initials, because a parent's initials may read any of its ports and XMILE's model is one flat graph (GH #1028).
- `db/stages.rs` -- `ModelStage0`/`ModelStage1` as cached queries over a model's module-reachability scope; consumed by unit checking.
- `db/diagnostic.rs` -- the `CompilationDiagnostic` accumulator, the typed `Diagnostic`, and the drain functions `collect_model_diagnostics`/`collect_all_diagnostics`.
- `db/units.rs`, `db/macro_registry.rs`, `db/invariance.rs` -- the unit-check pass, the macro registry query, and run-invariance classification of flow variables.
- `db/analysis.rs`, `db/ltm_ir.rs`, `db/ltm/` -- LTM (below).

### Rules the salsa layer depends on

- A cached value must be a pure function of its inputs. Never let `HashMap` iteration order reach a cached value or the compiled artifact: sort first (`temp_sizes_by_id`, sorted table idents in `Compiler::new`, sorted runlist seeds).
- AST constants hold `ast::Literal`, compared by bit pattern, so a `NaN` literal (every stdlib template declares `initial_value = NAN`) does not defeat backdating. Any new float-bearing field reachable from the AST must use `Literal`; the `Eq` derives make a bare `f64` a compile error.
- A per-variable query needs a per-variable key. Reading a whole-model value (`model.variables(db)`, `ModelDepGraphResult`) from a per-variable query makes every variable recompile on any edit; go through a projection query that returns only what is needed (`var_runlist_membership`, `model_variable_by_name`). Whether a projection actually bought anything is measured, never assumed: `db::exec_probe::ProbedDb` counts every tracked query's body entries over an edit from salsa's own `WillExecute` events, because salsa backdates an equal value and keeps the memo address, so neither the value nor the pointer says whether the body re-ran.
- A source parse is a function of `(variable, project)`. `parse_source_variable` reads the variable's fields, the dimensions it names, the project-global contexts and, for a `PREVIOUS`/`INIT` subscript index, one referenced variable through its owning model's per-name projections -- never the owning model's variable set or a module instance's wiring: a model-derived parse KEY cannot backdate at all, so it re-executes every parse in the model on any edit that moves it (`db::fragment_char_tests::implicit_helper_add_is_tight_for_plain_and_module_helpers` and `module_helper_add_reparses_only_the_added_variable` are the gate). A decision that needs the owning model belongs in lowering, where `FragmentInput.deps` knows every name's kind; failing that, on the `SourceVariable` input as a field set at sync (`owner_model`, read back through `variable_owner_model`) -- never a per-variable scan of a model map.
- A module cycle drives recursive tracked queries into salsa's dependency-graph panic, which is a process abort under `panic = abort`. Every compile, diagnostic, and analysis entry point consults `project_module_graph(..).cycle_error_from(..)` before recursing.
- Salsa has no input reclamation. Inputs are reused across syncs, never recreated, and the expanded-project slot is allocated at most once per db.
- Diagnostics derived once per project (macro-registry build error, unit-definition errors, module cycles) are emitted from their memoized value, not accumulated inside the deriving query: an accumulator reports once per reachable model and is lost after an unrelated revision bump prunes the subtree.

## Standing invariants of the compiler

- **Addresses are assigned once, at assembly.** Lowering and codegen name variables (`VarRef`); nothing before `resolve_module` knows a slot, and a `FragmentInput` carries no offset of the model being compiled. A cross-module reference `m·x` lowers to `VarRef { name: m, element_offset: x's slot inside the instance }` because only the sub-model's layout is fixed at that point: the module dependency's `DepKind::Module` carries that layout as a `ModelShape` (`db::model_shape`, recursively for nested instances), and `Context::resolve` is the one reader of it. `VarSizes` (keyed by `VarRef`, projected from the dependency shapes by `fragment::reference_extents`) is the only size information codegen reads.
- **`resolve_bytecode` is the only producer of concrete bytecode**, and it proves the VM's fixed-stack safety: a program deeper than `STACK_CAPACITY` is a compile error. The peephole fusions (`SymbolicByteCodeBuilder`) run before resolution and are address-independent, so resolution is a 1:1 opcode mapping; the run-invariant flow prefix length and SCC segmentation count on that. `Compiler` (through its `SymbolicByteCodeBuilder`, which builds the fused superinstructions) is the only producer of a `SymbolicOpcode`, so every variant of that enum (and of its `Opcode` twin) is one codegen emits; the dead-code lint, denied under clippy, enforces it -- never `allow` it on a variant.
- **Both opcode enums are tables.** `symbolic_opcode_table!` (`compiler/symbolic.rs`) and `opcode_table!` (`bytecode.rs`) hold one row per opcode: its operands and, on the symbolic side, its concrete twin; on the concrete side, its stack effect. An operand's type is its kind -- `SymVarRef`, `LiteralId`, `ModuleId`, `ViewId`, `DimListId`, `TempId`, `GraphicalFunctionId` with its `TableCount`, `PcOffset`, anything else data -- and `resolve_opcode`, `renumber_opcode`, `gf_run`, `var_ref`, `jump_offset`, `stack_effect` and `name` derive from the rows, so adding an opcode is one row plus its `vm.rs` and `wasmgen` arms. The every-row tests (`symbolic_table_tests`, `bytecode::tests`) and the merge proptest's blanking oracle derive from the same rows; `vm.rs`, `wasmgen`, the fusion patterns and the `db/` scans name variants by what they mean and stay hand-written.
- **A stock update is always the fused `BinOpAssignNext`.** There is no un-fused `AssignNext`; `Var::new` rejects any update whose lowered form does not end in an `Op2`.
- **An array operand is a view over storage.** Codegen accepts `StaticSubscript`, `TempArray`, `Var`, `Subscript`, and an array-valued `PREVIOUS`/`INIT` (a view over a snapshot region). `array_operand.rs` materializes everything else into a temp; a shape it cannot size declines and codegen reports the error. Temps are per-fragment, 0-based, and recycled across sequential fragments; an interleaved SCC fragment sums them instead (`TempStrategy`). Within a fragment every id comes from one `TempAllocator`, issued by that one pass and final when issued: a body two or more elements read takes one id for the equation and is written ahead of the element code, and a body one element reads takes an id the elements reissue (`element_scopes`), so an equation costs one id per simultaneously-live temp rather than one per element. The bytecode `TempId` is a `u8`: every opcode that writes a temp narrows the id with a plain `as TempId`, unguarded, while a static VIEW over a temp carries the `u32` and is rejected at resolution above 255 (`symbolic::resolve_static_view`). GH #583 is that namespace; no shape in the corpus reaches it, and the write side stays deliberately unguarded.
- **No silent wrong numbers.** When a construct cannot be compiled correctly, refuse with `NotSimulatable` (VM) or `WasmGenError::Unsupported` (wasm) rather than approximate. The wasm backend has no VM fallback.
- **The VM is the correctness oracle for wasmgen.** Every emitted module is run under a pure-Rust wasm interpreter in tests and compared with `Vm::run_to_end`; the corpus in `tests/integration/simulate.rs` does this for every VM-simulated model.
- **Constant folding is platform-deterministic.** `compiler/fold.rs` folds only IEEE-exact operations with the VM's own `eval_op2`; `^` and transcendentals stay runtime so the VM and the wasm blob agree bit for bit.
- **Graphical functions:** a per-element arrayed GF's tables are laid out at the element's row-major declared-dimension index (`variable::reorder_arrayed_element_tables`), because `Lookup`/`LookupArray` index `graphical_functions[base_gf + element_offset]`. A standalone lookup-only variable (empty or `"0+0"` equation plus a table) is a static table: excluded from every runlist, no series, and a bare reference to it is `LookupReferencedWithoutArgument`. `WITH LOOKUP` is value-bearing and lowers to `LOOKUP(self, input)`.
- **Floats.** `float::NA` is Vensim's `:NA:`, the finite value `-2^109`, so `IF x = :NA:` works and `:NA:` arithmetic stays finite. A NaN is an absorbing failure signal, produced for out-of-range vector reads and empty reducers other than `SUM`. The module docs of `float.rs` are the landing page for this.

## Arrays

Subscripts are 1-based in source and 0-based internally. Dimensions are `dimensions::Dimension` (`Indexed` or `Named`); `DimensionsContext` holds subdimension relations, `maps_to` chains, and element-level mappings, and is the single statement of how a mapped read resolves (`resolve_mapped_read`: name on the source axis, then the declared mapping, then a mapped parent). `resolve_axis_index_name` is the single element-vs-dimension-name precedence for a bare identifier inside brackets (element first); the compiler and the LTM describers both read it.

`dimensions::match_axes` is the single statement of how two axis lists pair: exact name, then declared mapping, then subdimension, then size, staged flat (each rule runs across every source axis before the next runs for any) and one-to-one, so a stronger match wins a target axis whatever the declaration order and no two source axes read the same one. Every compile-time caller asks it -- the implicit subscripts a bare arrayed reference gets, the subscripts a bare reference under a reducer gets, the reordering that lines two operands up, `Expr2`'s bounds unification, the per-element resolution inside an apply-to-all body, and the view join -- and a caller supplies an `AxisRelations` projection saying which declared relations it can act on. `DimensionsContext` answers the mappings; `DirectMappingsOnly` withholds the mapping-onto-a-parent rung from a caller that resolves the paired element by ORDINAL; `SubdimensionRelations` adds the subdimension rung for the one caller that never resolves an element through the answer; `NoAxisRelations` is what a caller comparing two `ArrayView`s can supply. `match_dimensions_two_pass` stays separate: it is the RUNTIME broadcast matcher, pairs `dim_id`s where no `DimensionsContext` exists, and states a deliberately weaker rule (id, then size for indexed dimensions).

In lowering, `ArrayView` (`ast/array_view.rs`) is the compile-time shape (dims, strides, offset, sparse mappings, dimension names). Apply-to-all equations are unrolled per element at lowering; a reference inside the body resolves each axis against the active element, broadcasting a lower-dimensional source by dimension name. A subscript naming a dimension is an `IndexOp::ActiveDimRef` all the way to `compiler::subscript`, which allocates the active positions ONE TO ONE across a reference's subscripts (so `square[D,D]` under a `[D,D]` target reads the cell, not the diagonal) and resolves the element through the one mapped read; `compiler::project_var_index_to_temp` pairs a temp's axes to the variable's by the same two rules. Array-producing builtins (`VECTOR ELM MAP`, `VECTOR SORT ORDER`, `RANK`, `ALLOCATE AVAILABLE`, `ALLOCATE BY PRIORITY`) and per-element arrayed-GF applies are materialized into `AssignTemp` and read back per element; whether that happens once per equation or once per element is decided by structural identity of the lowered body (`compiler/array_operand.rs`). `VECTOR ELM MAP` and `VECTOR SORT ORDER` follow genuine Vensim semantics, ground-truthed against Vensim output in `test/` (`vm_vector_elm_map.rs`, `vm_vector_sort_order.rs`): ELM MAP reads the source variable's full row-major storage from the base the reference establishes with no wraparound and NaN out of range; SORT ORDER ranks within each innermost row, 0-based.

At runtime a `StaticArrayView` is resolved once per opcode (`PushStaticView`) and `ViewStorage` says which region it reads (`Curr`, `Temp`, `Prev`, `Initial`); dynamic subscripts go through `PushVarViewDirect` plus `ViewSubscriptDynamic`/`ViewRangeDynamic`. `BeginIter` loops evaluate elementwise bodies into temps, matching source views to the iteration by dimension id (`dimensions::match_dimensions_two_pass`: name first, then size for indexed dimensions). A view's axis therefore has to be named for the dimension it actually ranges over, and both statements of that name must agree: a star range `arr[*:Sub]` produces a `Sub`-named axis in `compiler::subscript::build_view_from_ops` and in `ast::Expr2`'s bounds, so the temp the reference materializes into matches its source view rather than reading NaN for every element. A dimension-reordering transform on an `ArrayView` goes through one helper (`permute_axes`) because `dims`, `strides`, `dim_names`, and every `SparseInfo::dim_index` -- an index INTO `dims` -- move together; moving three of the four addresses the wrong axis (GH #1027).

## Loops That Matter (LTM)

LTM instruments a model with synthetic variables (link scores, loop scores, aggregate nodes, module pathway and composite scores) that are compiled through the same fragment pipeline as user variables and read back after simulation. Exhaustive mode enumerates every elementary circuit; discovery mode scores every causal edge and finds loops from the recorded series after the run. `db::model_ltm_mode` is the one gate that decides which, read by both the scored and the detected-loop surfaces.

- `db/ltm_ir.rs` -- the front door: walks each variable's `Expr2` once and classifies every reference site by access shape (`Bare`, `FixedIndex`, `PerElement`, `Wildcard`, `DynamicIndex`) and routing (direct or through an aggregate node). Every other LTM consumer reads this IR rather than re-walking the AST.
- `ltm_agg.rs` -- aggregate-node enumeration: each statically describable reducer subexpression becomes a `$⁚ltm⁚agg⁚{n}` node with a per-source `read_slice` of `AxisRead`s.
- `db/analysis.rs` -- causal edges (variable and element level; an INIT-only capture is no causal node, so no edge leads into or out of it), tiered circuit enumeration, cycle partitions, detected loops.
- `db/ltm/` -- generation and compilation: `mod.rs` (`model_ltm_variables`), `equation.rs` (`LtmEquation`, the typed per-arm `Expr0` a synthetic variable carries), `link_scores.rs`, `loops.rs` (including cross-aggregate loop recovery), `pinned.rs` (`LOOPSCORE` pins), `compile.rs` (fragment compilation and the compile-failure diagnostic pass), `parse.rs`.
- `ltm_augment.rs` and its `ltm_augment_*.rs` children -- the ceteris-paribus equation generators: wrap every non-source reference of the target's equation in `PREVIOUS`, pin arrayed dependencies to the element the target reads, and freeze subscript indices. Production never parses a target equation; it lowers the target's `Expr2` back to `Expr0` (`patch::expr2_to_expr0`) and consults the IR by structural path.
- `ltm/` -- the vocabulary (`Link`, `Loop`, polarity), `CausalGraph`, Johnson's circuit enumerator and Tarjan SCC (`indexed.rs`), static polarity analysis (`polarity.rs`).
- `ltm_finding.rs` with `ltm_finding_enum.rs` and `ltm_finding_fallback.rs` -- post-simulation discovery: exact union-graph enumeration, a shortest-path sampling fallback under a wall-clock and memory budget, retention against the full loop universe, and the coverage-aware cap.
- `ltm_post.rs`, `ltm_dominance.rs` -- relative loop and link scores (normalized within a cycle partition, in emission order so the IEEE sum is stable) and dominant-period selection.

Rules: LTM is an analysis overlay, so an LTM-only failure must never masquerade as a project compile error (`LtmEnabledGuard` flips the flag only for the diagnostic harvest). A link-score fragment that fails to compile is reported by `model_ltm_fragment_diagnostics` as a `Warning`, never silently stubbed to zero. Under RK2/RK4 a flow-to-stock link score is meaningless, so `assemble_simulation` rejects that combination. Conveyor and queue models do not participate in LTM. Open LTM work is organized under the `ltm` label on GitHub (epic #488).

## Special stocks: conveyors and queues

A conveyor or queue stock is not compiled directly. `conveyor_compile::expand_conveyors` and `queue_compile::expand_queues` rewrite the datamodel into ordinary stocks, hidden container auxes, and driven flows, clearing the markers; the expanded project is synced into the db's second input slot and compiled incrementally like any other; `resolve_plans` binds the names to slots; and the VM runs the native per-step passes (`conveyor.rs`, `queue.rs`) between Flows and Stocks, interleaving a queue that feeds a discrete conveyor (`CouplingTable`). `compile_project_incremental` rejects a surviving marker: an internal error in the main model, `*InSubmodelUnsupported` elsewhere. The wasm backend lowers both passes as unrolled plan-specialized code (`wasmgen/belt.rs`, `wasmgen/passes.rs`) and shares the VM's error-message constructors so the two backends cannot drift. Integration is Euler-only.

## Data model and identifiers

- `datamodel.rs` -- the canonical serializable model: `Project`, `Model` (with optional `MacroSpec`), `Variable`, `Equation` (`Scalar`, `ApplyToAll`, `Arrayed` with an EXCEPT default), `Dimension` with `mappings`, views.
- `variable.rs` -- the compiler's variable: `Variable { ident, units, eqn, errors, unit_errors, kind }` over `VarKind::{ Stock { init_ast, inflows, outflows, non_negative }, Aux { ast, init_ast, tables, non_negative, is_flow, is_table_only }, Module { model_name, inputs } }`, generic over the module-input type (`ModuleReference` before lowering, `ModuleInput` after) and the expression tier (`Expr0` before, `Expr2` after). `Aux` covers auxiliaries and flows alike -- they lower identically, one slot per element holding one equation's value, and `is_flow` only says where a stock's integration reads it. The two error `Vec`s are LIVE channels, not diagnostics-in-waiting: see `Variable::equation_errors`. `model::lower_variable` is a map over `kind`, so a transformation that only rewrites equations restates no field.
- `common.rs` -- `ErrorCode`, `Error`, `EquationError`, `Result`; the identifier types. An `EquationError` is `{start, end, code, details}`: the code names the CLASS of failure, the span points at the offending text (which `errors.rs` renders as a source snippet), and `details` carries the reason when it is not visible in the span -- the name that did not resolve, the arity a call missed, the identifier a lowering could not shape. A parse error therefore writes no `details`: the snippet is its reason, and every Rust surface renders that snippet. Nothing between a raising site and `collect_all_diagnostics` drops the reason or puts something else in its place: `From<Error> for EquationError` carries `Error::details` across, the compiler's lowering entry points hand a rejection's `details` to the `Error` they build -- never its span, which is a byte offset into a string the user never sees -- and `UnitError::DefinitionError` wraps an `EquationError` rather than keeping a second reason field beside it. `canonicalize` lowercases and normalizes a raw name; `Ident<Canonical>`, `CanonicalDimensionName`, and `CanonicalElementName` are interned, so clone is a refcount bump and equality is pointer equality. Sub-model variables are addressed as `module·var` (U+00B7).
- `patch.rs` -- `ProjectPatch`/`ModelPatch` operations (upsert, delete, rename, views, stock flows, loop names). A rename reprints every dependent equation through `print_eqn`, so the printer must produce text the lexer reads back; it refuses to rename to a name that contains `"`, which has no spelling.
- `results.rs` -- `Results` (offsets plus step-major series) and `Specs`.
- `errors.rs` -- `FormattedError`/`FormattedErrors`, the user-facing rendering shared by libsimlin and the MCP servers. The severity word comes from the diagnostic's severity, and `FormattedError::details` is the bare reason -- populated from whichever of `Error::details`, `EquationError::details` or the `UnitError` variants the diagnostic carries, and handed to the FFI as `SimlinErrorDetail::details` for consumers that render the variable themselves.

## Formats

`compat.rs` is the top-level entry: `open_xmile`, `open_vensim`, `open_vensim_with_data`, `open_systems`, `to_xmile`, `to_mdl`, `to_systems`. `xmile/` reads and writes XMILE with `simlin:` vendor extensions for element mappings, data sources, EXCEPT metadata, and multi-output macro invocations. Two contracts the XMILE writer keeps: every attribute it emits goes through `push_attribute`, and a newline inside a name is spelled as the two-character XMILE escape `\n` (the datamodel's stored form, which Stella also writes), never a raw newline -- XML attribute normalization would read one back as a space; only the free-text attributes decode the escape (`decode_free_text_attribute`). `xmile/views.rs` is the one place the view `zoom` changes unit: XMILE stores a percentage, while the datamodel, protobuf, JSON, and TypeScript all carry a factor (1.0 = 100%); `zoom_factor_from_xmile_percent`/`xmile_percent_from_zoom_factor` convert, reading Stella's `zoom="0"` as 1.0. `mdl/` is the native Vensim parser and writer (`lexer` -> `normalizer` -> `parser` -> `reader`, `mdl/convert/`, `mdl/view/`, `writer.rs`); `mdl/xmile_compat.rs` formats expressions, and its restructuring arms for builtin-named calls run before macro resolution, so a like-named macro cannot shadow them. `vdf.rs` and `vdf/` read Vensim binary data files; the readers are total on arbitrary bytes. `systems/` is the line-oriented systems format. `data_provider/` resolves `GET DIRECT` references (`FilesystemDataProvider` behind `file_io`). `json.rs` and `json_sdai.rs` are the JSON schemas.

## Units

Opt-in: a model that declares units on no variable gets no unit diagnostics. `units.rs` parses unit strings into `UnitMap`s and builds the `Context` (XMILE built-ins plus Vensim synonym groups, dropping a built-in the model redefines); `units_infer.rs` is Hindley-Milner-style inference over the free abelian group, partial-result throughout (a conflict is confined to its connected component; macro bodies' parameter-named units lower to per-instantiation metavariables); `units_check.rs` checks each equation against declared-or-inferred units, with literal-polymorphic `MAX`/`MIN`/`PREVIOUS`/`IF` and integer-literal exponent rules. Vensim's unit semantics are cited per rule; an unverified one is marked unverified. `db/units.rs` is the salsa pass.

## Analysis, layout, diagrams

`analysis.rs::analyze_model` bundles compilation, LTM discovery, and dominant-period selection into `ModelAnalysis`; a model that cannot compile returns `Ok` with `analysis_error` set so "could not analyze" is distinct from "no loops". `layout/` generates and incrementally updates diagram layouts (force-directed placement, crossing reduction, a calibrated quality metric; deterministic per seed). Incremental layout never rewrites an element the patch did not touch: position and `label_side` come back byte for byte (`layout_label_tests.rs` enumerates the arms), a label side is chosen only for elements created in that pass, and a new connector that runs through an existing label is accepted rather than re-optimizing its neighbours -- hand placement wins, and re-optimizing is exactly the churn that snaps a notebook user's dragged label somewhere else on the next edit. A label the layout wraps carries the stored two-character `\n` escape (`text::LABEL_LINE_BREAK`, the form the TypeScript editor's `encodeNameNewlines` produces), never a raw newline. `diagram/` renders SVG/PNG and exposes the exact geometry the layout metric scores.

## Tests

Unit tests live beside their code, either inline or in a sibling `*_tests.rs` mounted with `#[cfg(test)] #[path]` so `use super::*` still resolves. Integration tests are one harness, `tests/integration/main.rs` (add a `mod`, not a new `tests/*.rs`); `tests/vm_alloc.rs` is separate only because it installs a global allocator. `test_common::TestProject` is the model builder, exported behind the `test-support` feature for sibling crates' tests. There is one compiler, in tests too: a test that needs a variable's lowered form reads it through the production per-variable lowering (`TestProject::flow_exprs`, over `db::var_fragment::explicit_fragment_input` + `compiler::fragment::lower_fragment`), a test that needs a refusal's location reads `TestProject::error_diagnostics`, and a loop-discovery test drives `ltm_finding::discover_loops_with_graph` with the graph and context `analysis::analyze_model` builds. Never add a whole-model compile path for tests to compare against: it is a second implementation of layout and metadata that every compiler change then has to be made in twice. The `test/` corpus at the repo root holds models with expected outputs from other SD tools; the heavy C-LEARN and World3 gates are `#[ignore]`d and run with `--release -- --ignored`. Observe the time budgets in `docs/dev/rust.md`; test a threshold with a test-only override, not a fixture large enough to trip it.
