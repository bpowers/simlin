# simlin-engine

The simulation engine: it parses, lowers, type-checks, unit-checks, compiles, and simulates system dynamics models. The root `CLAUDE.md` holds the development rules; this file is a map of where functionality lives (paths are relative to this crate's `src/`) and of the standing invariants code in this crate keeps. It is a map, not a history: `git log` and `git blame` are the changelog.

## Compilation pipeline

Equation text becomes a running simulation in six stages. Each stage names its owners. "One owner" means the only place a decision is made; a second walker, classifier, matcher or resolver for the same fact is a defect, not a convenience.

1. **Parse** (`lexer/`, `parser/`, `ast/expr0.rs`, `variable.rs`).
   - `Expr0::new` produces the parsed AST, a bare zero-argument builtin's name (`pi`, `time`, `dt`) as the builtin's call. `ast::needs_quoting` is the one statement of which names cannot be written bare when an identifier is printed back to equation text: a keyword (`lexer::KEYWORDS`, the reserved-word table) and a zero-argument builtin's name, besides a name the lexer does not read as one identifier, so a variable of such a name round-trips quoted and still reads the variable. Bare is the builtin and quoted is the variable at every later stage: a NAME (an equation's quoted reference, a flow list's entry, a module input's source) is only ever a variable -- to name resolution (`db::var_fragment::resolve_referenced_heads`; an undeclared one is an unknown dependency like any other), to unit checking and inference, and to LTM -- so a variable declared under a builtin's name (Vensim models declare `dt = TIME STEP`) reads as itself through its quoted name. The rule is the engine's own, beyond XMILE 1.0, which reserves function names (the citations are at `ast::needs_quoting`); what Vensim does with such a name is unverified, and the MDL importer leaving such a reference bare is a disclosed gap (`mdl/CLAUDE.md`). A variable named for a clock slot (`time`, `dt`, `initial_time`, `final_time`) takes that slot's key in the results-offset map (`VariableLayout::root_shifted` inserts the clock's keys first, then the body's), so the column of that name is the variable's series and the clock keeps its slot (`results::TIME_OFF`) with no key: a reader of the clock reads the slot, as `save_check` does. `ast::print_eqn_proptest` holds `parse(print_eqn(e)) == e` over every `Expr0` variant, index form and name class (`ast::expr0_strategy`).
   - `ast::CanonicalEqn` (`ast/canonical.rs`, built by `Expr0::canonical`) is the one normal form of an equation, and so the one owner of whether two equations say the same thing: no source positions, canonical idents and function names, numbers by value, and under `Aliases::Engine` the engine's own rewrites (a builtin's alias through `BuiltinSig::by_name`, `MODULO(a, b)` as `a mod b` through `ast::operator_for_call`, which the module-function expansion applies too, `PI()` and `INF()` as their constants), none of them where the project defines a macro of the name (or, for an alias, of the builtin's own name), and no constant or operator fold inside a subscript. It has structural `Eq` and `Hash` and prints through `print_eqn`. `save_check` compares equations by it and `Expr0::eq_ignoring_loc` (helper identity) is its `Aliases::Spelling` equality walked without allocation; a caller with a further notion of sameness layers it over this form rather than restating it.
   - `parse_var(&ParseContext, impl Into<VariableSource>, ..)` is the one parse entry point. A `VariableSource<'_>` is a BORROWED view of the fields a parse reads (ident, equation, gf, units, kind, flows, module refs and target model name, `non_negative`, `can_be_module_input`, `active_initial`), built either straight over the salsa inputs (`db::variable_source`) or from a `datamodel::Variable`. A `ParseContext` carries the project-global contexts (dimensions, units, the macro registry, the enclosing macro body) plus the `SnapshotIndexFacts` a `PREVIOUS`/`INIT` subscript index is decided with.
   - A source parse reads the owning model only through per-name projections (`variable_owner_model`, `model_variable_by_name`, `variable_dimensions`, `project_has_qualified_element`), never its variable set, so `db::parse_source_variable` is keyed on `(variable, project)` (the rule under "Salsa layer").
2. **Module-function expansion** (`builtins_visitor.rs`, `capture.rs`, `module_functions.rs`, `snapshot_arg.rs`). `instantiate_implicit_modules` rewrites stdlib calls (`SMTH1`, `DELAY3`, ...) and project macros into module instances and routes `PREVIOUS`/`INIT` to the `LoadPrev`/`LoadInitial` opcodes.
   - Everything it synthesizes is parsed data on one ordered `capture::ImplicitVar` list: a `Capture` (a `PREVIOUS`/`INIT` argument that is not a static slot) or a `HoistedArg` (a call argument that is not a bare identifier) carries the argument's `Expr0` subtree, and an `ImplicitModule` carries its target model and input-port wiring. `ImplicitVar::parsed_variable` is the one conversion back to a parse-stage variable, so no helper is printed and parsed back (GH #913's class).
   - `capture::synthetic_ident` is the one derivation of a helper's `$⁚{parent}⁚{n}⁚...` name (`n` shared by an instance and its arguments). The name is an external key the runlist, the layout and the results map sort by; `capture::insert_implicit_var` is the one rule for two helpers claiming one name (a same-definition repeat is idempotent, a different helper is `DuplicateVariable`).
   - A helper's equation errors carry spans into the PARENT's equation and are reported on the parent; a helper body the COMPILER refuses is the parent's equation error too, with the compiler's code at the argument's span (`db/fragment_compile.rs`); only a codegen refusal stays an assembly row on the helper.
   - A helper keeps its parent's element context (GH #1035). `per_element_requirements` decides what an apply-to-all body needs: a snapshot-only body is captured ONCE, structurally, as an apply-to-all capture over the parent's dimensions (`CaptureShape::ApplyToAll`); a module-bearing body is expanded per element, every hoisted argument (a bare arrayed identifier or dimension name included) carrying the element it is one element of (`variable::ElementScope` on `VarKind::Aux`). A structural capture is lowered by the apply-to-all arm (`expand_per_element`) and a per-element helper by `Context::element_scope_context`, both under the element context the parent's own body gets, so a helper reads exactly what the plain spelling reads. Never add a parse-time replay of the compiler's resolution rule: two resolvers of one spelling drift exactly where the rule is non-trivial.
   - A snapshot subscript naming a dimension the parent's axes relate to (a declared mapping or subdimension) reads its slot directly: `index_spans_a_dimension` asks the compiler's own matcher (`match_axes_partial` under `DirectMappingsOnly`, the projection `active_dim_ref` uses).
   - `snapshot_arg::SnapshotArg::access` is the single statement of what a `PREVIOUS`/`INIT` argument addresses (`SnapshotAccess`: slot, view, or capture), classified by this parse and by codegen (`static_slot`, `Compiler::snapshot_static_view`) alike, so the dependency graph and the bytecode cannot disagree (GH #568's class).
   - Whether an identifier subscript of such an argument pins ONE declared element is the one model-level question the parse answers itself (a capture cannot be un-minted at lowering), through `builtins_visitor::SnapshotIndexFacts`: the source parse asks the referenced variable's declared axis -- an element of that axis wins over a same-named variable, XMILE 1.0 footnote 9 and the compiler's own `dimensions::resolve_axis_index_name` -- and whether the project declares a qualified `dimension·element`; the generated LTM parse, whose target may be a synthetic variable with no declared axis, asks whether any dimension declares the element and no variable of the model shadows it.
   - What a `PREVIOUS`/`INIT` argument's NAME denotes -- a bare module instance (refused: it has no storage of its own), a bound input port (its own slot), a module output port or a plain variable (a fixed slot) -- is resolved at lowering by `compiler::context::Context::snapshot_storage` from the dependency's shape. The parse captures only the one module-backed name it can know without the model: an instance synthesized earlier in the same walk.
   - A capture's kind is its phase demand (`capture::CaptureKind`): `PREVIOUS` storage is refreshed in flows only, `INIT` storage is populated in initials only unless a per-step definition reads its current value, and the dt and active-initial parses minting one storage for both consumers share it with the union of the two.
   - `DELAYN`/`SMTHN` rewrite to the canonical order-1 and order-3 models and wire only the ports the call names (`rewrite_alias_module_call`): an omitted initial value is the stdlib model's `isModuleInput(initial_value)` fallback to the input, XMILE 1.0 section 3.5.3; an order other than 1 or 3 refuses. `DELAY` -- XMILE's infinite-order (pipeline) delay, which the MDL importer writes Vensim's `DELAY FIXED` as -- is refused there too (`NotSimulatable` on the variable): it needs a record of the input over the whole delay time, which no stdlib model holds, and a first-order delay under its name would be a silent wrong number. Expected results for XMILE's `DELAY` are beside a Stella Architect file in `test/test-models/tests/delay_xmile` (the input exactly one delay time back; which tool wrote them is not recorded), and Vensim's for `DELAY FIXED` in `test/sdeverywhere/models/delayfixed*` and `test/test-models/tests/delay_fixed`.
   - `MacroRegistry::resolve_call` is the one routing decision for a call (`Expand`, `Passthrough`, `RenamedBuiltinSelfCall`, `Unresolved`), read by the visitor and by macro-recursion analysis. A macro shadows a like-named builtin: the engine's rule, unverified against Vensim's documentation, and the opposite of XMILE 1.0 3.2.2.5, which reserves builtin names and says a conflict SHOULD be flagged. A genuine passthrough lowers as its builtin under the macro's arity, and the enclosing macro's own renamed builtin lowers as the builtin (GH #554).
3. **AST lowering** (`ast/`, `model.rs`, `builtins.rs`). `Expr0` -> `Expr1` (typed `BuiltinFn`; `ast::typed_ast`) -> `Expr2` (array bounds resolved; `ast::lower_ast`).
   - `ast::LoweringScope` is what the `Expr2` lowering knows: the project's dimensions and, for every name the equation can reference, the `DepShape` the fragment compiler resolves it through (the same `FragmentInput::deps` map), so a helper lowers under its parent's shapes. A module output `m·x` is never a key and lowers without bounds (`compiler::Context` resolves it through the instance's shape). Every lowering -- a source variable's, a helper's, a generated LTM equation's -- runs under the shapes of the names it references.
   - An `Expr2` node's bounds slot is `ast::NodeBounds`, an `Option<Box<ArrayBounds>>`: the lowered trees are retained (the per-variable memos, the LTM handle maps) and a bound is `None` on every scalar subexpression, so a `None` costs one pointer. Readers go through `get_array_bounds`; the box is spelled only where a bound is produced.
   - `classify_dependencies` is the one dependency walk, run over the typed `Expr1` for the dependency query and over a retained `Expr2` subtree for LTM's per-slot readers, through one `DepExpr` projection per tier; it needs no scope. It records each read as a `DepOccurrence` with its `DepLag` (`Current`; `Previous`; `Initial` for an `INIT` argument or a `PREVIOUS` fallback) and each `LOOKUP` table holder as a typed table reference beside the reads.
   - `model::lower_variable` is the one `Expr0 -> Expr2` map over a variable's `kind`; its module arm resolves the instance's wiring through `db::build_module_inputs`, the one owner of that wiring, under the model's CANONICAL name.
   - Each variable is lowered ONCE: `db::lowered_source_variable` (explicit) and `db::lowered_implicit_variable` (a parse-synthesized helper) are the only owners of a lowered `Expr2` variable. The fragment borrows the memo; unit checking and the LTM describers hold its `Arc` through `db::model_lowered_variables`; no whole-model lowered copy exists.
   - `BuiltinFn::signature()` is the one statement of every per-builtin fact: name and aliases, source arity, which argument positions are array operands and whether the enclosing apply-to-all element pins their axes (`ArgKind`), the result's shape (`ResultKind`), and the invariance class (`Invariance`). `args()`/`args_mut()` and the `map` family are the uniform argument view. A match over `BuiltinFn` anywhere else encodes per-variant semantics (which opcode, which unit rule, which argument shapes the result) and says so in a comment.
4. **Per-variable fragment compilation** (`compiler/fragment.rs`, `db/var_fragment.rs`, `db/fragment_compile.rs`, `db/ltm/compile.rs`, `compiler/`).
   - `compiler::fragment::lower_fragment(&FragmentInput, is_initial)` is the one per-variable lowering entry point. A `FragmentInput` is the variable in its `Expr2` form plus a `DepShape` -- dimensions, and whether the name is a plain variable or a module instance -- for every name it can reference; it carries no offset of the model being compiled.
   - Four constructors: explicit variables (`explicit_fragment_input`), implicit helpers (`implicit_fragment_input`), LTM synthetic variables (`ltm_fragment_input`) and LTM implicit helpers (`ltm_implicit_fragment_input`). The two in-model constructors resolve dependency shapes through the per-variable firewall queries (`db::var_fragment::DeclaredName` over `model_variable_by_name`, `model_implicit_var_by_name`, `variable_dimensions`, `model_shape` for a module's sub-model, and `variable_tables` for a called table) and borrow the variable's lowering memo, so a helper the parse hoisted lowers -- and is refused -- exactly as the equation's own spelling.
   - The two LTM constructors read the whole `model.variables(db)`, `model_implicit_var_info` and `model_ltm_implicit_var_info` maps (the LTM surface they lower is itself derived from a whole-model query, `model_ltm_variables`) and share one lowering, `lower_ltm_variable`: the reads classified on the typed `Expr1`, resolved through `DepScope::resolve` to the shapes the compiler reads, and the equation lowered under that same map.
   - `lower_fragment` lowers `Expr2` -> `Expr3` (`ast/expr3.rs`, a structural rewrite that resolves wildcards and gives every bare array reference its subscripts) -> `compiler::Expr`: `compiler/mod.rs` expands apply-to-all and arrayed equations per element (`expand_per_element`); `compiler/context.rs` resolves references and subscripts against the dependency shapes; `compiler/subscript.rs` normalizes static subscripts into views; `compiler/fold.rs` folds constants.
   - `compiler/array_operand.rs` is the fragment's ONE materialization pass: it moves every array value codegen cannot express in place -- the array-producing builtins, the per-element arrayed-GF applies, and the computed array operands -- into temps, so codegen only ever sees views. It is the only caller of `ast::TempAllocator::alloc`; the allocator is owned by the `compiler::Context` the fragment lowers under and shared by every context derived from it.
   - `compiler/codegen.rs`, under the same input's `FragmentInput::emit_ctx`, emits `SymbolicOpcode`s whose variable operands are `VarRef { name, element_offset }`.
5. **Assembly** (`db/layout.rs`, `db/assemble.rs`, `compiler/symbolic.rs`).
   - `compute_layout` assigns slots per model, and `flattened_offsets` reads that layout back out as the results-offset map (`CompiledSimulation::offsets`: `module·var` through each module instance, `var[e1,e2]` per element of an arrayed variable, explicit or a structural capture helper (GH #1033), no key for a lookup-only table or for an INIT-only capture, whose slot nothing writes per step), so slot order is stated once.
   - `assemble_module` collects every fragment source -- explicit, implicit, LTM synthetic, LTM implicit -- into one map and emits each of the module's three programs in runlist order: a resolved recurrence SCC's members replaced by the SCC's combined fragment at the first member, the run-invariant flows hoisted ahead of the dynamic ones, the LTM tail after the runlist. It drives ONE `FragmentMerger` through them: every initial as a standalone program, then the flows and the stocks as one concatenation each. The merger renumbers per-fragment literal/GF/module/view/temp/dim-list ids into the module's single table set, de-duplicates graphical functions by content, and gives each program its own literal pool; `resolve_module` then turns `VarRef`s into offsets.
   - A combined fragment interleaves the members' per-element segments in the element graph's order, and `segment_member_by_element` is the one statement of where a member's code splits -- the graph and the combiner both read it. A member's PROLOGUE (the leading temp blocks two or more elements read, or that a later prologue block reads) is emitted once, immediately before the first of its readers in that order, and the graph wires the prologue's reads into exactly those readers, so a recurrence whose shared temp reads a non-reader element runs that element first rather than being refused.
   - `assemble_simulation` enumerates module instances (`enumerate_module_instances`: a model's explicit `Module` variables and the instances its parses synthesized, one candidate shape, each recorded under `(target model, bound-port set)`) and builds the `CompiledSimulation`.
   - A reference's port is `port_of(dst)`, and the one bound-port rule over it (`bound_port`: `port_of(dst)` when the `src` is outside the instance's namespace) is what both the instance's compilation identity (`module_input_set`) and its lowered wiring (`build_module_inputs`, at lowering) project from, so the ports a sub-model is compiled under are the ports its instance writes; a reference `bound_port` declines is dropped there without an error, which is why the wiring is validated by the diagnostic pass.
   - `model_module_wiring_diagnostics` validates `port_of(dst)` for every reference and warns about a reference to one of the instance's own ports whose `src` is inside the instance's namespace, which binds nothing (a `src` inside the namespace with a `dst` in another instance is the connect a writer records on the source instance, and the `dst` check is its report).
6. **Execution** (`vm.rs`, `bytecode.rs`, `wasmgen/`). The stack VM runs initials, then per step flows and stocks, under Euler, RK2, or RK4. `wasmgen` lowers the same `CompiledSimulation` to one self-contained wasm module that mirrors the VM opcode for opcode.
   - The run is on a step grid that `results::Specs` states once and both backends compute in the same f64 operations: the clock is counted, never accumulated (step `k` is at `Specs::time_at(k)`, `start + k * dt`); the run evaluates steps `0..=Specs::final_step()`; saved row `m` is the first step at or after its save time (`Specs::saved_row_step`), so a save step that is not a whole number of DTs keeps its declared row count and times to within a DT (the engine's rule; XMILE has no save step and what Vensim does with a SAVEPER off the TIME STEP grid is unverified) and is reported as the warning `SaveStepOffTheStepGrid`. A time a person writes as a step's is read as that step within `STEP_TOLERANCE` (a millionth of a step). Whatever finite numbers the specs hold, a run is refused with a reason or has row zero at step zero: specs no run can be made under (a stop before the start, a DT that is not positive) are refused by both backends for the one reason `Specs::refusal` gives, the save step in DTs is kept finite, and a run whose rows cannot be counted or that the allocator will not give is `BadSimSpecs`, its numbers written as a person writes them (`results::written`; the wasm blob also refuses a run of more steps than its i32 counter holds).
   - `Vm::run_to(t)` evaluates every step at or before `t` and rests at the next, unevaluated; `Vm::run_until(t)` evaluates every step before `t` and rests at the first step at or after it, which is where a caller sets a value that must hold from `t`. The clock never goes back: a finished run rests one step past the stop, its stocks integrated through the final step and its flows previewed, and a further call takes no step. The wasm blob's resting `curr` is the VM's, bit for bit, while the target is before the blob's last saved row; from there on the blob rests at that row, evaluated, and takes no step past it (with a save step over DT, not even those before the stop). `wasmgen::module_tests::where_a_run_rests_on_each_backend` tables both; making the blob rest where the VM does is a question of its ABI, left open. `Vm::with_specs` runs a compiled program under other specs: the program does not depend on them.
   - XMILE's `PULSE` fires at the first step at or after its time, read on the step grid within `STEP_TOLERANCE`, so a pulse time written as a step's is that step (`vm::pulse`, and `emit_pulse` in `wasmgen/lower.rs`). XMILE 1.0 section 3.5.4 says only "a one-DT wide pulse at the given time"; what Stella does with a pulse time between two steps is unverified (every PULSE in the corpus is at a step's time). Vensim's `PULSE(start, width)` is another function, which the MDL reader lowers to its own expression. `STEP` compares the clock half a step ahead.

`db::compile_project_incremental` is the single production entry point for ordinary models. `queue_compile::compile_sim` is the dispatch every VM-backed caller goes through: a model with a conveyor or queue marker takes the special-stock path (below), anything else goes to `compile_project_incremental`. `build_sim` is `compile_sim` plus `Vm::new`.

## Salsa layer (`db.rs`, `db/`)

`SimlinDb` owns the salsa storage, the sync state of the last synced datamodel, the expanded (conveyor/queue) twin's sync state, and the one-shot stdlib model inputs. The inputs (`db/input.rs`) are `SourceProject`/`SourceModel`/`SourceVariable`, storing datamodel fields directly so invalidation is per field; `db::variable_source` is the parser's borrowed view of them. `db/sync.rs` maps a `datamodel::Project` onto those inputs through one extraction per input (`SourceProjectFields`, `SourceModelFields`, `SourceVariableFields`, each a `from_datamodel`) that both the fresh-sync constructor and the incremental updater read, reusing handles across syncs and setting only fields whose value changed. `db::simulation_key` hashes those same extractions, and every type their fields hold, each destructured without `..`, leaving out what no run reads (units; the names and uids only a diagnostic words; a pinned loop's description; a table's y scale, and its x scale beside written x points): a field the compiler starts reading is a compile error there until the key says whether it counts, so the key cannot fall behind the sync. `db/simulation_key_tests.rs` takes each type's field list from a pattern that must name them all (`fields!`, `variants!`) and fails for a field or variant with no row. Text is hashed as written, so a respelled equation or a case-only rename moves the key: it may call one simulation two, never two one. A sync state remembers the variable each input was last set from (`PersistentVariableState::synced`, by its `Arc`), so a re-sync after a patch, which shares every variable the edit left alone, extracts and compares only the variables the edit replaced (`db/sync_identity_tests.rs`). What a pass may take from that memory is stated once, in `InputMemory`: the state must be that of the inputs' latest sync (`PersistentSyncState::is_current`; a rollback re-syncs with the state from before a staging, and compares every variable), and an input is answered for once per pass, so a second variable or a second model that shares an input (two of one canonical name) is always compared. The standing test of the incremental sync is that a db holds, after any sequence of syncs, staged syncs and rollbacks, what a fresh db synced to the same project holds, and so answers what it answers (`db/sync_differential_tests.rs`, over a pool of projects that varies every field the sync writes: the default suite compares the inputs, the gates every diagnostic, series and loop count too). The stdlib models' inputs are the db's own and no sync writes them: a project model named for a stdlib model has inputs of its own and stands in the stdlib model's place while the project holds it. Two project models known by one name (`datamodel::canonical_model_name`: the canonical name, an unnamed model's being `main`) make a project refused as a model with two variables of one name is (`db::diagnostic::project_duplicate_models`: the compile gate and one project-level `DuplicateVariable` row), and `AddModel` refuses to make one. Of several models of one canonical name the sync files only the last (`filed_models`), so re-syncing such a project makes no input. `AddModel` also refuses a name under the stdlib's prefix: the one way a project holds a stdlib model is the stdlib's own definition, which `Project::ensure_referenced_stdlib_models` adds. Everything else is tracked queries:

- `db/query.rs` -- per-variable parse (`parse_source_variable`), direct dependencies, dimension reads, module maps, the module-reference graph (`project_module_graph`), and the firewall queries (`model_variable_by_name`, `model_implicit_var_by_name`, `project_model_by_name`, `variable_owner_model` over the `owner_model` name the sync sets on every `SourceVariable`, `project_has_qualified_element`, `variable_tables`) that let a fragment or a parse depend on one variable, one owner, one model or one element instead of the whole map.
  - One dependency representation: `variable_direct_dependencies` owns a variable's reads as `DepRefs`, a set of `DepRef { target: DepTarget { module_path, variable, stock_output }, phase, lag }` for the variable and for each helper its parse synthesized (`ImplicitVarDeps`), plus the typed `referenced_tables`.
  - `DepScope::resolve` proves every `·` hop against metadata through the per-name projections: the head must be a module instance in scope (an explicit `Module` variable or an implicit instance), each further segment a `Module` variable of the model the previous hop instantiates, and the terminal's kind is read in the same walk (`stock_output`). A leading `·` is XMILE's parent-scope spelling, read as the bare name. A spelling that fails a hop is one local name, that `·` stripped, which the compiler refuses at lowering.
  - No consumer splits a name. `dep_graph::ordering_edges` is the one statement of which reads order which phase: a `Dt`/`Current` read orders the dt phase unless its target is a sub-model stock, at any depth (a prior-step read); every init read but `Previous` orders initials; `Dt`/`Initial` reads seed the initial snapshot. `dt_previous_only` is `Previous - Current`: an `INIT` read never cancels a lag. The pinned-loop and statelessness gates, the causal edges, the output-port scans, the lowering memos' `heads`, the layout and the libsimlin surface all read the projections.
  - The causal-edge builder records the sub-model outputs each node reads once (`CausalEdgesResult::module_outputs_read`); both LTM modes select a loop's exit port from it (`unique_module_output`).
- `db/implicit_deps.rs` -- `ImplicitVarDeps`, one per helper a parse synthesized: the helper's identity, its `capture_kind` (the phase demand the runlists read; `None` for a hoisted argument or a module instance), its reads as `DepRefs` (a module instance's are its input sources) and its typed `referenced_tables`, built by `extract_implicit_var_deps` through the same `DepScope` the parent's reads resolve through.
- `db/dep_graph.rs` -- the dependency graph and cycle gate: runlists, the dt/init cycle relation (`walk_successors`), and recurrence-SCC resolution (an SCC whose element-level graph is acyclic is compiled as one interleaved fragment instead of being rejected). A capture's runlists are its kind: an INIT-only capture leaves flows unless a per-step definition's current-value closure reads it, a PREVIOUS capture is never seeded into initials, and a helper's `INIT` referents are initialization roots. A model instantiated as a module (an explicit module's target, a stdlib template, a macro) evaluates every value-bearing variable in its initials, because a parent's initials may read any of its ports and XMILE's model is one flat graph (GH #1028).
- `db/diagnostic.rs` -- the per-model diagnostic owner `model_all_diagnostics` and the drains `collect_model_diagnostics`/`collect_all_diagnostics`. The payload is `crate::diagnostic::Diagnostic` (below), the salsa accumulator itself.
  - A recursive query never accumulates: `model_ltm_variables` and `model_ltm_fragment_diagnostics` return ordered `Vec<Diagnostic>` facts on their memoized values and the dependency graph returns its cycle as `ModelDepGraphResult::cycle_variables`; the owner emits each model's facts once (a parent reaches a child's LTM derivation through module scoring and layout, so a warning accumulated inside it would be reported once per reaching model).
  - The drain collapses identical rows by full equality (one fragment's two phases, one parent's per-element helpers).
  - Rows come out in the accumulator walk's order -- a memo's own rows, then each input's in first-read order: the owner's own advisories, the fragments, the cycle facts (`model_cycle_diagnostics`), the helpers, the unit pass, the wiring check and the LTM facts (`model_ltm_diagnostics`), each a tracked child read in that order. A source that must follow the variables' rows is a child, never a row the owner files itself.
- `db/units.rs`, `db/macro_registry.rs`, `db/invariance.rs` -- the unit-check pass (`check_model_units`, over a stack-local `UnitModel` view of each scope model's `model_lowered_variables`; `model_scope_models` is the module-reachable closure inference runs over, an iterative name-only worklist), the macro registry query, and run-invariance classification of flow variables: the fragment's compiler-local verdict (`compiler/invariance.rs`, a walk that treats every reference as invariant and refuses the time-dependent builtins, lagged reads, module evaluation and module inputs) joined with the variable's `Dt`/`Current` `DepRef`s and called tables, so a conditional the compiler folds keeps both arms' reads and is under-hoisted, never wrongly hoisted.
- `db/var_fragment.rs`, `db/fragment_compile.rs`, `db/layout.rs`, `db/assemble.rs` -- the fragment constructors and assembly (pipeline stages 4 and 5).
- `db/analysis.rs`, `db/ltm_ir.rs`, `db/ltm/` -- LTM (below).
- `db/exec_probe.rs` -- `ProbedDb`, the execution-count probe the incrementality tests read.

### Rules the salsa layer depends on

- A cached value is a pure function of its inputs. Never let `HashMap` iteration order reach a cached value or the compiled artifact: sort first (`temp_sizes_by_id`, sorted table idents in `Compiler::new`, sorted module inputs in `Var::new`, sorted runlist seeds). Pinned by the 12-repeat `db::fragment_determinism_tests` and `db::diagnostic_determinism_tests`, and on the surfaces a host reads by `tests/integration/build_determinism.rs`, which opens a file twice in one process and builds every artifact from each open (saves, diagnostics, links, the wasm blob and layout, results, loop analysis): an artifact that differs took its order from a map.
- AST constants hold `ast::Literal`, compared by bit pattern, so a `NaN` literal (every stdlib template declares `initial_value = NAN`) does not defeat backdating. Any new float-bearing field reachable from the AST must use `Literal`; the `Eq` derives make a bare `f64` a compile error. The salsa inputs hold datamodel types, whose `==` compares floats bit for bit for the same reason (`datamodel::bitwise_eq!`): a lookup table holding a NaN is set once, not on every sync.
- A per-variable query needs a per-variable key. Reading a whole-model value (`model.variables(db)`, `ModelDepGraphResult`) from a per-variable query makes every variable recompile on any edit; go through a projection query that returns only what is needed (`var_runlist_membership`, `model_variable_by_name`, `variable_tables`). Whether a projection bought anything is measured, never assumed: `db::exec_probe::ProbedDb` counts every tracked query's body entries over an edit from salsa's own `WillExecute` events, because salsa backdates an equal value and keeps the memo address, so neither the value nor the pointer says whether the body re-ran. Gates: `db::fragment_char_tests::implicit_helper_add_is_tight_for_plain_and_module_helpers`, `module_helper_add_reparses_only_the_added_variable`, `equation_only_edit_recompiles_only_the_edited_fragment`.
- One lowering per variable. A variable's `Expr2` form is its memo (`lowered_source_variable`, `lowered_implicit_variable`); a consumer that needs a whole model's lowered variables assembles handles (`model_lowered_variables`, an `Arc<Variable>` per name), never a second lowering (`db::lowered_variable_tests` pins the sharing by `Arc::ptr_eq` and `ProbedDb` body counts).
  - The memo lowers under its dependencies' DIMENSIONS only (`DeclaredName::dimensions_shape`): a module instance's compiler shape is its sub-model's layout, a recursive query that a module cycle -- reachable through the unit pass -- turns into a salsa panic. The one map entry that is not a memo, an element-scoped helper's element-pinned projection (the read the LTM describers classify), resolves the helper's heads to the compiler's shapes, a module head's included, so the map builder takes it only where `project_module_graph(..).cycle_error_from(..)` is `None` and holds the memo's handle under a cycle, which the unit pass reads identically (`db::units_tests::a_module_cycle_reached_through_a_per_element_helper_still_unit_checks`).
- A source parse is a function of `(variable, project)`. `parse_source_variable` reads the variable's fields, the dimensions it names, the project-global contexts and, for a `PREVIOUS`/`INIT` subscript index, one referenced variable through its owning model's per-name projections -- never the owning model's variable set or a module instance's wiring: a model-derived parse KEY cannot backdate at all, so it re-executes every parse in the model on any edit that moves it. A decision that needs the owning model belongs in lowering, where `FragmentInput::deps` knows every name's kind; failing that, on the `SourceVariable` input as a field set at sync (`owner_model`, read back through `variable_owner_model`) -- never a per-variable scan of a model map.
- A module cycle drives recursive tracked queries into salsa's dependency-graph panic, which is a process abort under `panic = abort`. Every compile, diagnostic, and analysis entry point (`model_detected_loops` included) consults `project_module_graph(..).cycle_error_from(..)` before recursing (`db::module_cycle_tests`).
- Salsa has no input reclamation. Inputs are reused across syncs, never recreated, and the expanded-project slot is allocated at most once per db.
- Diagnostics derived once per project (macro-registry build error, unit-definition errors, module cycles, models known by one name) are emitted from their memoized value by `collect_all_diagnostics`, and diagnostics derived by a recursive or multiply-keyed query (the LTM facts, the dependency graph's cycle) are returned on the value and emitted by `model_all_diagnostics`: an accumulator inside such a query reports once per reachable model and is lost after an unrelated revision bump prunes the subtree (`db::diagnostic_payload_tests::every_warning_family_is_emitted_once_across_revisions`).

## Standing invariants of the compiler

- **Addresses are assigned once, at assembly.** Lowering and codegen name variables (`VarRef`); nothing before `resolve_module` knows a slot, and a `FragmentInput` carries no offset of the model being compiled. A cross-module reference `m·x` lowers to `VarRef { name: m, element_offset: x's slot inside the instance }` because only the sub-model's layout is fixed at that point: the module dependency's `DepKind::Module` carries that layout as a `ModelShape` (`db::model_shape`, recursively for nested instances), and `Context::resolve` is the one reader of it. `VarSizes` (keyed by `VarRef`, projected from the dependency shapes by `fragment::reference_extents`) is the only size information codegen reads.
- **`resolve_bytecode` is the only producer of concrete bytecode**, and it proves the VM's fixed-stack safety: a program deeper than `STACK_CAPACITY` is a compile error. The peephole fusions (`SymbolicByteCodeBuilder`) run before resolution and are address-independent, so resolution is a 1:1 opcode mapping; the run-invariant flow prefix length and SCC segmentation count on that. `Compiler` (through its `SymbolicByteCodeBuilder`) is the only producer of a `SymbolicOpcode`, so every variant of that enum (and of its `Opcode` twin) is one codegen emits; the dead-code lint, denied under clippy, enforces it -- never `allow` it on a variant.
- **Both opcode enums are tables.** `symbolic_opcode_table!` (`compiler/symbolic.rs`) and `opcode_table!` (`bytecode.rs`) hold one row per opcode: its operands and, on the symbolic side, its concrete twin; on the concrete side, its stack effect. An operand's type is its kind -- `SymVarRef`, `LiteralId`, `ModuleId`, `ViewId`, `DimListId`, `TempId`, `GraphicalFunctionId` with its `TableCount`, `PcOffset`, anything else data -- and `resolve_opcode`, `renumber_opcode`, `gf_run`, `var_ref`, `jump_offset`, `stack_effect` and `name` derive from the rows, so adding an opcode is one row plus its `vm.rs` and `wasmgen` arms. The every-row tests (`symbolic_table_tests`, `bytecode::tests`) and the merge proptest's blanking oracle derive from the same rows; `vm.rs`, `wasmgen`, the fusion patterns and the `db/` scans name variants by what they mean and stay hand-written.
- **A stock update is always the fused `BinOpAssignNext`.** There is no un-fused `AssignNext`; `Var::new` rejects any update whose lowered form does not end in an `Op2`.
- **An array operand is a view over storage.** Codegen accepts `StaticSubscript`, `TempArray`, `Var`, `Subscript`, and an array-valued `PREVIOUS`/`INIT` (a view over a snapshot region). `array_operand.rs` materializes everything else into a temp; a shape it cannot size declines and codegen reports the error.
  - Temps are per-fragment, 0-based, and recycled across sequential fragments; an interleaved SCC fragment sums them instead (`TempStrategy`). Within a fragment every id comes from one `TempAllocator`, issued by that one pass and final when issued: a body two or more elements read takes one id for the equation and is written ahead of the element code, and a body one element reads takes an id the elements reissue (`element_scopes`), so an equation costs one id per simultaneously-live temp rather than one per element (`db::temp_allocation_tests`).
  - The bytecode `TempId` is a `u8`: every opcode that writes a temp narrows the id with a plain `as TempId`, unguarded, while a static VIEW over a temp carries the `u32` and is rejected at resolution above 255 (`symbolic::resolve_static_view`, pinned by `test_resolve_static_view_temp_past_the_id_namespace`). GH #583 is that namespace; no shape in the corpus reaches it, and the write side stays deliberately unguarded.
- **No silent wrong numbers.** When a construct cannot be compiled correctly, refuse with `NotSimulatable` (VM) or `WasmGenError::Unsupported` (wasm) rather than approximate. The wasm backend has no VM fallback. The loud-safe refusals each keep their test: the stack bound, `resource_base`'s id capacity, `renumber_opcode`'s checked adds, the combiner's SCC segmentation (`db::dep_graph_tests::a_prologue_reading_an_scc_member_refuses_the_recurrence`) and `fragment_vars_in_layout`.
- **The VM is the correctness oracle for wasmgen.** Every emitted module is run under a pure-Rust wasm interpreter in tests and compared with `Vm::run_to_end`; the corpus in `tests/integration/simulate.rs` does this for every VM-simulated model (`ensure_wasm_matches`), and `simulate_ltm_wasm` does it for every exposed key of an LTM run.
- **Constant folding is platform-deterministic.** `compiler/fold.rs` folds only IEEE-exact operations with the VM's own `eval_op2`; `^` and transcendentals stay runtime so the VM and the wasm blob agree bit for bit.
- **Graphical functions:** a per-element arrayed GF's tables are laid out at the element's row-major declared-dimension index (`variable::reorder_arrayed_element_tables`), because `Lookup`/`LookupArray` index `graphical_functions[base_gf + element_offset]`. A standalone lookup-only variable (empty or `"0+0"` equation plus a table) is a static table: excluded from every runlist, no series, and a bare reference to it is `LookupReferencedWithoutArgument`. `WITH LOOKUP` is value-bearing and lowers to `LOOKUP(self, input)`. `variable::parse_table` builds the table every lookup reads, from the points as the datamodel holds them: omitted x points are spread over the x scale, a lone point at the scale's start. The lookups binary-search x, so x that decreases anywhere is `BadTable` with the two values (XMILE 1.0 section 4.1.3: "the x-values MUST be in ascending order"), as is an x that is not a finite number (an infinite end extrapolates to `inf - inf`) and, for x points spread over the scale, a scale bound that is not finite or a minimum above the maximum (the reason names the scale, and a per-element table's names its element); nothing downstream of the datamodel reorders points. Vensim reads a lookup listed out of x order as the curve through its points (ground truth: `test/test-models/tests/subscripted_lookups`), so the MDL importer puts them in order as it reads them (`mdl::convert::variables::points_in_x_order`, which a `GET DIRECT DATA`/`LOOKUPS` series goes through too). Neighbouring points that share an x are a vertical step and in order as they stand; each `LookupMode` reads one by the rule it reads every knot by, wherever in the table it is (at that x: the first listed point when interpolating or stepping forward, the last when stepping back), the engine's rule and the same on both backends. How a lookup reads its table is the opcode's `bytecode::LookupMode`, never a property of the stored table (tables are de-duplicated by their points): a plain application (`LOOKUP(t, x)`, `t(x)`, `WITH LOOKUP`) takes the mode of the table's kind (`LookupMode::of_kind`: continuous interpolates and holds the end values, extrapolate extends the end segments, discrete holds the next lower x's value; XMILE 1.0 section 3.1.4), and `LOOKUP_FORWARD`, `LOOKUP_BACKWARD` and `LOOKUP_EXTRAPOLATE` (Vensim's `LOOKUP FORWARD`/`BACKWARD`/`EXTRAPOLATE`) name their own and keep it whatever the table's kind. `Compiler::lookup_mode` is the one place the mode is decided: each element of a per-element graphical function is read by its own kind, and a lookup that picks its table as the model runs (a computed subscript, every element under a reducer) is refused when the tables it can reach differ in kind. `vm::lookup_in_mode` and `wasmgen::lower::HelperFns::lookup` are the two dispatches, and `wasmgen/lookup.rs` holds the differential test (any table, any index, every mode, VM against wasm). The lookups never read before a table: a search that ends at the first knot without hitting it answers with that knot.
- **Floats.** `float::NA` is Vensim's `:NA:`, the finite value `-2^109`, so `IF x = :NA:` works and `:NA:` arithmetic stays finite. A NaN is an absorbing failure signal, produced for out-of-range vector reads and empty reducers other than `SUM`. The module docs of `float.rs` are the landing page for this.
- **A helper reads what the plain spelling reads.** A hoisted argument, a capture and a per-element helper lower under the parent's element context and dependency shapes, so they read, and are refused, exactly as the plain equation is (`db::lowering_scope_tests::a_helper_reads_what_the_plain_spelling_reads`, `a_helper_is_refused_where_the_plain_spelling_is`, `mapped_reference_semantics_tests::a_hoisted_argument_reads_what_the_plain_equation_reads`).

## Arrays

- Subscripts are 1-based in source and 0-based internally. Dimensions are `dimensions::Dimension` (`Indexed` or `Named`); `DimensionsContext` holds subdimension relations, `maps_to` chains, and element-level mappings, and is the single statement of how a mapped read resolves (`resolve_mapped_read`: name on the source axis, then the declared mapping, then a mapped parent; `resolve_dimension_subscript` adds the one ordinal last resort, for a subscript that NAMES its active dimension over an axis declaring no correspondence to it, and both subscript paths -- static `build_view_from_ops`, dynamic `lower_index_expr3` -- resolve a dimension-named index through it, so a sibling index decides a reference's route and never its rule, GH #1044). `resolve_axis_index_name` is the single element-vs-dimension-name precedence for a bare identifier inside brackets (element first); the compiler and the LTM describers both read it.
- `dimensions::match_axes` is the single statement of how two axis lists pair: exact name, then declared mapping, then subdimension, then size, staged flat (each rule runs across every source axis before the next runs for any) and one-to-one, so a stronger match wins a target axis whatever the declaration order and no two source axes read the same one.
  - Every compile-time caller asks it -- the implicit subscripts a bare arrayed reference gets, the subscripts a bare reference under a reducer gets, the reordering that lines two operands up, `Expr2`'s bounds unification, the per-element resolution inside an apply-to-all body, and the view join -- and supplies an `AxisRelations` projection saying which declared relations it can act on: `DimensionsContext` answers the mappings; `DirectMappingsOnly` withholds the mapping-onto-a-parent rung from a caller that resolves the paired element by ORDINAL; `SubdimensionRelations` adds the subdimension rung for the one caller that never resolves an element through the answer; `NoAxisRelations` is what a caller comparing two `ArrayView`s can supply (`axis_match_tests` rows every arm).
  - `match_dimensions_two_pass` stays separate: it is the RUNTIME broadcast matcher, pairs `dim_id`s where no `DimensionsContext` exists, and states a deliberately weaker rule (id, then size for indexed dimensions).
- In lowering, `ArrayView` (`ast/array_view.rs`) is the compile-time shape (dims, strides, offset, sparse mappings, dimension names). Apply-to-all equations are unrolled per element; a reference inside the body resolves each axis against the active element, broadcasting a lower-dimensional source by dimension name.
  - A subscript naming a dimension is an `IndexOp::ActiveDimRef` all the way to `compiler::subscript`, which allocates the active positions ONE TO ONE across a reference's subscripts (so `square[D,D]` under a `[D,D]` target reads the cell, not the diagonal) and resolves the element through the one mapped read; `compiler::project_var_index_to_temp` pairs a temp's axes to the variable's by the same two rules.
  - Array-producing builtins (`VECTOR ELM MAP`, `VECTOR SORT ORDER`, `RANK`, `ALLOCATE AVAILABLE`, `ALLOCATE BY PRIORITY`) and per-element arrayed-GF applies are materialized into `AssignTemp` and read back per element; whether that happens once per equation or once per element is decided by structural identity of the lowered body (`compiler/array_operand.rs`).
- `VECTOR ELM MAP` and `VECTOR SORT ORDER` follow genuine Vensim semantics, ground-truthed against Vensim output in `test/` (`vm_vector_elm_map.rs`, `vm_vector_sort_order.rs`): ELM MAP reads the source variable's full row-major storage from the base the reference establishes with no wraparound and NaN out of range; SORT ORDER ranks within each innermost row, 0-based.
- At runtime a `StaticArrayView` is resolved once per opcode (`PushStaticView`) and `ViewStorage` says which region it reads (`Curr`, `Temp`, `Prev`, `Initial`); dynamic subscripts go through `PushVarViewDirect` plus `ViewSubscriptDynamic`/`ViewRangeDynamic`. `BeginIter` loops evaluate elementwise bodies into temps, matching source views to the iteration by dimension id (`match_dimensions_two_pass`).
  - A view's axis therefore has to be named for the dimension it ranges over, and both statements of that name must agree: a star range `arr[*:Sub]` produces a `Sub`-named axis in `compiler::subscript::build_view_from_ops` and in `ast::Expr2`'s bounds, so the temp the reference materializes into matches its source view rather than reading NaN for every element.
  - A dimension-reordering transform on an `ArrayView` goes through one helper (`permute_axes`) because `dims`, `strides`, `dim_names`, and every `SparseInfo::dim_index` -- an index INTO `dims` -- move together; moving three of the four addresses the wrong axis (GH #1027).

## Loops That Matter (LTM)

LTM instruments a model with synthetic variables (link scores, loop scores, aggregate nodes, module pathway and composite scores) that are compiled through the same fragment pipeline as user variables and read back after simulation. Exhaustive mode enumerates every elementary circuit; discovery mode scores every causal edge and finds loops from the recorded series after the run. `db::model_ltm_mode` is the one gate that decides which, read by both the scored and the detected-loop surfaces.

- `db/ltm_ir.rs` -- the front door: walks each variable's `Expr2` once and classifies every reference site by access shape (`RefShape`: `Bare`, `FixedIndex`, `PerElement`, `Wildcard`, `DynamicIndex`) and routing (direct or through an aggregate node). Every other LTM consumer reads this IR rather than re-walking the AST.
  - A dimension-named subscript is classified by the compiler's own resolution (`ltm_agg::classify_axis_access` over `DimensionsContext::executed_read_correspondence`: the element's name first, then the declared element map, in either declaration direction): all-iterated axes are `Bare` exactly when the two declared dimension lists reproduce the pairing the subscript spells (`db::bare_axis_pairing`, the one pairing behind `expand_same_element`, the arrayed score's admission and the dependency pins), and `PerElement` carrying the axes otherwise (shared element names under no mapping, a subrange over a superset, a transposition).
- `ltm_agg.rs` -- aggregate-node enumeration: each statically describable reducer subexpression becomes a `$⁚ltm⁚agg⁚{n}` node with a per-source `read_slice` of `AxisRead`s. A bare arrayed argument's slice is pass 0's pairing of its axes with the enclosing iteration (`match_axes_partial` under `DirectMappingsOnly`; whole-array with no iteration in scope or inside an array-producing builtin), so it hoists exactly as its subscripted twin does.
  - The node stores its reducer with that spelling written out (`AggNode::reducer`), which is also the synthetic dedup's identity (`synthetic_by_key`: `sum(pop)` in a scalar owner and `sum(pop[region])` under a `region` iteration are two nodes; a reducer's text is resolved to a node only among its owner's own nodes, `by_var`).
  - A per-element (`Ast::Arrayed`) slot's bare argument reads the row its element pins; the node minted for it is the whole array, so the slot's edge through it is declined loudly by the per-element-owner rule (`unhoisted_reducer_source_read`) rather than scored against that node. A source element no target element reads is no row (`iterated_axis_slot_elements`).
- `db/analysis.rs` -- causal edges (variable and element level; an INIT-only capture is no causal node, so no edge leads into or out of it), tiered circuit enumeration (an edge read from a strict subset of an `Ast::Arrayed` target's slots is target-restricted, `EdgeShapesResult::target_restricted_edges`, and keeps its cycles on the element-level path with one loop per circuit), cycle partitions, detected loops (`model_detected_loops`, empty under a module cycle).
- `db/ltm/` -- generation and compilation.
  - `mod.rs`: `model_ltm_variables`, and `endpoint_dimensions`, the projection of `model_dep_shape` onto plain variables (an explicit variable's declared dimensions, a structural capture's, none for a module) read by the causal edges, the element graph, every score emitter, the loop builders and the pins -- one shape answer is not one emitter, since an element-bound helper's edge exists at one element and only `try_implicit_scalar_to_arrayed_link_scores` scores it.
  - `equation.rs`: `LtmEquation`, the typed per-arm `Expr0` a synthetic variable carries (a text generator's arm is parsed once, `LtmArm::new`; a typed generator's arm is its tree, `LtmArm::from_typed`). `link_scores.rs`: the emitters, each parsing its arm once and reading the completeness guard off that arm; `shaped_link_score` is the per-shape entry.
  - `loops.rs` (including cross-aggregate loop recovery), `pinned.rs` (`LOOPSCORE` pins), `compile.rs` (`lower_ltm_variable`, the one lowering of a generated equation or a generated capture under the shapes of its reads; fragment compilation; the compile-failure diagnostic pass), `parse.rs`.
  - `LtmImplicitVarMeta` is captures only: a generated equation is built from an expanded tree and mints no module instance, so the module universe under LTM is the source models' own (`db::assemble::enumerate_module_instances`).
- `ltm_augment.rs` and its `ltm_augment_*.rs` children -- the ceteris-paribus equation generators: wrap every non-source reference of the target's equation in `PREVIOUS`, pin arrayed dependencies to the element the target reads (`subscript_idents_in_expr0`, on the tree), and freeze subscript indices. The clock is a frozen input too (GH #1016): a changed-first partial reads `TIME` and a time-dependent call (`STEP`, `RAMP`, `PULSE`; the builtin's own `Invariance::TimeDependent`, read through `is_time_dependent_builtin`) at the previous step -- a bare `TIME` through the per-model helper `$⁚ltm⁚freeze⁚time = PREVIOUS(TIME)` (`FROZEN_CLOCK_HELPER`, minted once by `model_ltm_variables` when any arm reads it), a call lagged whole with its arguments verbatim, or left to the enclosing freeze inside a frozen dependency's subscript index -- unless the call holds an occurrence of the isolated input's live shape (the occurrence IR's verdict), in which case it stays live, clock included; the changed-last duals (`wrap_live_shaped_in_previous`, `wrap_matching_in_previous`) leave the clock live because their numerator reads every other input at `t` on both sides. A flow-to-stock score is the closed-form partial of the stock's synthetic net-flow aux `$⁚ltm⁚net⁚{stock} = inflows - outflows` (`generate_net_flow_equation`, minted beside the score by `shaped_link_score` and deduplicated by name), `sign * |Δflow / Δnet|` over the same `[t - dt, t]` window as every other link; the aux is not a causal node. Production never parses a target equation; it lowers the target's `Expr2` back to `Expr0` (`patch::expr2_to_expr0`) and consults the IR by structural path, and a target with no lowered body is declined (`PartialEquationErrorKind::MissingTypedTarget`), never scored around user text or a `0` body. An aggregate node's reducer is the classified `BuiltinFn<Expr2>` (`AggNode::reducer`, projected by `reducer_expr0`); `AggNode::reducer_key` is its printed identity for the dedup, the IR's routing and the wrap's matching, never an equation to parse.
- `ltm/` -- the vocabulary (`Link`, `Loop`, polarity in `types.rs`), `CausalGraph` (`graph.rs`), Johnson's circuit enumerator and Tarjan SCC (`indexed.rs`), cycle partitions (`partitions.rs`), static polarity analysis (`polarity.rs`).
- `ltm_finding.rs` with `ltm_finding_enum.rs` and `ltm_finding_fallback.rs` -- post-simulation discovery: exact union-graph enumeration, a shortest-path sampling fallback under a wall-clock and memory budget, retention against the full loop universe, and the coverage-aware cap.
- `ltm_post.rs`, `ltm_dominance.rs` -- relative loop and link scores (normalized within a cycle partition, in emission order so the IEEE sum is stable) and dominant-period selection, whose periods begin and end at the run's saved rows' own times (`calculate_dominant_periods` takes them, never a cadence: a save step off the DT grid saves rows unevenly).

Rules:

- LTM is an analysis overlay, so an LTM-only failure must never masquerade as a project compile error (the overlay is an argument of every query, `db::LtmOverlay`; libsimlin's `get_errors` assesses compilability with it `Off` and harvests LTM diagnostics with it `On` only for a project that requested LTM). The overlay reaches a FRAGMENT through one shape only, a module instance's (the sub-model's layout, which carries its LTM section under `On`), so a fragment is keyed on it only where it resolves one: every caller of the fragment queries resolves its key through `db::var_fragment::fragment_overlay` over `fragment_reads_module`, and each constructor `debug_assert`s the predicate against the shapes it built, because an under-approximation would let an `On` assembly read module offsets resolved under `Off`.
- The describers see an element-scoped helper with every read its element pins spelled as the static index the COMPILER resolves it to (`FragmentInput::element_pinned_target`, `Context::pin_element_reads`: the helper's own fragment context running `normalize_subscript_ops` and `build_view_from_ops`), so the element graph and the scores name the slot the helper's fragment reads -- a proper subdimension, a shared-name axis or an element map included. Never substitute a spelling for that index: a qualified `dimension·element` of a foreign axis folds to an ordinal the compiler does not read.
- One correspondence describes every dimension-named read, plain or helper, subscripted or bare (`DimensionsContext::executed_read_correspondence`; `db::bare_axis_pairing` pairs the declared lists for a bare one, under the relations the spelling's own lowering consults -- `BareSpelling::Equation`, pass 0's `DirectMappingsOnly`, for a read in an equation body, `StockFlow`, the full context, for a stock's flows).
  - A frozen occurrence of a `PerElement` dependency keeps its subscript (`OtherDepVerdict`), since the bare spelling is a different read.
  - A reducer's bare argument that pairs with no axis of the iteration is `Wildcard`, the whole array, as `SUM(src[*])` is; the wildcard argument of a reducer the hoist declines is held live in its own edge's partial (`occurrence_realizes_shape`), the co-sources frozen around it.
  - The one executed read the describers leave undescribed is the ordinal fallback of an undeclared pair with disjoint element names at equal cardinality (GH #527); it is declined loudly, never described positionally.
- A generated equation's dependency shapes come from `ltm_dep_shape` (`model_dep_shape` plus LTM helpers and LTM synthetic variables), for a synthetic variable's fragment and a generated helper's alike, and its `Expr2` lowering runs under those shapes.
- The generated-text boundary is one place: the guard form a generator prints around its wrapped tree is parsed once, at the emitter (`LtmArm::new`); nothing upstream prints engine text to parse it again, and a helper carries no `Variable::eqn` (the generators read a target's axes off its `ast()`, keeping the `eqn` arm for user-authored source text).
- No silent wrong numbers in LTM: a link-score fragment that fails to compile is reported by `model_ltm_fragment_diagnostics` as a `Warning`, never silently stubbed to zero, and a target whose lowering failed or a read the describers cannot name is declined with a warning (`ltm_unified_tests::a_target_whose_lowering_failed_is_declined_not_scored`, `ltm_array_agg::a_per_element_slots_bare_reducer_argument_is_declined_not_scored`). Every LTM warning is a fact on the derivation's value (`LtmVariablesResult::diagnostics`, the fragment pass's `Vec<Diagnostic>`, `ShapedLinkScore::Unscoreable`'s payload) that `db::model_all_diagnostics` emits once per model, so a declined edge, a mode flip or a failed fragment in a sub-model is reported once however many parents instantiate it.
- LTM runs under Euler, RK2 and RK4 alike. A link score is a ratio of integration-step (dt) deltas reported at the saved steps: `PREVIOUS` reads the state the previous dt step ended in (the VM snapshots `prev_values` on every dt iteration, before the save/advance decision, so with save_step > dt a recorded score is the last dt step's ratio, not the saved interval's), and the VM and wasm both re-evaluate the flows at the restored end-of-step state before snapshotting it under RK, so the scores follow the method's own trajectory (`tests/integration/ltm_integration_method.rs`: a flow proportional to its stock scores identically under all three methods; a nonlinear one does not). Conveyor and queue models do not participate in LTM. Open LTM work is organized under the `ltm` label on GitHub (epic #488).

## Special stocks: conveyors and queues

A conveyor or queue stock is not compiled directly. `conveyor_compile::expand_conveyors` and `queue_compile::expand_queues` rewrite the datamodel into ordinary stocks, hidden container auxes, and driven flows, clearing the markers; the expanded project is synced into the db's second input slot and compiled incrementally like any other; `resolve_plans` binds the names to slots; and the VM runs the native per-step passes (`conveyor.rs`, `queue.rs`) between Flows and Stocks, interleaving a queue that feeds a discrete conveyor (`CouplingTable`). `compile_project_incremental` rejects a surviving marker: an internal error in the main model, `*InSubmodelUnsupported` elsewhere. The wasm backend lowers both passes as unrolled plan-specialized code (`wasmgen/belt.rs`, `wasmgen/passes.rs`) and shares the VM's error-message constructors so the two backends cannot drift. Integration is Euler-only.

## Data model and identifiers

- `datamodel.rs` -- the canonical serializable model: `Project`, `Model` (with optional `MacroSpec`), `Variable`, `Equation` (`Scalar`, `ApplyToAll`, `Arrayed` with an EXCEPT default), `Dimension` with `mappings`, views. `Project::default_model` is the one statement of the model a host runs when it names none: the model whose name is `main` (`canonical_model_name`, so `Main` and an unnamed model are it), else the first that is neither a macro nor a stdlib model. `Model.variables` and `StockFlow.elements` are `SharedVec`s, each element behind its own `Arc`, so a clone of a project (a host's undo copy) shares every variable and view element until one is edited. A `SharedVec` has no `iter_mut`, `IndexMut` or `&mut` iteration, so every mutation says what it touches and nothing unshares by accident: `get_mut`, `find_mut` and `replace` for one element, `edit_where` for the ones a predicate picks, `update` for a pass that can't tell beforehand what it changes (it reads each element and returns a replacement for the ones it changes, so it cannot change one and leave it out), and `rewrite` for a pass over a plain `Vec` that changes them all (imports, layout generation). No mutation's result depends on whether a copy shares the elements; `patch_sharing_tests.rs` holds every patch operation to that, and holds every patch operation and the conveyor and queue expansions to leaving each variable and view element they do not change in the allocation it was in (two models and three special-stock fixtures, one a driven flow already holding the placeholder `0`, in the default suite; the corpus for the patch operations in the gates).
  - `==` on the datamodel is "the same model", bit for bit: every float-bearing type compares its floats by their bits (`bitwise_eq!`, which destructures without `..` and refuses an unmarked float; `LinkShape` and `Dt` by hand), so every datamodel type is `Eq`, a value holding a NaN equals itself, and `0.0` is not `-0.0`. `SharedVec::share_identical` relies on it to put an old allocation back for an equal element of a view built afresh.
  - `Variable::expression_texts` (with `expression_texts_mut` and `map_expression_texts`, all three from one walk) is the one statement of where a variable holds text the engine parses as an expression: the equation's texts, an element's initial, `ACTIVE INITIAL`, and the conveyor and leak options. A pass over what a variable references (a rename, the special-stock scans) takes the texts from it.
  - `Model::map_variable_names` (over `Variable::names` and `ViewElement::names`, each from one walk) is the one statement of where a model holds a variable's name outside an expression, each under its `NameRole`: a variable's own name, a stock's flow lists, a module reference's ends, a spread inflow's distribution (a variable's name or a list of numbers, never an expression), a group's members, a macro's parameters and outputs, and a diagram element's label; a loop names its variables by uid. Both walks destructure without `..`, so a field added to a model, a variable or a view element fails to compile until it is listed as an expression, a name or neither.
  - A stock's `inflows`/`outflows` hold what the producer wrote, a repeat included; `distinct_stock_flows` is the one statement of how they are read (each flow once, at its first occurrence -- the engine's rule, unverified against Stella and Vensim). Every reader that decides what the model does takes the set through it before reading: the salsa sync (which records the repeats for the `RepeatedStockFlow` advisory), `queue_compile::build_compiled` before either expansion, the layout metadata, the MDL writer's `INTEG`, and the patch ops, which store the set. The order of a list is the modeler's and every patch operation keeps it: XMILE 1.0 section 4.2 makes it the inflows' priority and a queue's outflow priority, and the queue and conveyor passes read it (`patch_flow_order_tests.rs`).
- `variable.rs` -- the compiler's variable: `Variable { ident, units, eqn, diagnostics, kind }` over `VarKind::{ Stock { init_ast, inflows, outflows, non_negative }, Aux { ast, init_ast, tables, non_negative, is_flow, is_table_only }, Module { model_name, inputs } }`, generic over the module-input type (`ModuleReference` before lowering, `ModuleInput` after) and the expression tier (`Expr0` before, `Expr2` after). `Aux` covers auxiliaries and flows alike -- they lower identically, one slot per element holding one equation's value, and `is_flow` only says where a stock's integration reads it.
  - `diagnostics` is a LIVE channel, not diagnostics-in-waiting: the context-free `DiagnosticError`s the parse and the lowering raised, in order (a `Unit` entry is a malformed `<units>` string and is compiled past; everything else stops the variable, `Variable::fatal_diagnostics`), which the fragment constructors turn into `Diagnostic`s. `model::lower_variable` is a map over `kind`, so a transformation that only rewrites equations restates no field.
- `common.rs` -- `ErrorCode`, `Error`, `EquationError`, `Result`; the identifier types. An `EquationError` is `{start, end, code, details}`: the code names the CLASS of failure, the span points at the offending text (which `errors.rs` renders as a source snippet), and `details` carries the reason when it is not visible in the span -- the name that did not resolve, the arity a call missed, the reference whose dimensions did not fit. A parse error therefore writes no `details`: the snippet is its reason, and every Rust surface renders that snippet. A unit-definition error, whose units string has no equation to point into, adds that string to its reason, or to its code's description when it has none (`EquationError::in_context`), as in "the equation ends unexpectedly (in units 'kg/')". An `Error`'s `details` is likewise a complete phrase ("there is no model named 'x'", never a bare "x"), and an `Error` displays as `Error::reason`: its `details`, else `ErrorCode::description`, the plain-words meaning every code has. `ErrorCode`'s own `Display` is its snake_case name, for the terminal summaries.
  - Nothing between a raising site and `collect_all_diagnostics` drops the reason or puts something else in its place: `From<Error> for EquationError` carries `Error::details` across, the compiler's lowering entry points hand a rejection's `details` to the `Error` they build -- never its span, which is a byte offset into a string the user never sees -- and `UnitError::DefinitionError` wraps an `EquationError` rather than keeping a second reason field beside it.
  - `canonicalize` lowercases and normalizes a raw name; `Ident<Canonical>`, `CanonicalDimensionName`, and `CanonicalElementName` are interned, so clone is a refcount bump and equality is pointer equality. Sub-model variables are addressed as `module·var` (U+00B7).
  - `CanonicalElementName::from_subscript` / `from_parts` is the one owner of what a per-element subscript names (split on commas outside quotes, each part canonicalized, joined with `,`): every side of an element-arm match -- the arm keys, the declared-combination keys, the per-element gf tables, the conveyor init lists, the two arrayed-arm advisories, the readers -- goes through it. Never key one side by canonicalizing the whole subscript. `variable::elements_without_an_arm` is likewise the one owner of which declared elements have no arm (parsed arms plus per-element tables plus a live EXCEPT default).
- `diagnostic.rs` -- the one diagnostic payload. `DiagnosticError::{Equation(EquationError), Model(Error), Unit(UnitError), Assembly(String)}` is the typed error exactly as its raising site produced it, and `Diagnostic { model, variable, owner, severity, error }` is that error plus the context it is reported under -- the salsa accumulator, built at the salsa layer's raising sites (the fragment constructors, the per-model advisories, the unit pass, the LTM `ltm_warning`), where the model, the variable and the severity are known; a `Variable` carries only context-free errors and nothing between a site and the drain re-attaches context, so nothing asserts it.
  - `owner` is the variable a generated helper's row is presented under (the one it was synthesized for: a user variable, or for an LTM helper the synthetic link score); `variable` stays the helper's physical name.
  - Consumers read `code()`, `category()` (`DiagnosticCategory`: the four arms with `Unit` split by `UnitError`'s three), `location()`, `reason()` and `is(category, code)` rather than matching arms. The unit-inference umbrella is a `Unit(InferenceError)` filed under no variable, like every other unit diagnostic. When several arms of an arrayed equation fail to lower, the arm reported is the first in the dimensions' declared element order (`ast::lower_arrayed_arms`).
- `patch.rs` -- `ProjectPatch`/`ModelPatch` operations (upsert, delete, rename, views, stock flows, loop names, and `EditView`, a view edit whose model operations `editing::derived_operations` derives from the edited view when the patch applies; `is_view_only_patch` derives them to decide whether a patch needs recompiling).
  - A rename is syntactic: each expression text (`Variable::expression_texts`) is parsed as written (`Expr0::new`) to find its references, and each renamed reference is spliced into the text at its span, so everything else the modeler wrote comes back byte for byte. A text longer than a span addresses (`u16::MAX` bytes: `builtins::Loc` is a pair of `u16`s, and a position past them wraps) is respelled by `print_eqn` instead, decided on the text's length before any span is read. Neither compiler tier can serve a rename: the parse memo's tree is the expanded one (a `SMTH1(x, 3)` is already an instance read, a `PREVIOUS(x + 1)` a capture), and the lowered tree is absent for an equation the compiler refuses, which must still be renamed. The new name is spelled by `ast::print_ident` from its canonical form, so one holding a literal period is written quoted.
  - `patch::Rename` says what a name refers to. A reference names the variable bare in its own model and through a chain of module instances from a model that instantiates it, resolved as `db::DepScope::resolve` does (a spelling whose head is no instance, or an instance of a model the project lacks, is one local name); a module reference's `dst` names a port through the instance it starts at, whatever that instance instantiates. So a rename reaches the equations, module `src`/`dst` and stock flow lists of every model that can name the variable, and every other place a model holds the name (`Model::map_variable_names`) but a diagram's labels: every view's label keeps the old name until a view edit or a diagram sync that carries the patch relabels it.
  - A rename never decides what an identifier inside a subscript's brackets names, because the compiler has no single statement of it: the dependency walk skips a dimension or an element of any dimension (`variable::ClassifyVisitor::is_dimension_or_element`), a static subscript reads an element of its axis (`compiler::subscript`, `resolve_axis_index_name`), a range reads its ends as elements only when both are, and a dimension's name is the active axis's element where an axis supplies it and the like-named variable where none does (`compiler::Context::lower_from_expr3`). Unifying that rule is the compiler's work; until it is one rule, a rename that would have to choose is refused, changing nothing (`patch::Reader`): when the old or the new name is a dimension's (XMILE 1.0 section 3.7.1 requires dimension names to differ from variable names), when the variable is written alone in a subscript (or at an end of a range there) and its old or new name is an element of a dimension, and when a reference's new spelling is a `dimension·element`. Never replace the refusal with a reading of the brackets: a second resolver of one spelling drifts exactly where the rule is non-trivial, and this one has three.
  - A rename refuses a new name that contains `"`, which has no spelling. It does not give a variable the name of one of the run's clock slots (`db::IMPLICIT_GLOBALS`, asked through `db::is_implicit_global`: the time, the time step, the initial and the final time): a variable of that name takes the slot's results key, where hosts read the clock, so the rule is deliberately stricter than the compiler, which resolves the quoted name. A model that already declares one keeps it, its display spelling included, and renaming it away respells its quoted references and leaves the bare words, which are the builtin. Another builtin's name (`pi`) is not refused: the printer quotes it.
  - The standing test of a rename is the run: it is refused and changes nothing, or the model computes after it what it computed before (`patch_rename_tests.rs`, on fixtures that name every refusal in the default suite, and on a corpus sample in the gates, which holds no name the subscript rule refuses). A delete unwires every module reference either end of which starts at the deleted variable, in any spelling: at its first segment when that is a module instance, else at the whole spelling, which is one local name. `SetSimSpecs` sets the project's specs and takes the root model's own away (`Project::default_model`), so the project's are what the root model runs under; another model's own specs stay.
- `results.rs` -- `Results` (offsets plus step-major series; `step_count` is the rows a run saved, each a step it evaluated) and `Specs`, the one statement of the step grid (pipeline stage 6): which steps a run takes, the time of each, and which of them it saves. `Results::print_tsv` prints one column per key of the results-offset map, in slot order; a slot the map has no key for is not printed.
- `errors.rs` -- `FormattedError`/`FormattedErrors`, the ONE presentation adapter over a `Diagnostic`, shared by the CLI, libsimlin and the MCP servers. The severity word comes from the diagnostic's severity, `variable_name` is the presented variable (a helper's `owner`, else `variable`), `category` is the diagnostic's (libsimlin derives `SimlinUnitErrorKind` from it), and `details` is `Diagnostic::reason` -- an inference error's rewritten to plain language, `ErrorCode::description` when there is none, so it is always present -- handed to the FFI as `SimlinErrorDetail::details` for consumers that render the variable themselves. `message`'s summary line joins the code's name to the raising site's reason (`code -- reason`) in every arm, for terminals and language-model clients.

## Formats

- `compat.rs` is the top-level entry: `open_xmile`, `open_vensim`, `open_vensim_with_data`, `open_systems`, `to_xmile`, `to_mdl`, `to_systems`. `open_xmile_with_warnings` and `open_vensim_with_warnings` open the same project and also return an `ImportWarning` for each kind of thing the file holds that the project does not keep (`import_losses.rs` holds the type and the wording both readers share: `29 comments on view 'View 1' are not kept, such as ...`).
- `save_check.rs` (`check_save`, `check_save_with_data` for a project opened with a data provider, which the MDL read-back reuses) says whether saving a project in a format keeps what its model means: the project is saved, the save read back, and the two compared, reporting a change whenever it cannot be sure there is none. The structure is the definition, compared whether or not the model runs: specs (the project's and each model's own), each dimension's elements (numbered or named), parent and mappings, and each variable's kind, dimensions, elements, per-element equations, applied `:EXCEPT:` default, whether it is a table alone (`variable::is_lookup_only`, the compiler's own verdict), initial values, graphical functions as the compiler reads them, flows, module inputs and the markings that change a simulation, each with what it carries. The walk is exhaustive by construction: every `datamodel` type it reads is destructured with no `..`, a field that is no part of the meaning named with the reason, and `save_check_field_tests.rs` rows every field (an edit to it, and the reason the check gives or none). Equations are the same when their `ast::CanonicalEqn`s under `Aliases::Engine` are. Behaviour compares every variable's series value for value (-0 is 0) when the project simulates, and the errors when it does not; it sees only the run the specs ask for. Each `MeaningChange` has a `ChangeKind`: `Results` when the save's results differ, `Structure` when only the definition does; a non-negative marking only one side's stock or flow has is `Results` wherever there are results, because the engine does not enforce the marking and so no run of it shows whether the marking binds (an auxiliary's marking means nothing to the compiler and is not compared). The run reads a results column as a variable's through `save_check::column_variable` (the whole column first, so a name may hold `$`, `[` or `·`; a compiler helper by `ltm::SYNTHETIC_NODE_PREFIX`, the prefix `capture::synthetic_ident` spells), which the corpus gate and the agent tools' edit gate ask too. Variables pair by canonical ident exactly. Units, documentation and views are not meaning, and a control variable a format keeps as the specs, with the same value, is no change. The check reads the save back with this engine's reader, so a writer and a reader that agree with each other and not with the format's own tool are a fixed point it cannot see through. `tests/integration/save_meaning.rs` holds it to the corpus in every pair of formats (read as MDL or XMILE; saved as MDL, XMILE, native JSON, protobuf): one table lists every save that does not keep its model, with the check's verdict and the cause (the format cannot hold it, or a defect), ratcheted both ways, and an independent run comparison holds the check to calling every save whose series differ a change to the results. The whole-corpus sweep is a gate (ignored; C-LEARN included); a few models that make every pair run in the default suite against the same table.
- `xmile/` reads and writes XMILE with `simlin:` vendor extensions for element mappings, data sources, EXCEPT metadata, and multi-output macro invocations. Two contracts the XMILE writer keeps: every attribute it emits goes through `push_attribute`, and a newline inside a name is spelled as the two-character XMILE escape `\n` (the datamodel's stored form, which Stella also writes), never a raw newline -- XML attribute normalization would read one back as a space; only the free-text attributes decode the escape (`decode_free_text_attribute`). `xmile/views.rs` is the one place the view `zoom` changes unit: XMILE stores a percentage, while the datamodel, protobuf, JSON, and TypeScript all carry a factor (1.0 = 100%); `zoom_factor_from_xmile_percent`/`xmile_percent_from_zoom_factor` convert, reading Stella's `zoom="0"` as 1.0. `xmile/unread.rs` reports what a file holds that the reader skips, as a pass of its own over the file's XML events that `project_from_reader_with_warnings` runs after the ordinary read: the read is untouched, so a report can neither change the project nor fail the open. It also reports what the reader reads as something other than the file says: a graphical function whose `type` names no kind the reader knows (the kinds are matched whatever their case, `GraphicalFunctionKind::from_type_attribute`) opens as the default kind, never as a failed open, and is reported there with its variable, as is a draft-format `discrete="true"`, which the reader does not act on; each warning says the kind the function is read as (the default, or the one its `type` names). It looks wherever the reader reads a `<gf>` -- a flow's or an auxiliary's own (`OWN_TABLE`), any variable's `<element>` (`ELEMENT_TABLES`), in a model or a `<macro>` body -- and `unread_tests` derives its rows from what the reader reads, so the two lists cannot drift from it. The pass holds no recursion, reads only as deep into an unread element as a label needs (`LABEL_DEPTH`), and leaves out of a label whatever does not unescape, so ill-formed or deeply nested content the read skips is counted without examples.
- `mdl/` is the native Vensim parser and writer (`lexer` -> `normalizer` -> `parser` -> `reader`, `mdl/convert/`, `mdl/view/`, `writer.rs`); `mdl/xmile_compat.rs` formats expressions, and its restructuring arms for builtin-named calls run before macro resolution, so a like-named macro cannot shadow them. `vdf.rs` and `vdf/` read Vensim binary data files; the readers are total on arbitrary bytes.
- `serde.rs` maps the datamodel to and from `project_io.proto`, the form the web app's database stores, so the schema only ever gains fields and an absent field reads as the project read without it. `serde_proptest.rs` holds the format to keeping a project: `deserialize(serialize(p)) == normalize(p)` on the FIRST trip, over generated `datamodel::Project`s and over what the importers produce from the corpus, where `normalize` is the one list of what protobuf does not keep (variable order, a proto3 zero read as "none", an element subscript's display spelling, and ISEE's AI information, which is outside the engine's scope and has no field in the schema). A period in an ident field is rewritten on read (`migrate_stored_ident`, GH #690), so the generators write none and the corpus gate lists the one file it reaches. `serde_stored_tests.rs` holds the two rules of the schema to stored projects, the stand-ins for the database's rows (`test/protobuf-compat/`, each `.pb` beside the `Debug` form of the project it reads to): a field's number and type never change, since every field the schema defines is on the wire of some stored project (the test reads `project_io.proto` and walks the stored bytes, so a field added to the schema fails until a stored project carries it), and a field a stored project lacks reads as before. The `.pb` files are never rewritten -- bytes a current writer produces pin nothing about reading old ones -- and the test holds each to its SHA-256. `deserialize` returns a `ProtobufDecode` error, with what is missing and where, for a message that lacks what every writer writes and the reader has no reading for: the project's sim specs, a variable's kind or equation, an equation's kind, a view element's kind, a table's scales (an empty buffer decodes to such a message).
- `systems/` is the line-oriented systems format. `data_provider/` resolves `GET DIRECT` references (`FilesystemDataProvider` behind `file_io`). `json.rs` and `json_sdai.rs` are the JSON schemas.

## Units

Opt-in: a model that declares units on no variable gets no unit diagnostics. `units.rs` parses unit strings into `UnitMap`s and builds the `Context` (XMILE built-ins plus Vensim synonym groups, dropping a built-in the model redefines; of the sim specs it holds the time units and nothing else, so a parse keyed on it is not re-run by an edit of a run's start, stop, DT, save step or method); `units_infer.rs` is Hindley-Milner-style inference over the free abelian group, partial-result throughout (a conflict is confined to its connected component; macro bodies' parameter-named units lower to per-instantiation metavariables); `units_check.rs` checks each equation against declared-or-inferred units, with literal-polymorphic `MAX`/`MIN`/`PREVIOUS`/`IF` and integer-literal exponent rules. Vensim's unit semantics are cited per rule; an unverified one is marked unverified. `db/units.rs` is the salsa pass: inference and checking read one `Ast<Expr2>` per variable, the same lowering memo the fragment compiler borrows, through a `units_check::UnitModel` built on the stack per scope model.

## Analysis, layout, diagrams

- `analysis.rs::analyze_model` bundles compilation, LTM discovery, and dominant-period selection into `ModelAnalysis`; a model that cannot compile returns `Ok` with `analysis_error` set so "could not analyze" is distinct from "no loops". Its discovery step is `discover_run_loops`, which a caller with its own run under the LTM overlay in discovery mode (a what-if value, a staged equation) calls on that run's results.
- `analysis.rs::model_links` is the one owner of a model's causal links: the unique edges of `model_causal_edges` with their static polarity, macro and module internals collapsed into the links between the variables a modeler wrote (`ltm_finding::collapse_synthetic_links`) unless asked for the raw graph, and, given a run's `Results`, each link's LTM score and relative score. libsimlin's model- and sim-level link queries, its wasm-results twin and the agent tools all read it, so the structural and scored link sets cannot drift apart. The list is in `(from, to)` name order, the order of `CausalEdgesResult::edges`, an ordered map.
- `layout/` generates and incrementally updates diagram layouts (force-directed placement, crossing reduction, a calibrated quality metric; deterministic per seed). The metric and the eval harness that measures layouts against it are described in [layout quality](/docs/design/layout-quality.md). The incremental path lives in `layout/incremental.rs`: chains an edit adds whole are laid out as chains beside the diagram, a new stock hung off a drawn chain continues its row, and what the edit added is decluttered around the fixed diagram (`declutter::declutter_part`). Incremental layout never rewrites an element the patch did not touch: position and `label_side` come back byte for byte (`layout_label_tests.rs` enumerates the arms), a label side is chosen only for elements created in that pass, and a new connector that runs through an existing label is accepted rather than re-optimizing its neighbours -- hand placement wins, and re-optimizing is exactly the churn that snaps a notebook user's dragged label somewhere else on the next edit. A dependency the view does not draw gets a connector only where the edit is about it -- into a variable the patch names (upserts, renames, re-lists), or where an end is drawn for the first time -- so a connector an author left out stays out whatever unrelated edit follows; likewise a link drawing no dependency the model has goes only with an edit to its reader, and a variable the view does not draw is drawn only when the patch names it. A connector or cloud the pass creates references only what the view draws: a variable left out of the view can still have a uid (a project MCP opened gives every variable one), and a link into it or a cloud of it would name no element. An element the pass rebuilds -- a variable whose kind changed, a flow whose attachment changed -- keeps its uid (`LayoutState::remove_for_rebuild`), so the links and aliases touching it survive, and a surviving curved link whose endpoint moved turns its takeoff with its chord (`rebow_moved_links`); a variable that became a stock, aux or module is redrawn at its old center and no polish pass moves it, save that one whose new, larger shape covers another shape there (a parameter turned into a stock) moves to the nearest clear spot. A label the layout wraps carries the stored two-character `\n` escape (`text::LABEL_LINE_BREAK`, the form the TypeScript editor's `encodeNameNewlines` produces), never a raw newline.
- The flow arm of that rule (`layout_flow_tests.rs` enumerates it): incremental layout rebuilds a flow only when the patch creates it or changes the flow's own attachment -- moves it to another stock, drops it from a stock's list (that end becomes a cloud), lists it on a stock at its cloud end (that end becomes the stock), deletes an attached stock, or changes an attached stock's kind -- because its stored endpoints then name the wrong element. A drawn flow whose attachment changed is re-attached in place through the editing core (`retarget_flow`, over `editing::{heal, route, route_end}`): an end that becomes a cloud stays where it was, moved off a stock it no longer attaches to (`clear_of_stocks`), an end that attaches to another stock is routed to it keeping as much of the pipe as stays valid, and the flow keeps its uid, name and valve; only a flow that must attach to a stock this pass creates is rebuilt as new. A flow the patch names keeps its geometry (a rename changes only its name, a delete removes it with its clouds), and every other flow, a sibling of a flow added to or removed from the same stock included, comes back byte for byte even where a fresh layout would draw it differently. A created side flow takes a face its stock's drawn side flows leave free where there is one. The endpoint snap (`resnap_flow_endpoints`), the slot placement (`face_slots`: a created flow's stock end keeps the design plan's `PIPE_SPACING` from the ends already on its face where the face has room, else the farthest slot, always within the corner clearance; a two-point flow between parallel faces takes one line only where that line keeps the spacing on both faces; a created cloud end keeps off other clouds) and the finishing pass (`finish_flow_geometry`) run only on the flows the pass creates. The one repair made to an untouched flow is wiring an endpoint the view left unattached to the flow's own cloud (`diff_clouds`), which moves nothing.
- What a sync after an edit must do is stated independently of `incremental.rs` by `layout/edit_audit.rs` (scope: untouched elements and surviving links come back as they were; consistency: the view agrees with the model and routed flows hold the strict invariants, charging only what the edit introduced; placement: created elements land on no shape and routed pipes through no foreign stock), and `layout/edit_scenarios.rs` generates the edits an agent makes for any model and drives them through `apply_patch` and the production sync rule. The battery (`edit_scenarios_tests.rs`) pins every finding in `KNOWN_DEFECTS`, each row naming its defect: a new finding fails, and so does a row that stops reproducing, so a fix deletes its rows. Element order is the view's draw order and what a saved file lists: a sync keeps surviving links and clouds in place and appends what it creates in a deterministic order.
- `diagram/` renders a model's first stock-and-flow view as SVG (`render_svg`, byte-identical to the TypeScript static renderer; `src/diagram/tests/svg-rendering.test.ts` is that parity test), as PNG (`render_png`, behind `png_render`), and as a scene display list (`build_scene`, whose contract is [the diagram scene](/docs/design/diagram-scene.md)), and exposes the exact geometry the layout metric scores. Every drawing decision has one owner, and both serializers read it:
  - `resolve::resolve_view` decides which elements are drawn (a link or flow whose endpoints are missing from the view is not), their layer and draw order, whether each is arrayed, an alias's target, and the fit-to-content bounds.
  - Each element's geometry is one function: `aux_geometry`, `stock_geometry`, `module_geometry`, `alias_geometry`, `group_geometry`, `cloud_transform` (over the shared `CLOUD_PATH`), `flow_geometry`, `connector_geometry`, `arrowhead_geometry`, and `label::label_lines` for per-line label anchors. `render_*` prints from it and `scene.rs` reads it. Never compute a drawn number a second time in either serializer: a hand-maintained twin drifts exactly where the geometry is non-trivial; extend the geometry function instead.
  - The scene changes representation only: `path::PathBuilder::svg_arc_to` converts every SVG arc to cubic Béziers (SVG 1.1 F.6.5 and F.6.6, at most 30 degrees per cubic, so a cubic stays within 1e-6 of its radius), and transforms are applied to the points. `scene_tests.rs` checks each scene number against the number the SVG prints for the same project.

## Diagram editing

`editing/` is the editing core native hosts plan through ([design plan](/docs/design-plans/2026-09-12-editing-core-in-rust.md); the invariants G1-G8, M1-M3 and E1-E6 are [the TypeScript core's](/docs/design-plans/2026-09-10-diagram-editing-core.md)). It is tuned for touch and deliberately differs from the TypeScript planner where that planner follows from pointer-and-keyboard input; no test holds the two together.

- Flow geometry: `geometry.rs` (the G1-G8 constants, which `diagram::flow_geometry` reads too), `terminal.rs` (face attachment and terminals), `route.rs` (`route`/`route_end` over obstacles queried by region), `offset.rs`, `heal.rs`, `path.rs`, `validity.rs`.
- Planning: `base.rs` (`BaseView`, the index a tap or a drag plans against, built once), `hit.rs` (`HitIndex`, a view indexed for hit testing: every drawn element's shapes, end handles and label box computed once, and a grid of the boxes each element reaches over; an entry holds a part only where the scene draws its shape, asked of the scene's own builders and the predicates `scene::finish` filters with (`SceneShape::is_finite`, `SceneLabel::is_finite`), never of a finiteness check of its own; `hit_test` builds one for a single call; decided in tiers: a firmly held body, an end handle, a firmly held label, the nearest drawing), `gesture.rs` (`plan_tap`, `begin_drag`, `GestureSession::frame`, `plan_move`, the move-selection frame at an offset, which a drag's frame calls and a keyboard nudge plans without a session, `Plan::edit`; every edit is planned through `Changes::into_plan`, which plans nothing where the changes equal the base and commits nothing where a changed element holds a non-finite number, which the scene would draw nothing for, so a frame, its release and a nudge agree on what lands; a drop target is valid exactly where the drop is allowed (`Changes::into_drop`), so an allowed drop that changes nothing keeps its valid target and commits nothing), `links.rs` (links following moved endpoints), `preview.rs` (a frame's scene elements, through `diagram::scene`'s one element serializer), `edit_view.rs` (`plan_delete`, `plan_rename`, `derived_operations`).
- A frame allocates in proportion to what its gesture changes, never to the size of the view.
- A hit costs in proportion to what is near the point, never to the size of the view. The tiers walk the elements from the topmost down, and an element offering a point nothing changes nothing in that walk, so walking only the elements with a box within reach decides what walking every element decides; that equality is the grid's one claim, and `hit_prune_tests.rs` checks it (both walks, and the rule that decided, over generated scenes and World3).
- Tests: `invariants.rs` is the one oracle, every arm enumerated (`FlowArm::ALL`); `scene_gen.rs` generates scenes with its own geometry, never the checker's or the core's; every decision table derives its rows from its enum (`HitPart::ALL`, `GestureKind::ALL`, the no-drag arms of `begin_drag`, the kinds of view element a nudge moves), and a commit is checked by applying it through the production patch path.

## Agent tools

`tools/` is the agent tool surface ([design plan](/docs/design-plans/2026-09-20-agent-tool-surface.md)): the tools an agent uses to read a model, stated once so every host that mounts them answers alike. It is behind the `agent_tools` feature (default on; libsimlin's browser bundle leaves it out). libsimlin mounts them for native hosts (`simlin_tool_session_*`); the plan's hosts phase mounts them in the MCP servers and pysimlin.

- `tools::Session` is one agent's work on one model: `call(Workspace, tool, input_json)` answers a tool with JSON (`ToolOutput`, whose `is_error` marks a refusal for the agent to read and repair; only a tool the catalog does not list is an `Err`). A `Workspace` is the project, the db synced to it with `SimlinDb::sync`, the host's revision, which must be equal exactly when the contents are, and `waiting`, how the host says other work waits for the project: a call checks it between units of its work (`Workspace::yield_point`) and stops with a refusal marked `interrupted` that kept nothing. `cancelled` is how the host says it cancelled the call: `call`, `run_results` and `land_plan` fold it into the checkpoints' `waiting` (`checkpointed`), and a call a cancel stopped answers a refusal marked `cancelled` (`ToolOutput::cancelled`), which no host retries. `changes_since_read` is what changed since the session's last `read_model`, leaving out what one of the session's own plans left (the agent's work, once a host lands it).
- `catalog.rs` owns the tool list (`ToolName::ALL`, names, descriptions, effects). The input and output schemas are derived from the serde types with schemars (inputs under the deserialize contract, outputs under the serialize contract, so a field an output skips when empty is optional) and checked in as `catalog.json`, which `catalog_json` embeds so builds without `schema` carry no schemars code; `tool_catalog_matches_the_checked_in_file` fails when it is stale and `UPDATE_TOOL_CATALOG=1` rewrites it. Inputs are `deny_unknown_fields`.
- One owner per decision: `names` resolves a name (canonically, else by word similarity over names and documentation, stop words dropped from queries only) and ranks candidates; `evidence` gives diagnostics and loops ids stable for the session's life (a diagnostic keyed by variable, severity, code and the engine's own reason, never by span, so an edit that moves a problem keeps its id; a loop by its cycle's canonical rotation, builtin and macro internals left out, so a loop has one id in every run, at every revision, from a run or from structure); `changes` diffs variable records (a case-only rename is a change of `name`), sim specs, the project's dimensions and unit definitions, and its other models' variables against the last read (views excluded: a layout edit changes nothing an agent read); links come from `analysis::model_links`.
- Every answer keeps to the session's byte budget (`OUTLINE_BUDGET`), fitted, with what it leaves out counted or named. `outline.rs` (`read_model`) lists diagnostics errors first and fits them by bytes, keeping every entry when the entries fit alone, else outlines by sector (stocks, then diagnostics, then names); `variables.rs` has `read_variables` (a variable or one element of one, `names::split_subscript`/`resolve_element`; per-record caps, then whole records named in `omitted`) and `find_variables`. `evidence::window` cuts a quoted equation to 240 characters around its span.
- Runs: `runs.rs` holds a run's `RunPlan` (values from a time, replacement equations, specs), the session's `RunStore` and `execute`. Values and specs are VM overrides (`Vm::with_specs`: the compiled program does not depend on the specs), so a plan of them compiles nothing and touches no salsa input; a replacement equation -- or a spec change on a conveyor or queue model, whose expansion reads the specs -- stages a copy on the host's db (`Staging`, a guard that restores on drop, as a dry-run patch does), so the project never changes. A run is fresh while `db::simulation_key` (the salsa sync's extraction of what the compiler reads, less units; memoized per revision) is what it ran at, so a layout, notes or units edit stales nothing; the store keeps the current run per key, at most `MAX_RUNS` named runs in the order they were made, and at most `MAX_RUN_BYTES` of results and loop analyses (the oldest keep their plans, in their places, and run again while fresh). One run's cost is held to `MAX_RUN_VALUES` saved numbers and `MAX_RUN_STEPS` slot-steps, or the model's own when that is more (`over_budget`, checked before the VM allocates). `Session::runs` and the agent's `list_runs` list each run's plan exactly as it ran (`RunListing`: from, changes, specs), and `Session::forget_run` forgets one the person discards. `execute_then` compiles under an overlay and hands the caller the db while it still holds the staged project, for an analysis that reads the run's structure. A value from `t` holds from the first step at or after `t` under every integration method: the run is taken to that step with `Vm::run_until` and the value set before the step is evaluated. A plan over another (`RunPlan::over`) is a timeline per variable: a change from the start replaces every change the base made to that variable, and a value from a time replaces only the base's changes from that time or later. A run is taken in `RUN_SLICES` slices of its steps, counted as the VM counts them (`Vm::run_until_step`), so a run whose clock's last place is coarser than its DT still ends, and stops between two slices when the workspace says other work waits (`RunFailure::Stopped`, which a tool answers as the stop). A replacement equation drops the variable's table (`replace_equation`). `experiment.rs` is `run_experiment`, which resolves a multiplier to a value against the starting run when it is made, and refuses a value from a time on a variable the starting run gave an equation that is not a number (the time goes into the equation); `series.rs` summarizes a series (`SeriesCore`, rounded as decimals to five significant digits, with any number that is not finite left out) and is `read_behavior` (one element by name; fitted to the budget: samples, then turns, then elements, then variables). Every number a summary reports is the series' own, rounded, so every tool reports the same one, and its parts agree: a series that is not at rest reports extremes that read differently, and it went negative exactly when a number reported of it is negative. Every tool reads a series at the scale of what it is computed from in the run (`series::scale_in_run`, per results key, so each element at its own, and from the run's own equations, its plan's replacements applied by `runs::apply_equations`: a stock's flows over the horizon, the terms of an equation that is a sum; an experiment's two runs share the larger of their magnitudes, each read at its own equations' scale), so arithmetic residue of quantities that cancel is at rest, while a real change of more than 64 units of `f64::EPSILON` of that scale (a part in 7e13 of it), and a model whose quantities are all tiny, are read as they move. Residue that reaches a series through anything but a sum (a quotient feeding a stock, `SMTH1`, `MAX`) is read as it moves; a stock's flow counts at its own scale as a sum, one level back.
- `loops.rs` is `analyze_loops`. A run is made without the LTM overlay; its loops are analyzed on demand by replaying its plan under the overlay with the project in discovery mode (set by the `DiscoveryMode` guard, which sets it back on drop, a panic included) and running `analysis::discover_run_loops`, and the analysis is kept on the `Run`, which a layout edit leaves fresh. It stops before each stage -- the replay, the discovery over its results, the loops from structure -- when the workspace says other work waits. The answer is per cycle partition: a dominance timeline of 12 windows merged while the same loop is strongest (each span names the strongest loop and its rivals, those with half its share), each boundary between two leaders moved to the step the new one overtakes from, and the loops the timeline names plus the most important others. A chain starts at a stock, leaves builtin and macro internals out (their links composed), and signs a link by the run when the run scored it (`LoopPolarity::from_runtime_scores`, unknown when its sign changed; a link discovery stitched across an aggregate node by the path score through it, `LinkScores`) and by its equation otherwise; a loop over `MAX_CHAIN` variables is given by its stocks, and whole by id (`loops`). `through` takes a variable or one element. A run with no active loop, or whose stocks are at rest (`behavior::classify_at`, each at its scale in the run), falls back to the structural loops (`db::model_detected_loops` with discovery mode off, when `model_ltm_mode` says the structure alone enumerates them), says which, and says how to disturb it. A plan that replaces equations reports the links it removed and the model's loops through them. The answer is fitted to the session's budget by leaving out a partition's lesser loops, then partitions, then rivals, before ids are given (the fit runs on a copy of the evidence); loops by id come whole, the last asked for left out (`leftOut`) when they do not all fit.
- `battery.rs` is `run_tests`, the validation battery: units (skipped, saying so, for a model that declares none), extreme conditions, integration error, sensitivity, loop knockouts and disturbances, each a set of checks (one changed run each) under ids keyed by test, target and condition, shared between the tests in turn and fitted to the budget, ids given only to what is listed; what the default targets leave out (unit conversions; dates, for the tests that scale a constant) is said once (`leftOut`). `Roles` classifies the constants once: unit conversions (value one of its units: a ratio of one unit at two scales, a ratio of two units of time at their known ratio within `TIME_RATIO_TOLERANCE`, or one unit its name states, by any name the project reads as it), shares (high extreme the whole), dates (compared with `TIME` or given to `STEP`/`RAMP`/`PULSE` as a time, directly or through a carrier auxiliary; extremes the run's start and past its stop), divisors (low extreme a tenth), fractional rates (high extreme at most one over two DTs), and `time_constants` (low extreme a tenth and at least `DTS_PER_STAGE` DTs a stage, DT in the constant's own unit; a delay's time from the engine's stdlib tables, `TIME_PORT`; with units, a unit of time; without, or declared dimensionless in a rate that carries a unit warning, by its role in a rate on equations `normalized` so a power of -1 reads as a division; each says why, `TimeConstantEvidence`, and whether it paces a stock). A call's `extremes` replace the rules' for a constant (one entry a constant; a second is refused); each extreme check says its rule (`ExtremeRule`), and a sensitivity check held at one says which (`heldAt`). A problem an extreme finds as the run goes is confirmed at a tenth of DT, at most `MAX_CONFIRMATIONS` a call. Below zero is judged per element, for stocks and for series marked non-negative, where the model's own run keeps the element at or above zero (a stock with any element below zero there is signed and not judged), by more than `behavior::residue_bound` at its scale; a check says what went below zero, never why. The model's own run is a check of its own, listed first: series not a number in it (judged by no other check), and marked series below zero, with a note that the engine does not enforce the marking. A model that does not simulate says so once (`runFails`) and every test is skipped; extreme conditions and integration error are skipped for a model with no top-level stocks (a module model's are not read yet), and the tests that compare recorded variables when none are recorded. Integration error is one measurement, the runs at half and a quarter DT saved at the model's own times (`finer_specs`, which asks `results::save_step_is_on_the_step_grid`, rows matched by time, `rows_at`): Richardson's estimate and the observed order (given only where the runs converge), passed at or under `INTEGRATION_TOLERANCE`, flagged up to `INTEGRATION_FAILURE` and failed above it, naming the shortest time constant that paces a stock (a literal one written into a rate included), flagged where the runs do not converge or an equation reads DT. Sensitivity reads each run at its own scale with the two series' magnitudes shared (`series::compared_scales`, the one owner, which `run_experiment` uses too; a series not a number somewhere shares none) and is flagged when a behavior changes family (`BehaviorFamily::of`, the classifier's mode with pace set aside), the series' turns at `MATERIAL_CHANGE` of its range change too, and the series' own range is material in one of the runs; a response shows the classifier's damping where the series oscillates (`damping`, `wasDamping`). It is not run again at a finer DT. Checks that flag the same change of the same series are listed once, naming the others (`same_changes_folded`, `sameChange`); a check, knockout or disturbance whose run makes a recorded series undefined is flagged; a check lists at most three responses and counts the rest (`moreChanges`); a difference within the residue of the series' shared scale is no change, and a series the model's run holds at zero is measured by that scale. Knockouts hold every element of an arrayed variable at its own start (`runs::Replacement::Elements`). Value-only checks run through `runs::execute_values`: one compile, a VM each, in parallel off wasm, at most `runs::concurrent_runs` at once (`MAX_BATCH_BYTES` of results; a test lowers it with `TEST_BATCH_BYTES` and counts the runs in flight), each summarized inside the map, none started once the workspace says other work waits. A call that stops restores the session's evidence, so it gives out no id. `battery_corpus.json` labels every check the battery lists over 29 corpus models (accepted or not, and why); an ignored gate holds the battery to it and to the model count, and three small models do so in the default suite.
- `edit.rs` is `edit_model`: operations applied in order to a copy of the project (`Builder`), refused when anything they write -- a variable, the sim specs, a loop name -- changed since the session's last `read_model` (provenance aside, `changes::same_record`; unless one of the session's own plans left it so: `Expected`, `AsRead`), placed by the incremental layout (an element `EditView` when it implies no model operation, else the whole view), and gated on the staged db (`gate`, staged under `runs::Staging` and stopping between its stages when the workspace says other work waits; `Gate::refusal`: an error the model did not have, by code and variable mapped through renames; specs whose run costs more than a run may, `runs::over_budget` against the model's own; a model that simulated and no longer does; a value that becomes non-finite; a unit-clean model's first unit warning; every new warning listed). In a project that records provenance, what the edit adds or edits is marked (`after_ai_edit`, ISEE's AI information). A plan that passes is kept under an id with its operations, engine patch, lines and what it writes before and after (`Plan`, `Written`); `land_plan` (`Session::land_plan`) lands it by construction: its patch at its revision, else its operations planned again on the contents as they are, fresh against what the plan was made on (`AsPlanned`), gated again, and with the lines the person approved. The output's lines are fitted to the budget.
- `verify.rs` is `verify_findings`: each citation of a finding checked against the session at the current revision (runs made before the model changed, diagrams aside, are not evidence), a failure saying what is true instead, a finding every citation of which holds given an id keyed by its claim. An `equation` citation compares parsed equations in a normal form (`normal`: spacing, case and name spelling aside); `value`, `ends_near` and `compares` judge a number against the actual one (`near`: 5% of the larger of the two, or, for values near zero, `VALUE_FLOOR`, the summary's precision, of the series' largest magnitude), and a cited time outside the run is refused; a table variable's equation is its table at its input (`LOOKUP(name, input)`); a series at rest has no peak; `readers` is the exact set of what the variable links to. A cited battery check answers from the session's check log while the revision is the one it ran at, and is run again (`battery::recheck`) after an edit; loop citations read the run's loop analysis (`loops::leadership`, `loops_through`, `polarity_of`, and `through_of` for an element). It stops after the citation during which other work began to wait, giving out no id.
- `behavior.rs` is the one statement of a behavior mode (`classify`, and `classify_at` for a caller that knows the scale): at rest, linear, exponential, goal seeking, S-shaped, overshoot, rise and fall, fall and rise, oscillation (damped, sustained, growing), undefined, other. It reads a series against its saved times, so unevenly saved rows read as the curve they sample where they resolve it, and every threshold is a fraction of the series' own range or magnitude, so a mode is the same at any scale, offset, direction and unit of time. At rest is a range under one unit of the last digit a summary reports, or a series that never leaves zero by more than the rounding floating point leaves at the scale its caller reads it at (`RESIDUE_EPSILONS`, 64, units of `f64::EPSILON` of that scale; a stock's scale already counts the run's horizon, so its steps are not counted again); there is no fixed floor, since residue and a tiny model are the same numbers and only the caller knows which. After trimming a still start and a settled end (each reported past a twentieth of the run; a share of the run is past a threshold only by more than a millionth, `past_share`, so a tie that evenly saved rows make reads alike on every clock), turning points are reversals over 1% of the range (`Shape::turns`, what a summary lists), and the mode is named for the large movements: reversals over a tenth of the range, less a first or last one under a quarter of the movement beside it and no longer than a quarter of the run (the run starting up or being cut off). No such turn is one movement, read from where a start-up transient ends, an overshoot when it ends short of its furthest by its largest reversal, else named by where it runs against its chord (along it, below it, above it, below then above); one is an overshoot, a rise and fall or a fall and rise; more are an oscillation, its damping the last swing against the first (with one whole swing, the movement after it is a second swing where it ends at a turning point, else the run cut it off). `behavior_tests.rs` holds the classifier to series from World3, C-LEARN and two small models labeled as a modeler names them (`behavior_real_series.tsv` in the default suite, a wider set and the file's fidelity to the models in an ignored gate), agreeing except where `KNOWN_DISAGREEMENTS` lists what it says instead and why (a late inflection reads as exponential; reversals over a tenth of the range make an oscillation of a growth curve), a table that fails when a listed row starts agreeing, to curves generated for each mode across parameters, densities, scales and clocks (a sample in the default suite, the full sweep an ignored gate), to rows either side of each threshold, and to the invariances as property tests.
- Tests go through `Session::call` over `TestProject` or corpus models (`tools/test_support.rs`'s `Host` syncs a db the way hosts do); `tools/tests.rs` validates every tool's input and output against the schemas the catalog publishes, with rows from `ToolName::ALL`, and `tools/corpus_tests.rs` (ignored; `--release -- --ignored`) sends every corpus model through the tools and checks every answer against its schema and the budget.

## Tests

- Unit tests live beside their code, either inline or in a sibling `*_tests.rs` mounted with `#[cfg(test)] #[path]` so `use super::*` still resolves. Integration tests are one harness, `tests/integration/main.rs` (add a `mod`, not a new `tests/*.rs`); `tests/vm_alloc.rs` is separate only because it installs a global allocator. `test_common::TestProject` is the model builder, exported behind the `test-support` feature for sibling crates' tests.
- There is one compiler, in tests too: a test that needs a variable's lowered `Expr2` reads `db::lowered_source_variable` (or `model_lowered_variables` for a model's worth), a test that needs its compiled form reads it through the production per-variable lowering (`TestProject::flow_exprs`, over `db::var_fragment::explicit_fragment_input` + `compiler::fragment::lower_fragment`), a test that needs a refusal's location reads `TestProject::error_diagnostics`, and a loop-discovery test drives `ltm_finding::discover_loops_with_graph` with the graph and context `analysis::analyze_model` builds. Never add a whole-model parse, lowering or compile path for tests to compare against: it is a second implementation that every compiler change then has to be made in twice, and it can only agree with the production one by construction where the two share code.
- What pins unit semantics is the unit suites over production diagnostics, and what pins sharing is `Arc::ptr_eq` against the production memos plus `ProbedDb` body counts (`db::lowered_variable_tests`). A fixture is what production produces: build models through `TestProject`, `open_xmile` or `open_vensim` and read results through the production queries.
- The `test/` corpus at the repo root holds models with expected outputs from other SD tools; the heavy C-LEARN and World3 gates are `#[ignore]`d and run with `--release -- --ignored`. Observe the time budgets in `docs/dev/rust.md`; test a threshold with a test-only override, not a fixture large enough to trip it.
