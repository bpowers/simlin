# simlin-tools

The agent tool surface: a session per model that answers an agent's tool calls with JSON.
It is built on every other engine crate but the wasm backend, and libsimlin's `agent_tools` feature is what depends on it.
The root `CLAUDE.md` holds the development rules; this file is a map of where functionality lives (paths are relative to this crate's `src/`) and of the standing invariants code in this crate keeps.

## Agent tools

This crate is the agent tool surface ([design plan](/docs/design-plans/2026-09-20-agent-tool-surface.md)): the tools an agent uses to read, run, analyze and edit a model, stated once so every host that mounts them answers alike.
It is behind the `agent_tools` feature (default on; libsimlin's browser bundle leaves it out). libsimlin mounts them for native hosts (`simlin_tool_session_*`), and pysimlin through it (`simlin.ToolSession`); the plan's hosts phase mounts them in the MCP servers.

- `Session` is one agent's work on one model: `call(Workspace, tool, input_json)` answers a tool with JSON (`ToolOutput`, whose `is_error` marks a refusal for the agent to read and repair; only a tool the catalog does not list is an `Err`).
  A `Workspace` is the project, the db synced to it with `SimlinDb::sync`, the host's revision, which must be equal exactly when the contents are, and `waiting`, how the host says other work waits for the project: a call checks it between units of its work (`Workspace::yield_point`) and stops with a refusal marked `interrupted` that kept nothing.
  `cancelled` is how the host says it cancelled the call: `call` and `run_results` fold it into the checkpoints' `waiting` (`checkpointed`), and a call a cancel stopped answers a refusal marked `cancelled` (`ToolOutput::cancelled`), which no host retries.
  No tool changes the project it is given: a tool whose effect is an edit (`ToolEffect::Edit`, `edit_model` alone) answers an edit it made with the project as the edit leaves it (`ToolOutput::edited`, present exactly when an edit was made and changes the project), and the host, which holds the project's contents for that call and passes it no `waiting`, makes it the contents in one edit and syncs its db to it.
  `changes_since_read` is what changed since the session's last `read_model`, refusing a project that no longer has the session's model as every tool does; the session's own edits are no part of it, since the session holds what an edit changed as read from the moment it is made (`ReadSnapshot::absorb_variable`).
- `catalog.rs` owns the tool list (`ToolName::ALL`, names, descriptions, effects).
  The input and output schemas are derived from the serde types with schemars (inputs under the deserialize contract, outputs under the serialize contract, so a field an output skips when empty is optional) and checked in as `catalog.json`, which `catalog_json` embeds so builds without `schema` carry no schemars code; `tool_catalog_matches_the_checked_in_file` fails when it is stale and `UPDATE_TOOL_CATALOG=1` rewrites it.
  Inputs are `deny_unknown_fields`.
  The catalog also publishes `refusalSchema`, the one shape of every refusal.
  `strict_schema.rs` renders each input schema for Anthropic's strict tool use (`strict_input_schema`, derived from the checked-in catalog when asked for, so the two cannot drift; the module cites the documentation it follows): `oneOf` to `anyOf` (every catalog `oneOf` is of disjoint variants, a test holds it), unsupported item bounds and formats and `title` left out (a bound said in the description), an optional property's `null` arm dropped.
  `strict_cost` is a tool's share of strict tool use's per-request limits; the catalog stays the contract the engine checks.
- One owner per decision: `names` resolves a name (canonically, else by word similarity over names and documentation, stop words dropped from queries only) and ranks candidates in tiers that never overlap (`names::similarity`: the name itself, then a phrase that starts the name's words, then a likeness capped at `FUZZY_CEILING`, which a phrase under `MIN_FUZZY_CHARS` has none of; a phrase over `MAX_QUERY_CHARS` is compared with nothing, and `find_variables` refuses it); `evidence` gives diagnostics and loops ids stable for the session's life (a diagnostic keyed by variable, severity, code and the engine's own reason, never by span, so an edit that moves a problem keeps its id; a loop by the canonical rotation of its cycle as the engine has it, each element and each builtin's instance a node, so a loop has one id in every run, at every revision, from a run or from structure, and two loops between the same variables, one of them through a builtin, are two); `changes` diffs variable records (`changed_fields`, the one statement of whether a variable changed, which `same_record` asks too: provenance and a uid are no change, a case-only rename is a change of `name`), sim specs, the project's dimensions and unit definitions, and its other models' variables against the last read (views excluded: a layout edit changes nothing an agent read); a record's inputs and readers come from `model_reads::model_reads`, and every name an answer gives is spelled as the model names the variable (`evidence::display_name`), a stock's flows and an edit's lines included, except inside the engine's own reasons and a module's wiring, which name variables canonically.
  `input::parse` reads a tool's input through a deserializer that tracks where it is, so a mismatch is refused at its place in the input (`set[1].value`) rather than at a line and column of text the agent never wrote; a mismatch inside an internally tagged variant (an operation, a citation), which serde reads from a copy, is placed at its field by elimination (`field_at_fault`, the tag passed over).
  It reads input as JSON is written, not as serde would accept it: a struct only from an object, a tag only from a string, a key once per object (`Unique`).
  `suggestions` in a refusal or a `notFound` only ever hold names (at most `MAX_NAMED`), and a `notFound` for an element a variable lacks says why in `reason`; an answer repeats a caller's text through `evidence::echo` (at most `ECHO_CHARS`, with its length) and writes a number through `results::written` (an exponent for one too large or small to read written out).
  A project-level diagnostic (a unit's declaration) names no variable: the reason names the unit.
  Every name an answer gives is one a tool takes back or is explained: a special-stock helper is said as what it stands for (`evidence::explain_helpers`, `conveyor_compile::describe_helper`), and a value that stops being a number in another model is named with its model.
- Every answer of every tool, refusals included, keeps to the session's byte budget (`OUTLINE_BUDGET`), fitted, with what it leaves out counted or named; an answer that cannot fit with everything it can leave out left out is refused, never given over.
  `fit` is the one loop answers are fitted by (each tool says what it leaves out, in what order, and how it counts it); `ToolOutput::refusal` cuts a reason the engine wrote at length to `MAX_REFUSAL_CHARS`, and under a budget smaller still leaves out suggestions and halves the reason; a run's failure is cut where it is made (`RunFailure`, `MAX_REASON_CHARS`), since every answer that says so repeats it.
  `find_variables` leaves its least close matches out (`omitted`), `verify_findings` a finding's last failures and then the last findings, giving ids only to what it shows, `run_experiment` its last comparisons, and an edit its last diagnostics and then its lines.
  What changed since the last read is cut to a quarter of the budget (`Changes::fitted`), so it never refuses a read.
  `outline.rs` (`read_model`) lists diagnostics errors first and fits them by bytes, keeping every entry when the entries and every error fit, else outlines by sector, filling its lists in order of need (`Part::ALL`: errors, stocks, the sectors that hold a variable, warnings, names), each only once every list before it is whole; a refused outline is no read.
  `variables.rs` has `read_variables` (a variable or one element of one, `names::resolve_reference`; per-record caps, then whole records named in `omitted`, then the one record left cut in `Cut::ALL` order, readers first and its equation last, `truncated` set when text was cut; a constant carries no behavior) and `find_variables` (the name itself, then names whose words the phrase starts, then names like it, `names::similarity`).
  Documentation is read as prose (`variables::tidy`: a Vensim comment's backslash line continuations joined).
  Every tool's budget is a property gate over generated models (`tests.rs`, `generated_models`, models with as many as 120 errors), each tool asked what makes its answer longest, with a default-suite row per shape (`every_tool_keeps_to_its_budget`); below `ANSWER_FLOOR` an answer is held to the floor (its first line, diagnostic or record is never cut), the outline and the records to the budget itself.
  `evidence::window` cuts a quoted equation to 240 characters around its span.
- Runs: `runs.rs` holds a run's `RunPlan` (values from a time, replacement equations, specs), the session's `RunStore` and `execute`.
  Values and specs are VM overrides (`Vm::with_specs`: the compiled program does not depend on the specs), so a plan of them compiles nothing and touches no salsa input; a replacement equation -- or a spec change on a conveyor or queue model, whose expansion reads the specs -- stages a copy on the host's db (`Staging`, a guard that restores on drop, as a dry-run patch does), so the project never changes.
  A run is fresh while `db::simulation_key` (the salsa sync's extraction of what the compiler reads, less units; memoized per revision) is what it ran at, so a layout, notes or units edit stales nothing; the store keeps the current run per key, at most `MAX_RUNS` named runs in the order they were made, and at most `MAX_RUN_BYTES` of results and loop analyses (the oldest keep their plans, in their places, and run again while fresh).
  One run's cost is held to `MAX_RUN_VALUES` saved numbers and `MAX_RUN_STEPS` slot-steps, or the model's own when that is more (`over_budget`, checked before the VM allocates).
  `Session::runs` and the agent's `list_runs` list each run's plan exactly as it ran (`RunListing`: from, changes, specs); `Session::runs` and `Session::kept_run_results` (a run whose results the store keeps) read the contents and revision alone, never the database (`RunStore::key_of`), so a host lists and charts runs while another call holds it; `Session::forget_run` forgets one the person discards.
  `execute_then` compiles under an overlay and hands the caller the db while it still holds the staged project, for an analysis that reads the run's structure.
  A value from `t` holds from the first step at or after `t` under every integration method: the run is taken to that step with `Vm::run_until` and the value set before the step is evaluated.
  A plan over another (`RunPlan::over`) is a timeline per variable: a change from the start replaces every change the base made to that variable, and a value from a time replaces only the base's changes from that time or later.
  A run is taken in `RUN_SLICES` slices of its steps, counted as the VM counts them (`Vm::run_until_step`), so a run whose clock's last place is coarser than its DT still ends, and stops between two slices when the workspace says other work waits (`RunFailure::Stopped`, which a tool answers as the stop).
  A replacement equation drops the variable's table (`replace_equation`).
  `experiment.rs` is `run_experiment`, which resolves a multiplier to a value against the starting run when it is made, and refuses a value from a time on a variable the starting run gave an equation that is not a number (the time goes into the equation); `series.rs` summarizes a series (`SeriesCore`, rounded as decimals to five significant digits, with any number that is not finite left out) and is `read_behavior` (one element by name, `names::resolve_reference`; fitted to the budget by `fit`: samples, then turns, then elements, then variables, then the names of the variables left out and of those not found, each list named as far as it fits with its whole length counted, `variablesCount`, `notFoundCount`).
  Every number a summary reports is the series' own, rounded, so every tool reports the same one, and its parts agree: a series that is not at rest reports extremes that read differently, and it went negative exactly when a number reported of it is negative.
  Every tool reads a series at the scale of what it is computed from in the run (`series::scale_in_run`, per results key, so each element at its own, and from the run's own equations, its plan's replacements applied by `runs::apply_equations`: a stock's flows over the horizon, the terms of an equation that is a sum; an experiment's two runs share the larger of their magnitudes, each read at its own equations' scale), so arithmetic residue of quantities that cancel is at rest, while a real change of more than 64 units of `f64::EPSILON` of that scale (a part in 7e13 of it), and a model whose quantities are all tiny, are read as they move.
  Residue that reaches a series through anything but a sum (a quotient feeding a stock, `SMTH1`, `MAX`) is read as it moves; a stock's flow counts at its own scale as a sum, one level back.
- `loops.rs` is `analyze_loops`.
  A run is made without the LTM overlay; its loops are analyzed on demand by replaying its plan under the overlay with the project in discovery mode (set by the `DiscoveryMode` guard, which sets it back on drop, a panic included) and running `analysis::discover_run_loops`, and the analysis is kept on the `Run`, which a layout edit leaves fresh.
  It stops before each stage -- the replay, the discovery over its results, the loops from structure -- when the workspace says other work waits.
  The answer is per cycle partition: a dominance timeline (`ltm_dominance::leader_timeline` in at most `MAX_SPANS` spans, each naming its leader and its rivals, those with half its share over the span), and the loops the timeline names plus the most important others, each with its mean share over the steps the partition is active at.
  A span is led by the loop with the largest mean share over its steps, a joined span too (`ltm_dominance::strongest`, the one statement of who leads, at a step and over a span: the largest share, a tie to the first in key order, which `timeline` takes its loops in); `leadership`, the verifier's `leads`, holds by the same rule over the steps from a cited `from` to its `to`, both included (a span prints the times of its first and last steps, one step from a time to itself), so every span leader an answer names, cited back, holds (`unconfirmed_leaders`, beside the other corpus oracles), and `leaders_after`, the battery's, reads the timeline's spans.
  A loop is one cycle of the model's elements, keyed by the engine's node sequence, from a run and from structure alike: the structural surface's apply-to-all loop is expanded to its elements' loops (`ModelNames::element_cycles`).
  A chain starts at a stock and leaves builtin and macro internals out, composing their links and marking the link with the builtin (`via`), and signs a link by the run when the run scored it (`LinkPolarity::from_runtime_scores` over its relative score, unknown when its sign changed; a link discovery stitched across an aggregate node by the paths through it, `RunSigns`) and by its equation otherwise; a loop over `MAX_CHAIN` variables is given by its stocks, and whole by id (`loops`).
  `through` takes a variable or one element, and lists only the loops through it, with the timeline of them.
  A run with no active loop, or whose stocks never leave zero by more than residue at the scale every tool reads them at (`behavior::residue_bound` at `series::scale_in_run`: scores of residue are noise), falls back to the structural loops (`db::model_detected_loops` with discovery mode off, when `model_ltm_mode` says the structure alone enumerates them), says so, and says how to disturb it; a run with active loops lists the model's other structural loops as `inactive`.
  Past residue, whether a run moves enough to analyze is the engine's exact rule (a link is active where its ends changed), never the precision a summary reports: a score is a ratio, as exact for a small movement as a large one.
  An analysis is `complete` only when it has every loop of the run -- not a sample, not capped, none left out as negligible -- and an absence is shown only from every loop of the model (`LoopAnalysis::shows_absence`: a complete analysis, or the active and the inactive loops together where the structure lists them), so `loops_through`, which the verifier's `no_loop_through` reads, names such a loop too, said to be inactive in a run the analysis has every loop of and otherwise not among the loops it reports (`unreported`: an inactive loop and one discovery left out are not told apart).
  The structural surface can report one cycle of elements twice (a loop through a reducer, its aggregate node left out, beside the direct one); `structural_loops` keeps one, undetermined where the two signs disagree.
  A plan that replaces equations reports the links it removed and the model's loops through them.
  The answer is the longest prefix of what it would list that fits the session's budget (`Selection`: each partition with its timeline and the loops it names, largest first, then a cut's loops, the other loops by share, the inactive loops), cut one unit at a time by `fit` on the ids the loops would get (`Evidence::preview_loop_ids`), so only what is listed is named; loops by id come whole, the last asked for left out (`leftOut`) when they do not all fit, a loop the run left inactive or a cut removed under `inactive` or `cut`.
- `battery.rs` is `run_tests`, the validation battery: units (skipped, saying so, for a model that declares none and has no unit diagnostic), extreme conditions, integration error, sensitivity, loop knockouts and disturbances, each a set of checks (one changed run each) under ids keyed by test, target and condition, shared between the tests in turn and fitted to the budget, ids given only to what is listed.
  The default targets are the constants that reach a stock by any read, as the run goes or where it starts (`Graph`, over `model_reads::model_reads`); what they leave out (unit conversions; dates, for the tests that scale a constant) is said once (`leftOut`), and a disturbance also leaves out, unsaid, the constants that move no stock as the run goes (`Graph::only_starts`), which a step after the start does not move.
  What a stock moves, for the time constants, is what it reaches by the reads made as the run goes (`Graph::moved_by`).
  `Roles` classifies the constants once: unit conversions (value one of its units: a ratio of one unit at two scales, a ratio of two units of time at their known ratio within `TIME_RATIO_TOLERANCE`, or one unit its name states, by any name the project reads as it), shares (high extreme the whole), dates (compared with `TIME` or given to `STEP`/`RAMP`/`PULSE` as a time, directly or through a carrier auxiliary; extremes the run's start and past its stop), divisors and constants that move no stock as the run goes (low extreme a tenth), fractional rates (high extreme at most one over two DTs), and `time_constants` (low extreme a tenth and at least `DTS_PER_STAGE` DTs a stage, DT in the constant's own unit; a delay's time from the engine's stdlib tables, `TIME_PORT`; with units, a unit of time; without, or declared dimensionless in a rate that carries a unit warning, by its role in a rate on equations `normalized` so a power of -1 reads as a division; each says why, `TimeConstantEvidence`, and whether it paces a stock).
  A call's `extremes` replace the rules' for a constant (one entry a constant; a second is refused); each extreme check says its rule (`ExtremeRule`), and a sensitivity check held at one says which (`heldAt`).
  A problem an extreme finds as the run goes is confirmed at a tenth of DT, at most `MAX_CONFIRMATIONS` a call.
  Below zero is judged per element, for stocks and for series marked non-negative, where the model's own run keeps the element at or above zero (a stock with any element below zero there is signed and not judged), by more than `behavior::residue_bound` at its scale; a check says what went below zero, never why.
  The model's own run is a check of its own, listed first: series not a number in it (judged by no other check), and marked series below zero, with a note that the engine does not enforce the marking.
  A model that does not simulate says so once (`runFails`) and every test is skipped; extreme conditions and integration error are skipped for a model with no top-level stocks (a module model's are not read yet), and the tests that compare recorded variables when none are recorded.
  Integration error is one measurement, the runs at half and a quarter DT saved at the model's own times (`finer_specs`, which asks `results::save_step_is_on_the_step_grid`, rows matched by time, `rows_at`): Richardson's estimate and the observed order (given only where the runs converge), passed at or under `INTEGRATION_TOLERANCE`, flagged up to `INTEGRATION_FAILURE` and failed above it, naming the shortest time constant that paces a stock (a literal one written into a rate included), flagged where the runs do not converge or an equation reads DT.
  Sensitivity reads each run at its own scale with the two series' magnitudes shared (`series::compared_scales`, the one owner, which `run_experiment` uses too; a series not a number somewhere shares none) and is flagged when a behavior changes family (`BehaviorFamily::of`, the classifier's mode with pace set aside), the series' turns at `MATERIAL_CHANGE` of its range change too, and the series' own range is material in one of the runs; a response shows the classifier's damping where the series oscillates (`damping`, `wasDamping`).
  It is not run again at a finer DT.
  Checks that flag the same change of the same series are listed once, naming the others (`same_changes_folded`, `sameChange`); a check, knockout or disturbance whose run makes a recorded series undefined is flagged; a check lists at most three responses and counts the rest (`moreChanges`); a difference within the residue of the series' shared scale is no change, and a series the model's run holds at zero is measured by that scale.
  Knockouts hold every element of an arrayed variable at its own start (`runs::Replacement::Elements`).
  Value-only checks run through `runs::execute_values`: one compile, a VM each, in parallel off wasm, at most `runs::concurrent_runs` at once (`MAX_BATCH_BYTES` of results; a test lowers it with `TEST_BATCH_BYTES` and counts the runs in flight), each summarized inside the map, none started once the workspace says other work waits.
  A call that stops restores the session's evidence, so it gives out no id.
  `battery_corpus.json` labels every check the battery lists over 29 corpus models (accepted or not, and why); an ignored gate holds the battery to it and to the model count, and three small models do so in the default suite.
- `edit.rs` is `edit_model`, an edit made in the one call when its gate passes.
  Operations are applied in order to a copy of the project through `apply_patch` (`Builder`, which notes the variables the operations name and the equations they write: `Touch`, `Authored`).
  What the edit changes is its `Delta`: every variable whose record differs, in any model (a rename's readers, the stocks a flow leaves, the modules of other models that instantiate this one), with its record before and after, the project's sim specs and each loop name by its uids.
  Everything in the delta must be as the session last read it (`Delta::stale_since_read`) or the edit is refused, naming it.
  The gate (`gate`, staged under `runs::Staging`, stopping between its stages when a checkpoint says so) judges the edited project against the project as it is under a `GatePolicy`, which asks for rules by name (`GatePolicy::asks`; `GatePolicy::AGENT_EDIT` asks for all), the gate asking them in `GateRule::ALL` order: the project's diagnostics, every model's, compared as a multiset by the evidence module's identity of a problem (`Described::identity`, the project's mapped through the edit's renames; a reason that names a renamed variable is compared without it), refusing an error the project did not have and an error in an equation the edit writes (a units error is the units string's, which the edit did not write) -- the engine reports one error of an equation and one cycle of a model, so the arms the edit wrote are judged with the others set aside (`isolated`), and the edit is judged a second time with the variables that were broken set aside (`set_aside`: their equations a constant), so an error a broken variable hid is not blamed on a repair and one written beside it is still seen -- and listing an error whose reason changed on a variable the edit does not write (`Listed`); a variable the edit removes that any text still names (`simlin_edit::patch::variables_naming`, over every model: a reader whose equation the compiler refused need not report it), refused naming the readers; the model the edit is of and the project's root model still simulating if they did; a value that becomes non-finite in either run; a model's first unit warning; and, under any policy, specs whose run costs more than a run may (`runs::over_budget`).
  What an edit the gate passes adds is placed by the incremental layout, which decides the view's elements and nothing else of the view (`Builder::place`); a refused edit is never laid out.
  A `name_loop` names a loop only when its variables are one feedback loop of the edited model, as the engine judges a named loop (`db::model_pinned_loops`, which reads them as a set, so their order is no part of it), refused before the gate naming the link that is missing (`no_loop`).
  Specs no run can be made under are refused at the operation (`runs::no_run`: the VM's own checks, `results::Specs::refusal`, which both backends ask, a run of numbers, and a DT no longer than the run), as are an equation nested deeper than `input::MAX_EQUATION_DEPTH`, measured on its tokens before anything parses it (`input::equation_depth`; the parser and every pass over its tree recurse).
  An edit the gate passes is made: `edit_model` returns the project as the edit leaves it, which `Session::call` puts on `ToolOutput::edited`, and the session's last read absorbs the delta (`Delta::absorbed_by`); an edit that changes no record says so (`unchanged`), is not gated (nothing is compiled or run, and `simulates` is absent), marks no provenance, draws nothing and hands the host nothing.
  A diagram the edit draws for a model that had none is no line.
  When a model that did not simulate does after the edit, the series that are not a number in its run are listed as warnings (`undefined`), since no rule refuses them.
  The answer's `revision` is the revision of the contents the edit was made on, never a promise of the one the host gives the edited contents (a counter's next, or a hash).
  An edit the gate refuses is a refusal, `is_error` set, in the one refusal shape (`ToolError`): its reason, and `refusedEdit` (`RefusedEdit`: the `GateRule` that refused it, and the lines, diagnostics and whether the model would simulate, as the edit would have had them), fitted to the budget as a made edit's lines are; nothing changes, the session included.
  The answer's lines (one per variable changed, other models' named with their model, every name spelled as the model spells it; a module's line says which inputs were rewired or left unwired, and an unwired input is a warning too; a change of kind says what the variable is computed from now, a lookup its points and their ranges, and the specs a save step a larger DT drops) are fitted to the budget, and a diagnostic a made edit leaves in the model is listed under the id a read gives it (`Evidence::diagnostic_ids`, the one owner of a diagnostic's id, over the staged report the gate kept).
  In a project that records provenance, what the edit adds or edits is marked (`after_ai_edit`: in-app provenance, unverified against ISEE's documentation).
  A name a variable can take is one made of words that an equation's spelling of it (`ast::print_ident`) reads back as one variable, reserved words and numbers aside (`Builder::named`).
- `verify.rs` is `verify_findings`: each citation of a finding checked against the session at the current revision (runs made before the model changed, diagrams aside, are not evidence), a failure saying what is true instead, a finding every citation of which holds given an id keyed by its claim.
  A variable or one element of it is named as the read tools name one (`named`, over `names::split_subscript`/`resolve_element`), so a citation names an element the variable has.
  An `equation` citation compares parsed equations in a normal form (`normal`: spacing, case and name spelling aside); a table variable's equation is its table at its input (`LOOKUP(name, input)`), and a table other equations look up has none of its own and is cited with an empty one.
  `value` and `ends_near` judge a number against the actual one (`near`: within 5% of the larger of the two, which two values of opposite signs never are; a cited zero against `VALUE_FLOOR` of the series' largest magnitude, and nothing but a cited zero against the series' size), and a cited time outside the run is refused; `compares` asks whether two runs end apart (`apart`: by more than 5% of the larger and more than the floor).
  A peak is a largest value the series is lower than at both ends of the run by more than `behavior::NOISE_FRACTION` of its range (`peak`): a series still at its largest where the run ends, or at its start, has none, and neither has one at rest.
  A loop leads a span where its mean share over the span's steps is the largest, or ties with it (`Leadership::leads`, the timeline's rule).
  `readers` is the exact set of what reads the variable, and `reads` one read of it, both by `model_reads::model_reads`; a `readers` citation does not hold while an equation of the model does not parse (`model_unread_equations`), which may read the variable.
  A cited equation deeper than `input::MAX_EQUATION_DEPTH` is refused as an edit's is.
  A cited battery check answers from the session's check log while the revision is the one it ran at, and is run again (`battery::recheck`) after an edit; loop citations read the run's loop analysis (`loops::leadership`, `loops_through`, `polarity_of`, and `through_of` for an element).
  It stops after the citation during which other work began to wait, giving out no id.
- `behavior.rs` is the one statement of a behavior mode (`classify`, and `classify_at` for a caller that knows the scale): at rest, linear, exponential, goal seeking, S-shaped, overshoot, rise and fall, fall and rise, oscillation (damped, sustained, growing), undefined, other.
  It reads a series against its saved times, so unevenly saved rows read as the curve they sample where they resolve it, and every threshold is a fraction of the series' own range or magnitude, so a mode is the same at any scale, offset, direction and unit of time.
  At rest is a range under one unit of the last digit a summary reports, or a series that never leaves zero by more than the rounding floating point leaves at the scale its caller reads it at (`RESIDUE_EPSILONS`, 64, units of `f64::EPSILON` of that scale; a stock's scale already counts the run's horizon, so its steps are not counted again); there is no fixed floor, since residue and a tiny model are the same numbers and only the caller knows which.
  After trimming a still start and a settled end (each reported past a twentieth of the run; a share of the run is past a threshold only by more than a millionth, `past_share`, so a tie that evenly saved rows make reads alike on every clock), turning points are reversals over 1% of the range (`Shape::turns`, what a summary lists), and the mode is named for the large movements: reversals over a tenth of the range, less a first or last one under a quarter of the movement beside it and no longer than a quarter of the run (the run starting up or being cut off).
  No such turn is one movement, read from where a start-up transient ends, an overshoot when it ends short of its furthest by its largest reversal, else named by where it runs against its chord (along it, below it, above it, below then above); one is an overshoot, a rise and fall or a fall and rise; more are an oscillation, its damping the last swing against the first (with one whole swing, the movement after it is a second swing where it ends at a turning point, else the run cut it off).
  `behavior_tests.rs` holds the classifier to series from World3, C-LEARN and two small models labeled as a modeler names them (`behavior_real_series.tsv` in the default suite, a wider set and the file's fidelity to the models in an ignored gate), agreeing except where `KNOWN_DISAGREEMENTS` lists what it says instead and why (a late inflection reads as exponential; reversals over a tenth of the range make an oscillation of a growth curve), a table that fails when a listed row starts agreeing, to curves generated for each mode across parameters, densities, scales and clocks (a sample in the default suite, the full sweep an ignored gate), to rows either side of each threshold, and to the invariances as property tests.
- Tests go through `Session::call` over `TestProject` or corpus models (`test_support.rs`'s `Host` syncs a db the way hosts do); `tests.rs` validates every tool's input and output against the schemas the catalog publishes, with rows from `ToolName::ALL`, and that a call stopped at a checkpoint keeps nothing (each tool at a few checkpoints by default; every tool at every checkpoint, followed by every tool, as a gate); `corpus_tests.rs` (a gate; `scripts/gates.sh corpus_tests`) sends every corpus model through the tools and checks every answer against its schema, the refusal schema and the budget.
- `model_reads` (`model_reads.rs`) is the one owner of "what does this variable read, and what reads it": every read of `variable_direct_dependencies` in both phases and under every lag, a helper's reads attributed to the variable it was made for, a read through a module instance a read of the instance, a stock's flows, a table a `LOOKUP` names, and what a stock's or a flow's options name (`ModelRead::option`: the special-stock build evaluates them outside the dependency set); a name the model does not declare is no read.
  An equation the compiler cannot read (it does not type, or does not parse) has no dependency set, and reads what its text writes (`simlin_edit::patch::text_references`), marked `unchecked`; `model_unread_equations` lists the variables with a text that does not parse, whose reads no one can know, so a claim that something has no reader cannot hold over the model.
  Each read carries the causal link's polarity from `model_links` where there is one, and is marked `start_only` when every read of the pair is made as the model starts (`read_at_start`, through an `INIT`-only capture, or as an instance's input source only its sub-model's start reads, `CausalEdgesResult::start_only_inputs`, which `init_only_sources` decides for both) and `table` when it is a lookup.
  `model_links` is the loops' graph and leaves those reads out, so "nothing reads this constant" would be false from it.
  The agent tools' records, the `readers` and `reads` citations and the battery's default targets read `model_reads`.

## Cargo features

`schema` (on by default) derives the tools' JSON schemas, which `catalog.json` is generated from; a build without it embeds the checked-in catalog.
