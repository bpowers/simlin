# Agent tool surface in the engine

## Why

Simlin's mission puts agents beside people: an agent reads a model, runs experiments, finds the feedback loops that drive it, tests it, and edits it. Today every host that gives an agent tools builds them itself:

- `simlin-mcp-core` has `ReadModel`, `EditModel` and `CreateModel`. `ReadModel` returns the whole model's JSON and every reported loop's per-step importance series; `EditModel` takes wholesale variable upserts, so an agent re-reads a variable before changing one field of it.
- pysimlin has `Model.explain`, `check`, `get_links`, `run(overrides=)`, `simulate()` with `run_to` and `set_value`, `Run.loops` and `analyze()`, each a composition in Python over libsimlin primitives.
- A native host that embeds an assistant would write a third set over the C API, and libsimlin already composes some analyses privately (`analyze_links_core`).

Three implementations of "what does this model do" drift, and none of them was designed for the job an agent does. An agent's tool result is the context for its next decision, and a claim it makes about a model is only as good as the evidence behind it. This plan puts the tools' semantics in the engine, once, for every host:

- **The engine computes, the agent explains.** Unit algebra, loop enumeration, dominance, sensitivity and integration error are what language models get wrong and what the engine gets exactly right. Every analysis an agent's critique relies on is a tool the engine runs.
- **Results are bounded and quiet.** No tool returns the whole model or a raw series. A model too large to outline in a few thousand tokens is outlined by sector. Success says little; a refusal names the rule it broke and the repair.
- **Results carry ids a claim can cite.** Diagnostics, loops, runs, test results and findings have ids that are stable for the life of a session, so an agent can say "D3" or "the half-adjustment run" and a verifier can check it.
- **Experiments are data.** An experiment is a declarative spec (values, multipliers, replacement equations, a start time, run specs), so it is bounded, checkable and cheap to describe.
- **An edit is one call, gated.** `edit_model` makes its edit or refuses it, as a tool that writes a file does: whoever lets an agent call it, a person or a host's policy, has approved the call, and the host's undo is how a person takes an edit back. Nothing sits between the gate and the project, so the gate is the rule: an edit that would break the project is refused and changes nothing. The engine never changes a project; it hands its host the project as the edit leaves it, and the host makes that one edit of its own, undoable wherever it keeps undo and shown like anyone else's.

The consumers are a host's own assistant (through libsimlin), MCP clients (through `simlin-mcp-core`), and pysimlin users, including evaluation harnesses that must exercise exactly what ships.

## Where it lives

`simlin_engine::tools`, beside `editing` and `analysis`. Both libsimlin and `simlin-mcp-core` already depend on the engine, so the module needs no new crate, no change to `scripts/dep-policy.json`, and no second copy of any engine query. The editing core (`docs/design-plans/2026-09-12-editing-core-in-rust.md`) set the precedent: host-facing planning that must agree across hosts lives in the engine, and libsimlin exposes it.

A separate crate would isolate the surface's serde and schema code from the compiler, but every tool is a composition of engine queries (diagnostics, causal edges, `build_sim`, discovery), so the crate would re-export most of the engine to itself.

## The session

A tool call runs in a `tools::Session`, bound to one model of a project:

```rust
pub struct Workspace<'a> {
    pub project: &'a datamodel::Project,
    pub db: &'a mut db::SimlinDb, // synced to `project`
    pub revision: u64,
}

impl Session {
    pub fn new(model_name: &str) -> Session;
    /// `Err` only for a tool the catalog does not list: the host's mistake.
    pub fn call(&mut self, ws: Workspace<'_>, tool: &str, input: &str)
        -> Result<ToolOutput, UnknownTool>;
    /// What changed in the model's variables and sim specs since the last
    /// `read_model`, for a host to tell the agent before its next turn.
    pub fn changes_since_read(&self, project: &datamodel::Project, revision: u64)
        -> Option<Changes>;
}

pub struct ToolOutput {
    pub json: String,
    pub is_error: bool,
}
```

A session holds what one agent's work needs across calls:

- **Evidence ids.** Diagnostics (`D1`, `D2`, ...), loops (`L1`, ...), test results and findings get ids when first reported, and keep them while the thing they name exists. A diagnostic is keyed by its code, variable and reason; a loop by its canonical cycle (the rotation-invariant, direction-preserving sequence of the engine's nodes, each element and each builtin's instance one), so the engine's own loop-id scheme, which the single-mode LTM plan changes, never reaches an agent.
- **Named runs**, each with the experiment that produced it, the revision it ran at, and a key of what it simulated, so a later claim can cite a run and a run can be replayed (with the LTM overlay, when loops are asked of it). A run is fresh while the model has what it simulated: a hash, once per revision, of what the salsa sync hands the compiler (`db::simulation_key`, over the sync's own extraction of each project, model and variable, less units), so the key holds exactly the fields a compile reads and a field the compiler starts reading cannot be left out of it. It takes apart every type those fields hold and leaves out what no run reads (a pinned loop's description and the uids that only word its diagnostic, a table's y scale); text is hashed as written, so a case-only rename or a respelled equation stales runs it need not have. Diagrams, sectors, provenance, the source file and documentation are no part of that extraction. Units are checked, never simulated, so a layout edit, or an edit of a variable's notes or units, leaves every run fresh, and the current run is not simulated again.
- **What the agent last read**: the revision and the model's variable records at its last `read_model`, with its sim specs and what its variables rest on (the project's dimensions and unit definitions, and its other models, which a module instantiates). When the revision moves, the next read reports what changed (a variable added, removed, or changed in named fields, a case-only rename among them; the specs, the dimensions, the unit definitions; each other model whose variables changed), and an edit of something that changed since the read is refused, naming what changed. The session's own edit is no change: when one is made, the session holds everything it changed as read, so the agent's next edit of it needs no read between and the report has only what someone else changed.
- **Caches per revision**, dropped when the revision moves.

A session is cheap and owns nothing of the project's, so a host can keep one per conversation, or share one between an agent and its own views of the same model.

### The revision

The host passes the project's revision with every call; equal revisions must mean equal contents. libsimlin counts them: `ProjectContents` advances a counter on every mutable borrow of the datamodel (the same `DerefMut` that already drops the hit indexes) and on every replacement of it (`replace`, which a committed patch and `simlin_project_replace_contents` go through), so no entry point can forget it, and reads (dry-run and rejected patches, simulations, diagnostics, renders) never advance it. The counter sits beside the shared datamodel, not in it, so a copy's revision is its own. `simlin_project_get_revision` reads it. A host without a counter of its own, like the stateless MCP filesystem access, passes a hash of the file it read.

A revision is a statement about the whole datamodel, views included. A layout-only change advances it, but it changes no variable record, so it makes no read stale and no run stale: a read's staleness is judged by comparing variable records, and a run's by comparing what a simulation reads, never by the counter alone.

## The catalog

`tools::catalog_json()` describes every tool: its name, a description that says what it is for, the JSON Schema of its input and of its output, and its effect (`read`, or `edit` for the one tool that changes the project). The schemas are derived from the serde types with schemars (the `schema` feature) and checked in as `src/simlin-engine/src/tools/catalog.json`, which a freshness test regenerates and compares, the pattern `docs/simlin-project.schema.json` already follows. libsimlin builds the engine without `schema`, and embeds the checked-in file, so no schemars code reaches the wasm bundle.

Property order in each schema is declaration order (`preserve_order`): a host that bridges the catalog into a structured-generation framework can take a property order from it.

Inputs are strict (`deny_unknown_fields`): an agent that misnames a field is told which field and what the schema expects, rather than having it silently ignored. The catalog also publishes `refusalSchema`, the one shape every tool's refusal has, so a host validates a refusal as it validates an answer.

A host that marks a tool `"strict": true` for Anthropic's strict tool use sends `tools::strict_input_schema(tool)`, a second rendering of the catalog's input schema in the subset strict tool use accepts (the "JSON Schema limitations" section of platform.claude.com's structured-outputs page): `oneOf`, every one of which is of variants no input matches two of, becomes `anyOf`; an item bound past `minItems: 1` and a `format` outside the listed string formats are left out, a bound said in the description instead; `title` is left out; and an optional property's `null` arm goes, since a missing property and a `null` one mean the same to the tool. The catalog stays the contract: the strict subset cannot state the bounds the engine refuses past, so a catalog written in it would understate what the engine checks, and the rendering is derived from the checked-in file, so the two cannot drift. Strict tool use also limits a request to 24 optional and 16 union-typed parameters across its strict tools; `tools::strict_cost(tool)` is a tool's share, counted at every depth, and the catalog's tools together are over the first limit, so a host marks a subset of them strict. OpenAI's strict mode is unverified.

## Outputs and failures

Every output is JSON with camelCase keys, and every successful output names the revision it read. Output types are serde types in the engine, so a UI consumes the same shapes an agent reads.

Every answer of every tool, a refusal included, keeps to a byte budget (`OUTLINE_BUDGET`, 12,000 bytes of JSON, about 3,000 tokens), fitted rather than cut: what an answer leaves out is counted or named, and each tool says where the rest is read. No answer is over its budget: one that does not fit with everything it can leave out left out is refused, saying why. A quote of an equation in a diagnostic's reason is a window of 240 characters around what it points at; an answer repeats a name or other text the caller sent at most 120 characters of, with its length; and a number too large or small to read written out is written with an exponent.

A number that is not finite -- a series that divided by zero or overflowed -- is left out of an answer, and its field is optional in the output schema; the behavior mode says when the series went undefined. JSON has no NaN, and a `null` where a schema says `number` is an answer the agent's framework may refuse to parse.

A domain failure is ordinary output with `is_error` set: `{"error": "...", "suggestions": [...]}`, naming the rule and the repair. `is_error` is set exactly when the call did not do what was asked, and every such answer has this one shape, an edit its gate refused included (which adds `refusedEdit`, the gate's rule and what the edit would have done): a harness or an MCP client that reads only `is_error` reads a refused edit as not made. An unknown variable is answered with the closest names, and `suggestions` only ever holds names; input that does not match the schema is answered with serde's reason and the place in the input it is about (`set[1].value`, or `operations[0].initial` inside a tagged operation), never a line and column of text the agent did not write. Input is read as JSON is written: a struct only from an object (never a list of its fields), a tag only from a string, and a key at most once in an object; a list past a tool's bound is refused by the tool, with the bound. A host bridges `is_error` to its framework's tool-error channel, and must not turn it into an exception that ends the agent's turn: the agent reads the refusal and repairs its call. Only a host's own misuse (a null pointer, an unknown tool name) is an FFI error. A call that stopped for other work on the project, and kept nothing, adds `"interrupted": true`, so a host that retries by itself can tell it from a refusal of the call itself (see the libsimlin surface). A call its host cancelled adds `"cancelled": true` instead, and is not made again.

Names are matched forgivingly: canonically first, then by a similarity over the canonical name and its words, so a misspelled or misheard name finds its variable, and one owner (`tools::names`) answers both "which variable did you mean" and `find_variables`. The name itself ranks first, then names whose words the phrase starts, then names like it; a phrase under four characters is like nothing (one letter off in three is another word), and one over 256 characters is refused.

### Experiments

```json
{
  "name": "half adjustment time",
  "from": "current",
  "set": [
    {"variable": "inventory adjustment time", "multiply": 0.5},
    {"variable": "customer orders", "equation": "10 + STEP(2, 5)"}
  ],
  "specs": {"dt": 0.125, "method": "rk4", "stop": 60},
  "record": ["inventory", "production"]
}
```

- A constant (or a flow whose equation is a number) takes a `value` or a `multiply`, applied as a VM override (`Vm::set_value`) with no recompile. A multiplier is resolved when the experiment is made, against the constant's value in the starting run, so a plan holds values and equations only and replaying it reproduces the run.
- `fromTime` makes value changes take effect at the first step at or after that time: the VM runs every step before it (`Vm::run_until`), then the values are set, and that step and every later one is evaluated with them, under every integration method. Under Euler that is the step `IF TIME >= t` turns on at. Under RK2 and RK4 an equation's `IF TIME >= t` is also read at the substeps of the step before, so it takes part of its effect a step earlier than a value set from `t` does; a change that has to match an equation's timing exactly is made as a replacement equation. A change at the start time is a change from the start, which initial values read.
- A variable takes a replacement `equation`, in that run only (for a stock, its initial value): the session stages a copy of the datamodel with the replacement on the host's db (`sync_staged`), compiles and runs it, and restores (`restore`, from a guard, so a panic restores too), exactly as a dry-run patch does, so the project is never changed and unchanged variables keep their compiled fragments. An equation change holds from the start; to change a variable at a time, the time goes into its equation. A replacement equation replaces the variable's value: a table its value was read from is dropped (`applied` says so), so holding an "effect of" at 1 holds it at 1. Replacing an equation cuts the links from what it read: that is how an agent knocks out a link to test an explanation, and the loop analysis names the loops it cut. A standalone table other equations call has no value to replace.
- A model that does not simulate can be tried in a copy: an experiment from "current" that replaces equations runs, compared with nothing, so an agent can test a fix to a learner's broken model before proposing it. A value change has nothing to run there, and is refused with that repair.
- `specs` change the run's start, stop, DT and integration method. The compiled program does not depend on them, so the model's own program is run under the plan's specs (`Vm::with_specs`) with nothing staged or compiled; a model with a conveyor or a queue, whose expansion reads the specs, is staged as an equation change is.
- `from` starts from another fresh run, keeping its changes as a timeline per variable: a change this experiment makes from the start (an equation, or a value with no `fromTime`) replaces every change the starting run made to that variable, and a value from a time replaces only the starting run's changes from that time or later, so the run is the starting run's up to that time. A value from a time is set on the variable as the starting run has it: where that run gave it an equation that is not a number, the experiment is refused and the repair is an equation with the time in it. A run made before the model changed is not a starting point.
- A session keeps 32 named runs and forgets the oldest past that; a name used again replaces its run. It keeps at most 64 MB of their results and loop analyses: past that the oldest keep only their plans, in their places in the listing, a fresh one is run again from its plan when asked for, and a stale one whose results went is gone.
- One run holds at most 2,000,000 numbers (its saved rows times the model's slots, 16 MB) and computes at most 200,000,000 (its steps times the slots), or what the model's own specs cost when that is more, so the model as it stands always runs. An experiment over either is refused before its results are allocated, with its numbers and a DT or stop time that fits. A DT of 1e-4 on a small model would otherwise ask for tens of megabytes, and the store would keep them.
- A call that runs several simulations -- a starting run, runs kept only as plans, the experiment's own -- stops before the next when other work waits for the project, and keeps nothing. A simulation is itself taken in sixteen slices of its horizon, and stops between two of them, so the work that waits waits at most a slice of a run.

### Loops

A run is made without the LTM overlay, which costs a compile the other tools never need. `analyze_loops` replays the run's plan under the overlay with the project in discovery mode (every causal edge scored; a guard sets the mode back, a panic included), runs discovery over the replay's results (`analysis::discover_run_loops`, the step `analyze_model` also takes), and keeps the analysis with the run, so a second call answers from it.

- **Partitions.** Loops compete only within a cycle partition (stocks connected by feedback), so the answer is per partition, largest first.
- **The timeline.** At each saved step the loop with the largest share of the partition's loop activity (the partition-relative loop score) leads, a tie going to the first of the tied by key, and no loop leading where none holds a thousandth. The timeline is the run cut where the lead changes (`ltm_dominance::leader_timeline`): every boundary is a step at which the lead passed, however long the run and however short the phase, so the growth phase of an S-curve has its span in a run a hundred times its length. Where a run has more than 12 such spans (an oscillation), the shortest joins its longer neighbour until it has 12, a joined span led, as every span is, by the loop with the largest mean share over its steps (`ltm_dominance::strongest`, the one statement of who leads, at a step and over a span, ties included); joining only removes boundaries. The first step, which has no score (a score is a change over the step before), belongs to the span after it. Each span names its leader and its rivals: the loops whose mean share over the span is at least half the leader's, at most three in all. Shares sum to one at each time over the partition's loops, so in a partition with thousands of loops (World3's) the leader holds a few percent; the answer then says that no one loop dominates those spans, rather than letting a small leader read as dominance. A span is printed from the time of its first saved step to the time of its last (one step is from a time to itself), and the verifier's `leads` holds by the same rule over the steps from a cited `from` to its `to`, both included, so every span leader an answer names, cited back, holds; the battery's "loops that lead after the step" are the leaders and rivals of the timeline's spans past it. A span names the single strongest loop, so where several loops take over together (SIR's balancing loops after the peak) the span changes a few steps after the turn. Loops that pass through no stock of the model (their state is inside a builtin) are in no partition and do not compete, so they are listed without a timeline or shares.
- **Loops listed.** Every loop the timeline names, then the most important others by mean share, at most 8 besides those. A loop's share is its mean over the steps at which its partition is active, so a partition's shares sum to one whatever part of the run it spends at rest. With `through`, only the loops through the variable are listed, and the timeline is of them: a span led by a loop that does not go through it names none.
- **Chains.** A chain starts at a stock and leaves out a builtin's or macro's internal nodes, composing the signs of the links across them and marking the link with the builtin it passes through (`via`), since a link through a `SMTH1` carries a delay and is another link than a direct one between the same two variables. Discovery leaves out an aggregate node (the synthetic node an array reducer such as `SUM(pop[*])` is routed through), and a link across one is signed by the paths through it, where they agree.
- **Link signs.** A link the run scored has the run's sign, by the rule a loop's polarity is read by, applied to the link's relative score (its share of its target's change at each step, `LinkPolarity::from_runtime_scores`): the sign its scores hold, where mixed signs count as one when they net to at least 99% of their magnitude, and `?` when its sign changed more than that. The relative score, because the raw one is unbounded: where a target's inputs nearly cancel, a few steps of the raw score outweigh the rest of the run. So a link through a non-monotone table, whose equation cannot sign it, is signed by what the run did, and a loop the run leaves undetermined shows which of its links changed sign. A link the run never scored has its equation's sign.
- **Long loops.** A loop of more than 12 variables is given by its length and its stocks; asked for by id, it comes whole.
- **Ids.** A loop's session id is keyed by the canonical rotation of its cycle as the engine has it: a cycle of the model's elements, a builtin's instance a node of it. So the same loop has one id in every run and revision, from a run or from structure (the structural surface's one loop for an apply-to-all family is expanded to its elements' loops), and two loops between the same variables, one direct and one through a builtin, are two loops with two ids.
- **A run at rest.** At equilibrium every loop score is zero, so dominance and a loop's runtime polarity are undefined. A run in which no loop is active, or whose stocks never leave zero by more than the residue of the quantities they are computed from (`behavior::residue_bound` at `series::scale_in_run`, the scale every tool reads a stock at), is answered from structure, saying so: the answer lists the model's loops from structure, with their equations' signs, when the structure alone enumerates them (`model_detected_loops` out of discovery mode, when `model_ltm_mode` says the model is small enough), and names the repair: an experiment that disturbs the model. Residue is the one exception to the engine's rule (a link scores where both its ends changed over the step, exactly): a score is a ratio of changes however small, so residue scores, and its dominance would be noise (two flows of 0.3 that differ in the last place make a balancing loop "lead" for one step and nothing else). Any real movement is analyzed from its scores, a stock a ten-thousandth from its goal as one ten away, since the ratios are as exact there as anywhere; the summary's precision, which reads such a stock as at rest, is no part of the rule.
- **Inactive loops.** A run in which some loops are active lists the model's other loops, from its structure, as inactive (at most 8, the shortest first), when the structure enumerates them: the answer is of the model's loops, not only of the part of it that moved.
- **Completeness.** `complete` says the analysis has every loop of the run: it is false for a sample (discovery could not enumerate), for the most important of more loops than discovery keeps (200), and when discovery left out loops that never held a thousandth of the activity. That no loop goes through a variable is shown only from every loop of the model: a complete analysis, or, where the structure lists the model's loops, the active and the inactive ones together (the loops discovery left out are among the inactive); otherwise `through` and the verifier say that a loop left out may.
- **Conveyors and queues.** A model with one builds through a path that scores no loop, and its causal graph has no link through one, so the answer says loops through them are not analyzed and lists only the structural loops that avoid them.
- **Knockouts.** A plan that replaces an equation reports the links the replaced variable read and no longer reads, and the model's loops through them: its structural loops, or its current run's when its structure is too large to enumerate.
- **The budget.** The answer is the longest prefix of what it would list that keeps to `OUTLINE_BUDGET`: each partition with its timeline and the loops that names, the largest first; then the loops a cut names; then the partitions' other loops, by share; then the inactive loops. The first partition always comes, without its rivals when even that is over. The fit is made on the ids the loops would be given, and only the loops the answer lists are named. Loops asked for by id come whole, as many as fit in the order asked, the rest named in `leftOut` for another call; one the run left inactive or a replaced equation cut comes under `inactive` or `cut`. World3 answers in 10 KB (one partition, 36 loops listed, the long ones by their stocks) and C-LEARN in 10 KB (2 of its 15 partitions, one per scenario), in 0.5 s and 2.5 s the first time and a millisecond or two after, on a release build.

### Behavior modes

One engine function classifies a series: at rest, linear, exponential, goal seeking (approach to an equilibrium, or decay), S-shaped, overshoot, rise and fall (overshoot and collapse), fall and rise, oscillation (damped, sustained or growing), undefined (a non-finite value), or other. The battery, experiments, `read_behavior` and a host comparing a person's predicted behavior with a run all call it. It reads the series against its saved times, so rows a run saved unevenly read as the curve they sample (where they resolve it: a dozen rows across a bend or a swing), and every threshold is a fraction of the series' own range or magnitude, so a mode is the same at any scale, offset, direction and unit of time:

- **At rest.** A series whose range is under one unit of the last digit a summary reports (five significant digits of its magnitude) is at rest, so a series that is not at rest reports extremes that read differently. Arithmetic residue is the other case: a stock fed `demand * fraction` and drained `demand / 10` creeps to 1e-15, and its numbers alone are the numbers of a model whose quantities are all that small. No fixed floor tells them apart, so the caller says what scale the series is read at, and a series that never leaves zero by more than the rounding floating point leaves at that scale (64 units of `f64::EPSILON` of it) is at rest. A stock's scale is its flows times the horizon, which already counts the steps its residue accumulates over, so a real net change of a part in 1e13 of the flows is still seen moving. The summary still reports the series' own numbers, so every tool reports the same ones. `read_behavior`, the behavior line of `read_variables`, the loop analysis and `verify_findings` read a variable, each element at its own, at the scale of what its values are sums and differences of in the run: a stock's flows over the horizon, the terms of an equation that is a sum at its top level. What a variable is a product or a quotient of says nothing of its scale. Each run is read at the scale of its own equations, the plan's replacements applied, so an experiment that replaces a cancellation of large terms with a small real flow sees the flow move. An experiment's two runs also share the larger of their magnitudes, so residue in the model's run beside a movement in the changed run is at rest and the change of behavior is seen.
- A still start and a settled end are trimmed, and reported as when the series starts and settles, once each covers more than a twentieth of the run. A share of the run is past a threshold only by more than a millionth of the run, so a stretch of exactly a twentieth (as rows saved evenly often make one) reads alike on every clock, whose times round differently; the smoothing window below follows the same rule.
- A turning point is a reversal larger than 1% of the range, so noise below that never makes one. These are the turning points a summary lists.
- The mode is named for the series' large movements: its reversals of more than a tenth of its range. A smaller reversal is a disturbance of the movement it interrupts wherever it falls (early wiggles before a long rise, a dip part-way, a slight recovery after a collapse). The first and last movements are the ones the run's window cuts, and one under a quarter of the movement beside it that lasts no more than a quarter of the run is the run starting up or being cut off: a brief rise before a long fall and recovery is a fall and rise, and a series that is one movement after a brief start-up hump is read from the hump's turn.
- With no such turn the series is one movement. It is an overshoot when it ends short of the furthest it went by more than the noise tolerance and by more than any dip on the way there. Otherwise it is named by where it runs against its chord, the straight line from its first point to its last, in the unit square and smoothed over a tenth of the run: along it (linear), below it (exponential), above it (goal seeking), below and then above (S-shaped). One threshold, 5% of the range, separates a line from every curve, so no curve falls between two tests; growth by a factor of about 1.5 over the run is where exponential growth stops reading as linear.
- With one it is an overshoot when the series comes back less than half the way it went, else a rise and fall or a fall and rise. With two or more it is an oscillation, damped, sustained or growing by its last swing against its first. With two there is one whole swing, and the movement after it is a second swing when it ends where the series turns back (a swing smaller than a movement, or the start of one the run cut off); otherwise the run cut it off, and the oscillation is growing when that movement is already larger than the swing, damped when the series settles within half of it, and undetermined otherwise. A second-order response is an oscillation when its second swing is over a tenth of its range (an overshoot of about a third), and an overshoot below that.

The evidence is of three kinds (`tools/behavior_tests.rs`). Series from World3, C-LEARN and two small models, each labeled with the mode a modeler gives it and why: 24 in the default suite from a checked-in file, and 56 in a gate that also holds the file to the models' own runs. The classifier agrees with each except for ten listed with what it says instead and why: two late inflections it reads as exponential; seven series whose reversals over a tenth of the range (volcanic dips in a temperature record, a rebound on the way down, a dip on a plateau, a late rebound, a dip that is most of a tiny range) it reads as an oscillation; and one oscillation whose damping it judges by its swings between turns rather than by the larger movement the run cuts off. That table fails when a listed series starts agreeing, so it says what the classifier does today. (World3's food per capita, which collapses and recovers 2% of its range, is a rise and fall; its birth rate, which rises briefly before a long fall and recovery, is a fall and rise; C-LEARN's temperature change from preindustrial, a noisy record to 2000 and a smooth projection after, is exponential growth under every climate sensitivity.) Generated curves of every mode across their parameters, sampling densities from five rows to five thousand, scales, offsets, directions and clocks: all named for their family clean, and at least 99 in 100 with noise a fifth of the tolerance. And rows either side of each threshold, with the invariances as property tests. What it names is the run's behavior over the run's horizon, not the structure's.

### The validation battery

The battery is the model tests of system dynamics practice (Forrester and Senge, "Tests for building confidence in system dynamics models", 1980; Sterman, *Business Dynamics*, ch. 21), run mechanically by `run_tests`. Each test is a set of checks, each check one run with one change compared with the model's current run:

| Test | What the engine runs | What it reports |
|---|---|---|
| `units` | unit checking | each unit diagnostic, by its `read_model` id; fails when there is one; skipped, saying so, for a model that declares no units and has no unit diagnostic (a broken unit definition is the project's), where nothing is checked |
| `extreme_conditions` | the model's own run, then each targeted constant at its low extreme and at its high one, each check naming the rule that chose its value (`extreme`) | values that become NaN or infinite when they are not in the model's own run (a failure); a stock's element, or a series marked non-negative, below zero where the model's own run keeps it at or above zero (flagged for judgment); in the model's own run, series not a number and marked series below zero |
| `integration_error` | the run at half and at a quarter of its DT, saved at the model's own times | one measurement: each stock's (every element's) error at the model's DT by Richardson extrapolation and the order the runs converge at; passes at or under 1% of its scale, flagged up to 5%, fails above, naming the shortest time constant DT is too large for; flagged, saying why, where the runs do not converge or an equation reads DT |
| `sensitivity` | each targeted constant at half and double, within its extremes | per recorded variable, the change in its final value and its largest change over the run (a difference within the residue of what the series is computed from is none), and its behavior mode in both runs, at most three; flagged when a behavior changes family materially |
| `loop_knockout` | a named variable held at its initial value, each element of an arrayed one at its own | the links and loops that cuts, and how the recorded variables respond |
| `disturbance` | each targeted constant stepped up a tenth, a tenth of the way into the run | how the recorded variables respond, and the loops that lead after the step |

- **Targets.** By default, the constants that feed the model's flows, those that reach the most stocks first, less the model's unit conversions, and for sensitivity and disturbance less its dates; an answer says once what the defaults left out (`leftOut`). A disturbance, a loop analysis each, steps the first three that are not zero. A knockout runs only on variables the call names. Recorded variables are the model's stocks by default. A call may give a constant its own `low` and `high` (`extremes`), which replace the rules' for the constant whose meaningful range its author knows.
- **Unit conversions are not inputs.** A constant whose value is one of its units changes the units a quantity is counted in, not the quantity, so zero or ten times it is a parameter made nonsensical. It is one when its units are a ratio of one unit at two scales and its value is their ratio (`1e6 tons/Mton`, `1e9 people/billion_people`, `1000 ppt/ppb`: SI prefixes, number words and pure-number units like percent), when its units are a ratio of two units of time and its value their known ratio, within 2% for the calendars' differences (`hours_per_week = 168 hour/week`, `days_per_year = 365` or `360 day/year`), or when its units are one unit and its name states its value in them, by any name the project reads as that unit (`one_year = 1 yr`, `100_percent`). A ratio that is not theirs is a quantity (`0.3 Mton/Gton`, `40 hour/week`), and a constant its name does not state is a parameter (`adjustment_time = 1 year`). A physical constant, a reference value or a unit carrier (`gdp_pc_unit = 1 $/(person*year)`) is tested like any other: nothing in its units says so. Vensim's `==` and an author's declared input range (Vensim's `[min,max]` in the units field, XMILE 1.0 section 4.1.1's `<range>`) would; the importers do not keep either.
- **An extreme is a condition of the system, not a value outside the constant's domain or an artifact of integration.** A constant some equation divides by has zero outside its domain, so its low extreme is a tenth of its value; any other's is zero. A time constant's low extreme is a tenth of its value and at least four DTs for each of its stages (a third-order delay's time spans three stages), with DT put in the constant's own unit of time: below that the run shows the integration (the low end of the rule that DT be a quarter to a tenth of the smallest time constant, Sterman, *Business Dynamics*, appendix A). A date, a constant used as a point in time (compared with `TIME`, or given to `STEP`, `RAMP` or `PULSE` as a time, directly or through an auxiliary that copies, selects or holds it), is tried at the run's start and a tenth of the run past its stop. The high extreme is ten times the value, except a share's, which is the whole, and a fractional rate's (a constant in one over a unit of time), which is at most one over two DTs: Euler's step of a first-order drain at rate `r` is `x(1 - r DT)`, which passes zero once `r DT` is over one and grows without bound past two, and at one over two DTs a step takes at most half the stock, so the extreme shows the drain and not Euler's step. No low extreme is above the value and no high one below it; a constant at its extreme already has no check there.
- **What only the model's DT finds is no finding.** An extreme conditions check that finds a problem as the run goes is tried again at a tenth of the DT, the same refinement the extreme applied to the system, and judged by that run, at most 12 checks a call; the test says how many found something only at the model's DT, and how many were not tried again. A sensitivity check is not run again: a family change that is Euler's is what the integration check names.
- **A test that would compare nothing is skipped.** A model whose stocks are all inside modules (which the tests do not read yet), or that has none, has its extreme conditions and integration tests skipped saying why, and the tests that compare recorded variables likewise when nothing is recorded; nothing checked is never passed. A model that does not simulate says why once, in `runFails`, and every test is skipped pointing there.
- **A call's own extremes.** `extremes` gives each constant one entry: a second entry for it is refused, as is a low above the high.
- **Time constants by units where there are units, by structure otherwise.** The time of a delay, smooth or trend is one, read from the engine's own tables (the argument wired to the stdlib model's `delay_time` port, its stages its model's stocks; `DELAYN` and `SMTHN` by their order). A constant with units is one when they are a unit of time, and is not otherwise. A constant declared dimensionless is one by its role where the rate it divides carries a unit warning, the declaration being the modeler's slip (workforce's `average_tenure`), and not where the rate's units balance (`pipeline / delay_time / number_of_stages`). A constant without units is one by its role in a rate: the divisor in `x / c` with `x` depending on a stock, unless `c` is a term of a sum in `x` (`(capacity - population) / capacity`, a scale); or a reciprocal beside such a factor, directly or through a fractional rate. A role is judged on the equation with the algebra that only spells it differently undone (`x * c ^ -1`, `x / c / 1` and `x * (1 / c)` read as `x / c`). A check at a short time says why its constant was taken for one (`timeConstant`). Only a time constant that paces a stock -- a delay's time, a divisor of a rate, or a number a rate's equation divides a stock-dependent quantity by (`backlog / 0.1`) -- is named as what DT is too large for: a capital-output ratio in years paces nothing.
- **Shares.** A constant is a share or fraction when it is within its whole and its units say so (`fraction`, `percent`), or, without units or dimensionless, its name does (share, fraction, proportion, percent) or an equation takes its complement (`1 - c`).
- **Below zero, said as what happened.** Under an extreme, a stock's element, or a series the model marks non-negative, is flagged when it goes below zero and the model's own run keeps it at or above zero; a stock with an element below zero in the model's own run (a heat anomaly, a balance) is a quantity with a sign and none of its elements is judged. A check says which series, from when and how far, and no cause: which flow drove it is the modeler's next question, and the tools that answer it are a call away. Below zero is below it by more than the residue floating point leaves at the series' scale (`behavior::residue_bound`, at the scale every tool reads the series at); a summary reports any number below zero as negative, and a `goes_negative` citation follows the summary.
- **What the model's own run already has is not a check's finding.** The model's own run is a check of its own, listed first: a series not a number in it is said there once and judged by no other check, and a series the model marks non-negative that goes below zero in it is flagged with a note that this engine does not enforce the marking, which a tool that does would hold at zero (an AI-generated model in the corpus runs three marked flows far below zero). That is the first thing a reviewer should hear.
- **Integration error is one measurement.** The difference between the model's run and the run at half its DT, and between that and the run at a quarter, give the order the runs converge at (about 1 for Euler, 4 for RK4 on a smooth model) and, by Richardson extrapolation, the error at the model's DT. Where the runs do not converge there is no error to estimate: an equation that reads DT makes each run another model, and a chaotic or discrete one has no trajectory to converge on; the check is flagged saying which, and gives no order.
- **A change of behavior family is material.** Which of linear, exponential, goal seeking or S-shaped growth a series reads as depends on the horizon as much as on the structure, so a sensitivity check is flagged for a change of behavior only when a recorded variable's mode changes family (still, rising, falling, rises then falls, falls then rises, oscillating; an overshoot that comes back less than 5% of its range is the movement it ends), its series' own range is at least 5% of its scale in one of the two runs, and its change is at least 5% of its scale somewhere. Each run is classified at its own scale, what the series is computed from in that run's equations, with the two series sharing the larger of their magnitudes (a series not a number somewhere shares none). The family comes from the classifier's mode, so a response's mode and family never disagree. The series' own turns, at 5% of its range, must change too, so a movement the classifier counts on one side of its threshold in one run and the other in the other is no change. A response shows the classifier's damping where the series oscillates (`damping`, and `wasDamping` where the check changed it), so a damped oscillation that a change makes grow is seen; it is not a change of family. Goal seeking is one behavior on either side of its goal. A check whose run makes a recorded series undefined, where the model's run has it a number throughout, has found something in any test, and is flagged.
- **What a family change cannot tell.** It reads the runs over the model's horizon, so an oscillation whose period a parameter lengthens past the horizon reads as one turn, and a start-up transient a parameter deepens until the classifier counts it as a movement reads as a turn. Both are listed for judgment and are the battery's main false alarms on the labeled corpus (below).
- **A model at rest hides its loops.** A model that starts in equilibrium has zero loop scores throughout, so dominance and loop polarity from a run are undefined there. The disturbance test is how the battery sees its structure.
- **What is listed.** A check that passed is counted, not listed, except sensitivity's strongest five. The model's own run is listed first. Sensitivity checks that flag the same change of the same series (one family to another) are listed once, as the strongest of them, naming the others in `sameChange`; a check whose half or double was held at an extreme names the rule that held it (`heldAt`). The others are shared between the tests in turn, each test's most telling first, so one test's many findings cannot crowd out another's; then put failures first, then checks that could not run, flagged, observed; at most 20 and within the answer budget, the rest counted. A check lists at most three responses and counts the further series it changed. Each listed check has an id (`T1`, ...) keyed by its test, target and condition, so running it again after an edit gives the same id, which is what a finding cites; a check left out gets no id.
- **Measured against a modeler's judgment.** `tools/battery_corpus.json` labels every check the battery lists over 29 corpus models -- whether a modeler would accept it as a finding about the model, and why, one person's judgment written so a reader can disagree with a row. Of 68 listed, 52 are accepted; the 16 rejected are start-up transients and periods past the horizon read as changes of family, constants that are definitions or references rather than conditions of the system, and integration artifacts of the model's own run that a change amplifies. An ignored gate holds the battery to the labels and these counts, and three small models do so in the default suite.
- **Cost.** Value-only checks share one compile and run in parallel VMs where the platform has threads, each run summarized as it finishes and its results dropped; a batch holds at most 64 MiB of results at once (`runs::concurrent_runs`, which a test lowers to count the runs it lets run together), so its memory does not grow with the host's cores. On a release build World3's battery takes 1.4 s and C-LEARN's 12.7 s (six of its 10 MB runs at a time), peaking at 450 MB, each answer within the outline budget. Once other work waits for the project, no further run starts and a run under way stops between its slices, and the battery stops and keeps nothing, the ids it gave out on the way included.

### Editing and the gate

`edit_model` takes a summary of the edit, for the person whose model it is, and operations as a tagged list (`add_stock`, `add_flow`, `add_variable`, `set_equation`, `set_units`, `set_notes`, `set_lookup`, `connect_flow`, `rename`, `delete`, `name_loop`, `set_sim_specs`). The call makes the edit or refuses it:

1. **One edit.** The operations are applied in order to a copy of the project, through the production patch path, so each sees the ones before it; a field edit keeps every field it does not set (an element's equation keeps the other elements', the `:EXCEPT:` default and whether it applies), and a flow's connections keep its stocks' lists whole. A loop is named by its session id, or by its variables, which must be one feedback loop of the model as the edit leaves it (the engine reads a named loop's variables as a set, so their order is no part of it): a set that is no loop is refused naming the link it lacks. Specs no run can be made under (a DT longer than the run, a run's length no number can hold) and an equation nested too deeply to read safely are refused at the operation that writes them. What the edit changes is its delta: every variable whose record differs, in any model of the project (a rename's rewritten readers, the stocks a flow leaves, the modules of other models that instantiate this one), each with its record before and after, the project's sim specs, and each loop name. A variable's provenance and its uid are not its record.
2. **Fresh.** Everything in the delta must be, before the edit, as the session last read it with `read_model`: the rule a tool that writes files keeps (read before you write; a write to something that changed since you read it fails and says what changed). An edit before any read is refused. The session's own edits need no read between: what one changed is held as read from the moment it is made.
3. **The gate.** The edited project is staged on the host's database, under a guard that restores the database however the gate ends, and judged against the project as it is by a policy whose rules are named one by one (`GatePolicy`; an agent's edit is held to all of them):
   - **Errors.** The project's diagnostics, every model's, are compared as problems are identified everywhere else in the surface: by variable, severity, code and the engine's reason (`evidence`), counted, with the project's own mapped through the edit's renames. An error the project did not have is refused. So is an error in an equation the edit writes, whether or not the variable had one: what an edit writes must stand on its own. An error in a variable's units is the units string's, which an edit of its equation did not write. The engine reports one error of an equation at a time (of an arrayed equation, its first failing element's) and one cycle of a model, so the elements an edit wrote are also judged with the variable's other elements set aside, and the edit is judged once more with the variables that were broken before it set aside: an error a broken variable hid is the model's, not the repair's, and a cycle written beside one the model had is still seen. A variable the edit removes that any equation still names is refused naming them, though the compiler need not report it (the equation may fail already).
   - **Simulation.** The model the edit is of, and the project's root model, which is what a person simulates, must still simulate if they did. An edit of a module's model is thus judged where the module is used, with its inputs wired.
   - **Values.** A value that is not a number, in either run, where the run before the edit had a number throughout.
   - **Unit warnings.** The first unit warning of a model that had none.
   - A run that would cost more than a run may (specs that cost more than the model's own and more than an experiment's limit) is refused under any policy.

   Every warning the edit adds is listed so the agent fixes it. The gate tolerates, by design:
   - errors the project had already, so a broken model can be repaired a step at a time. Fixing what one error names can bring out the next of the same variable; on a variable the edit does not write that is the model's own next problem, listed and not refused;
   - values not a number in a model that did not simulate before, which has no run to compare with.

   The staged diagnostics and each staged run are units of the call's work: a call a host cancels stops before each, making nothing.
4. **Placed.** An edit the gate passes, which can change the diagram, places what it adds with the engine's incremental layout (a whole layout for a model with no diagram), around the diagram as the person left it. An incremental layout decides the view's elements; everything else a view holds (its box, which is the viewport an editor keeps there, its name, zoom, lettering, font, the metadata an MDL writer keeps) stays the view's own.
5. **Made.** An edit the gate passes is made: the call's output carries the project as the edit leaves it (`ToolOutput::edited`), and the host makes it the project's contents in one edit and syncs its database to it. The host holds the project's contents for the whole call, as `simlin_project_apply_patch` does, so nothing changes between the gate and the edit, and it passes no `waiting`: a call that holds the contents has nothing to yield to. `edited` is present exactly when the edit was made and changes the project; a refusal, a cancelled call and an edit that changes nothing carry none.
6. **The answer**: an edit that changes no record is no edit: it is not gated, marks no provenance, draws nothing and is `unchanged`. A diagram drawn for a model that had none is no line. When a model that did not simulate does after the edit, the series that are not a number in its run are listed as warnings. For a made edit, one line per variable changed (a rename's rewritten readers and the modules of other models it rewires included, a loop named, the sim specs), the diagnostics it adds, whether the model simulates, and `unchanged` when the model already was as the edit asks (nothing changed, and `edited` is absent). Its `revision` is the revision of the contents the edit was made on: the engine does not know the revision the host gives the edited contents (a counter's next, or a hash of them), which the next `read_model` and the change report give. An edit the gate refuses is a refusal like any other tool's, `is_error` set, in the one refusal shape: its error names what refused it and how to repair it, and its `refusedEdit` names the rule (`errors`, `run_cost`, `simulation`, `values`, `unit_warnings`) and carries the lines, the diagnostics and whether the model would simulate, as the edit would have had them. A diagnostic a made edit leaves in the model is listed under its evidence id, the one the next `read_model` reports it by, so the agent can cite it or repair it without reading again; a refused edit's diagnostics are of no model and have none. The lines and diagnostics are fitted to the answer budget (a line's detail cut at 240 characters, the last diagnostics and then the last lines past the budget counted). A parse error in an equation that spells a variable as the model displays it, in several words, says how the equation language spells it. An input a deleted variable fed is left unwired, which no error reports and which changes what the module computes, so the answer says so in the module's line and as a warning.
7. **Provenance.** In a project that records who made its variables (`ai_state`, a letter per variable, read from ISEE's AI information), what an edit adds is marked made by AI (C) and what it edits marked edited by AI: a person's variable becomes D, or H once a person has edited it; an AI's stays C, or G once a person has edited it. A project that records no provenance gets none. This is in-app provenance: the transitions are unverified against ISEE's documentation, which states none, and a file the engine writes does not carry ISEE's signature.

The gate is `simlin-mcp-core`'s, moved where every host gets it and made stricter. It is shaped to become the one gate `simlin_project_apply_patch` and the MCP servers also call, each with its own policy.

The patch JSON's types live in the engine (`json::ProjectPatch`, `json` owning the project's JSON already), and convert to and from the engine's own `ProjectPatch`.

### Findings and verification

A finding is a flaw, a strength or an observation: a claim a person will read, and one to eight citations, each naming something a tool reported:

| Citation | Holds when |
|---|---|
| `variable` | the model has the variable |
| `equation` | the variable's equation (a stock's initial value; an element's, named by its subscript, which must name an element the variable has) parses the same as the cited one: spacing, case and the spelling of names aside. A variable with a table is its table at its equation's value, `LOOKUP(effect, input)`, and the input alone is not its equation; a table other equations look up has no equation of its own, and is cited with an empty one |
| `value` | the variable (or an element it has) is within 5% of the cited value at the cited time in the run (of the larger of the two, so never a value of the other sign); a cited zero holds for a value under 1e-5 of the series' largest magnitude, and nothing but a cited zero is judged by the series' size, so on a series that spans orders of magnitude one small value never stands for another; at the run's start when no time is cited, and a time outside the run is refused |
| `readers` | the variables that read the variable (`analysis::model_reads`: those whose equations read it in any phase, an initial value or `INIT` included, those that look it up as a table, a flow's stocks, the stocks and flows whose options name it, and an equation the compiler refuses by its text) are exactly the cited ones; none, for a variable nothing reads. It does not hold while an equation of the model does not parse, which may read the variable |
| `reads` | the variable reads the other (`analysis::model_reads`), through a link of the cited sign by its equation when a sign is cited |
| `diagnostic` | the model has the diagnostic of that id now |
| `no_diagnostics` | the model has no diagnostic (of the cited category) |
| `loop` | the run has the loop of that id, of the cited polarity (a mostly reinforcing loop is reinforcing) |
| `leads` | the loop's mean share of its partition's activity over the span's saved steps (from `from` to `to`, both included) is the largest there, or ties with it: the rule a timeline names a span's leader by |
| `no_loop_through` | no loop of the model goes through the variable, or the one element cited, active in the run or not (a loop through it is named, and said to be inactive when it is); unshowable when the analysis does not know every loop of the model: its structure too large to list them, and the run's analysis a sample, the most important of more than it keeps, or less those that never held a thousandth of the activity |
| `goes_negative` | the variable, or an element of it, goes below zero in the run: exactly when its summary reports a negative number |
| `peaks_at` | the variable peaks within 5% of the run of the cited time: it is at its largest there and lower at both ends of the run, by more than the noise a behavior mode ignores. A series still at its largest when the run ends (growth, or a plateau it rose to), or at its start, has no peak in the run: "peaks at the stop time" claims a decline the run does not show. A series at rest has none either, and a time outside the run is refused |
| `ends_near` | the variable ends at the cited value, as `value` judges one |
| `behavior_mode` | the classifier gives the variable the cited mode in the run |
| `compares` | the variable ends higher (or lower) in one run than another, by more than 5% of the larger and more than 1e-5 of the series' largest magnitude: runs that end a hair apart, or both at what reads as zero beside the series, end alike |
| `test` | the battery check of that id comes out as cited, run again when the model has changed since |

`verify_findings` checks each citation against the session at the current revision, deterministically, so a host can refuse to show a claim whose evidence does not hold, and an evaluation can check claims without judgment. A citation that fails says what is true instead ("population ends at 100 in run 'current'"). A finding every citation of which holds gets an id (`F1`, ...), keyed by its kind and claim, which the host shows it under. A run made before the model changed (its diagrams aside) is not evidence about the model: a citation of one fails and names the repair. The equation, value and readers citations exist because claims kept outrunning the others: "the capacity is now 1500" verified while citing only the variable, and "nothing uses the harvest fraction" while citing only that no loop goes through it. A variable of a run may be an element (`Population[north]`); a fact about one series of an arrayed variable names the element. Whether a claim follows from its citations is a judgment the surface does not make.

- `simlin_project_get_revision(project, out_revision, out_error)`.
- `simlin_tools_describe(out_buf, out_len, out_error)`: the catalog JSON in a `simlin_malloc` buffer.
- `SimlinToolSession`, refcounted, holding a reference to its model: `simlin_tool_session_new(model, out_error)`, `simlin_tool_session_ref`, `simlin_tool_session_unref`.
- `simlin_tool_session_call(session, name, input, input_len, out_buf, out_len, out_is_error, out_error)`: JSON in, JSON out. `out_is_error` carries a domain refusal; `out_error` only the host's misuse. A call of a tool whose effect is an edit holds the project's contents for the call and, when the call made an edit, makes the project it answered with the project's contents, as one edit, before it returns.
- `simlin_tool_session_get_changes(session, out_buf, out_len, out_error)`: the change report since the session's last `read_model`, as JSON, or `null`; `DoesNotExist` when the project no longer has the session's model. What the session's own edits changed is no part of it, so the report is the person's.
- `simlin_tool_session_get_run(session, name, out_revision, out_stale, out_error) -> *mut SimlinResults`: a named run's series for a host to chart, through the results handle `simlin_results_open_vdf` already returns, with the revision it was made at and whether it is stale. A run the session keeps the results of is read from the contents alone, so it waits for no call that holds the database.
- `simlin_tool_session_list_runs(session, out_buf, out_len, out_error)`: the named runs as JSON, oldest first, each with its revision, whether it is stale or gone, the run it started from, and everything it changed from the model, exactly as it ran: what a host's run list, chart picker and "run again" read. It reads the contents alone, never the database.
- `simlin_tool_session_forget_run(session, name, out_forgotten, out_error)`: forget a run the person discards, its series and its plan, so no tool reads it again; a run made from it keeps what it changed.
- `simlin_tool_session_cancel(session)`: cancel the session's calls under way, the one answering and any waiting for the session, as a host does when the window they were for closes. A call made after it runs as usual.

A call of a tool that reads holds its session for the call, and the project's datamodel only while it takes the contents it answers from and their revision. The contents are shared, not copied (`ProjectContents::shared`); an edit made meanwhile copies them first, as any edit of shared contents does. The call then answers under the db lock alone, and the db stays synced to those contents while the call holds it, since a sync needs the db lock. A call that finds the db held -- by another session's call, or by a host's query that holds only the db -- waits for it with the datamodel released, then takes the contents again. So a host's hit tests, planners and revision reads, which lock only the datamodel, never wait behind an analysis, which on the largest models takes seconds.

Work that holds the datamodel while it waits for the db -- an edit or an undo, a simulation, a read of the diagnostics, loop discovery, a wasm compile, a render that lays out a model with no view -- keeps those readers waiting with it, so a call yields to it; so does a query that takes the db alone (an equation's rendering, the model's links), which is the person's wait as much as an edit is. libsimlin counts such waiters: every lock of the db counts itself while it waits (`lock_db`, `lock_contents_and_db`, `lock_db_with`, `built_db`), and a call of `edit_model` from before it waits for its session, but a reading call's own lock does not, so two reading calls never stop for each other. A call checks the count between units of its work -- a slice of a simulation, or a stage of an analysis -- through `Workspace::waiting`, and stops there, answering a refusal marked `interrupted` that kept nothing. The waiter waits at most one unit, and the agent, or a host that retries by itself, calls again once the model is as the waiter left it: after an edit, at the next revision, and never in a loop against a project that stays busy, which would only take the database back from the person's work. Salsa's own cancellation would unwind the call, and a release build aborts on a panic; a second synced database for calls would double memory on exactly the models where calls are long.

A host cancels a call at the same checkpoints. Each call takes a ticket as it begins, before it waits for the session, and `simlin_tool_session_cancel` marks every ticket taken so far, with atomics alone, so any thread can cancel, and a later call is not cancelled. A call cancelled while it waits for its session answers as soon as it has it, without waiting for the db, which another session's call may hold. The engine's entry points fold `Workspace::cancelled` into what their checkpoints ask, so no checkpoint knows the difference, and a call a cancel stopped answers a refusal marked `cancelled`, not `interrupted`: nothing waits for it to be made again. Only `simlin_tool_session_call` is cancelled. The session is shared by everything a host shows of one model, and a host's own read of a run is not the agent's work. A loop analysis stops no sooner than its LTM compile ends: the compile is one query, and is not sliced. A call of `edit_model` is a write: it holds the datamodel for the call as `simlin_project_apply_patch` does, so nothing changes between its gate and its edit, and it counts itself among the waiters while it waits for the database, so a reading call that holds the database stops for it at its next checkpoint. It is given no `waiting` of its own; a cancel still stops it, before the edit is made.

The entry points are behind libsimlin's `agent_tools` feature (the engine's feature of the same name gates `tools`), on by default and off in the browser wasm bundle, as `png_render` is.

## MCP and pysimlin

- **pysimlin** binds the catalog (`simlin.tools.catalog()`) and a `simlin.ToolSession(model)` for its users and for evaluation harnesses, which then exercise the same functions a native host ships. `call(tool, input)` answers a `ToolOutput(data, is_error)`: a refusal is output the harness scores like any other, and only a tool the catalog lacks raises. `run(name)` reads a session run as the DataFrame `Run.results` gives, and `runs()` lists the session's runs with their revisions and staleness. A call of a tool whose catalog effect is `edit` that changed the project is committed as the project commits any edit (`Project._commit_tool_edit`: the revision moves, model caches are dropped, a file-backed model is written back, subscribers hear of it), under the lock order an edit takes, the project's file lock and then its handle lock; the session holds no Python lock of its own, so a cancel covers a call still waiting for the session and an edit is counted among the waiters before it waits.
- **simlin-mcp-core** mounts the catalog as MCP tools, each input schema extended with `projectPath` and `modelName`, holding one session per project path; `FileSystemAccess` supplies a content hash as the revision. A call of `edit_model` that makes an edit writes the project it answers with to its file, as `EditModel` does. The catalog's tools replace `ReadModel` and `EditModel`; `CreateModel`, which makes a file, stays a tool of the host's own.

## Relationship to other plans

- **Single-mode LTM** (`docs/design-plans/2026-09-07-ltm-single-mode.md`). `analyze_loops` reads the post-simulation discovery pipeline that plan keeps, and reports runtime polarity. Its session loop ids isolate agents from the engine's id change. Its structural fallback for a run at rest reads `model_detected_loops` out of discovery mode, which that plan replaces with `model_structural_loops`; the fallback moves to it, and gains World3 and C-LEARN, whose structure today is too large to enumerate. It needs one thing that plan's D4 would delete: a link's static sign. At equilibrium every link score is zero, so a model at rest has no runtime sign for any link; `read_variables` reports the static polarity, and a chain signs a link by its equation when the run never scored it. The replacement this surface needs is "the runtime sign when the run scored the link, the static sign otherwise".
- **Diagnostics' reasons.** Every diagnostic the engine formats carries a reason, the raising site's or, failing that, what its code means. An agent needs both what went wrong and where, so a report gives the site's reason and quotes the span whenever the diagnostic has one; a parse error, whose site wrote no reason, is reported by its span alone, and the code's meaning is the reason only when there is neither.
- **The editing core.** `edit_model`'s additions are placed by the same incremental layout, and its patch is the one the editing core's patches go through.

## Testing

- Every tool is tested through `Session::call` over models built with `TestProject`, `open_xmile` or `open_vensim`, and read back through production queries; no tool has a second path for tests.
- Decision tables derive their rows from their enums: every tool in the catalog, every kind a variable can be, every field a change report names, every behavior mode, every battery test, every citation kind, every edit operation.
- The catalog freshness test; a test that every catalog schema accepts the inputs the tool's tests send and rejects an unknown field.
- Output bounds: an outline and a loop analysis of every corpus model the suite already compiles stay within their budget (World3 and C-LEARN, with the other heavy gates, under `#[ignore]`); the outline budget itself is tested with a test-only override and a small model, and the loop analysis's order of leaving things out with a constructed analysis.
- libsimlin's integration harness drives each entry point: the revision advances exactly on mutations (a row per mutating entry point and per read, as `contents_tests.rs` rows the hit index), a session call from a model handle to JSON, refusals, and NULL safety.

## Phases

1. **The session and the read tools.** The contents revision and `simlin_project_get_revision`; `tools::Session`, the evidence ids for diagnostics, the change report, names; the catalog and its freshness test; `read_model`, `read_variables` (without behavior), `find_variables`; libsimlin's describe, session and call entry points; the links core moved into the engine as the one owner of a model's causal links with their polarities.
